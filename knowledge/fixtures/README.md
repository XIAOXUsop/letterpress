# 第二份真实内容集

`second-site/` 里的 markdown 是**给「第二个站点」这件事用的测试语料**（8 篇 + `Export Notes.md`）。
它们**不进 `src/content/`**，因此不会出现在构建产物里、不会被 lint 拦下、
也不会进 `content-manifest.json`。

由 `npm run verify:second-site-real` 读取。

**它抓到的第一个真缺口就是 `read-page` 的 slug 口径**（见下文）。

## 为什么需要它（而 `check-second-site.mjs` 不够）

`check-second-site.mjs` 用**硬编码的合成 docs 数组**，测的是
「核心函数在特定形状下对不对」（纯英文 slug、`kind: 'entity'`、一处刻意的断链）。

但路线图阶段 4 的退出条件是：

> **一个全新的真实内容集能在不复制内部代码的情况下使用核心流程。**

合成数组证明不了这一条——**它是我写出来的，天然符合我已经知道的形状**。
「我会用它」与「一份我没预先设计过的内容也能用」是两件事。

所以这里用**文件**，并且把**异构点事先写下来**（下一节），
而不是「随手造几篇看起来不一样的东西」。

## 异构点（每一项都有具体的风险，不是随手改）

| 维度 | 本站 `src/content/wiki/` | 这里 | 会咬人的地方 |
|---|---|---|---|
| slug 语言 | 全 ASCII | **中文** | `slugify` / `containsCjk` 的 CJK 分支 |
| slug 来源 | 多数靠文件名推导 | **部分显式写 `slug:`** + 一个文件名 ≠ slugify 结果的样本 | **这个异构点抓到了一个真缺口**（见下文），已修 |
| 章节标题 | 手写小节名 | **`## §1` 编号** | 段落切分与 `heading` 提取 |
| 关系字段 | `related:` | **`audience:`** | 核心只认 `related`，**适配层必须翻译** |
| 知识类型 | 5 concept / 1 entity | **2 synthesis / 3 concept / 1 entity** | `wikiKind` 的分布 |
| 同名标题 | 无 | **两篇「导出」+ 两篇「附录」** | `ambiguousTitles`；「导出」**被引用** → `ambiguous-wikilink`（error），「附录」**无人引用** → `ambiguous-title`（warn）。**两条规则分工不同，都要覆盖** |
| 孤儿页 | 无 | **若干**（互不引用的「导出」+ 刻意那篇） | `orphan-page` 规则 |

## 两条歧义规则的分工（此前只覆盖了一条）

| 规则 | 级别 | 触发条件 |
|---|---|---|
| `ambiguous-wikilink` | **error** | **有人写了**那个歧义标题（引用无法解析） |
| `ambiguous-title` | **warn** | 同名标题存在，**但还没人引用它**（预防性提醒） |

⚠️ **本 fixture 此前只触发前者**——两篇「导出」一个被 `[[导出]]` 引用、
一个被 `audience:` 声明，于是 warn 那条**恰好不触发**。

> **「恰好不触发」与「没有这条规则」在输出里长得一样**
> （本轮第三次撞上这个形状）。已加两篇 `附录-A/B`（同名、无人引用），
> 判据从「若报必是 warn」变成「**必报，且是 warn 级**」。

## 探针的负向验证抓出：**四条断言测的是巧合**

`npm run verify:second-site-real-mutations` 注入 7 种破坏，要求每次都以
**预期的那一条**断言变红。它抓出的最重要一件事是——
**第一版有四条断言测的是巧合**，它们在实现完全正确时也会变红：

| 断言 | 为什么是巧合 |
|---|---|
| 「孤儿页恰好 3 篇」 | 派生结果，`audience:` 加一条声明就变 2 |
| 「两篇都没拿到入链」 | `audience:` 给其中一篇入链就红 |
| 「`audience:` 被翻译」（查「审计日志有入链」） | 正文里本来就有真链接，**把 `audience:` 改名断言照样绿** |
| 「至少一篇是中文 slug」/「至少一段带 §」 | **只要求「有一个」**，改任意一篇都绿 |

> **一条通过但测不到机制的断言，比没有更糟**：
> 它让人以为那个机制被覆盖了。
>
> 而「变红」与「测不到机制」在输出里**长得一样**——
> 所以负向验证必须断言**报的是哪一条**，不能只看有没有红。

## `read-page` 的 slug 口径：已修（迭代 AS）

`readContentPage` **曾**只按文件名给 slug、不读 `slug:` 字段、也不跑 `slugify`；
而构建侧（`src/lib/content.ts:80`）走的是
`resolveSlug(data.title, data.slug, entry.id)`。

**实测后果**（fixture 里的 `Export Notes.md`，frontmatter 写 `slug: 导出说明`）：

```
read-page  → 「Export Notes」
构建侧     → 「导出说明」
```

`wiki:ask` 回答里的 `docId` 与 `content-manifest.json` 里的 id 对不上，
而订阅者正是靠那个 id 做增量同步的。

> 为什么长期没人发现：**letterpress 本仓库 0 篇写了 `slug:`**，
> 文件名也全是小写连字符（`slugify` 对它们是恒等的）。
> **一个在本站永远不触发的分支，就是没有守卫的分支。**

**已修**（`read-page` 改走 `resolveSlug`），并补了 6 条 slug 测试——
该模块此前**一条 slug 测试都没有**，那正是它能长期与构建侧漂开的原因。

## 这套语料第一次跑就暴露的五件事## 这套语料第一次跑就暴露的五件事

| # | 现象 | 是谁的错 |
|---|---|---|
| 1 | `Doc.summary` 是必填 `string`，而 `readContentPage` **不返回它** → `lint` 崩在 `.trim()` | **适配层**（真实站点得自己补） |
| 2 | 我读 `graph.ambiguous`（= 引用打向歧义标题的**引用**），要看的是 `graph.ambiguousTitles`（= 同名标题本身） | **探针** |
| 3 | 映射层不翻译 `audience:`，`[[审计日志]]` 就没有入链 → 被误判成孤儿页 | **适配层** |
| 4 | fixture 里把要测的 `[[导出]]` 写成了行内代码 `[[导出]]`，而 `parseWikiLinks` **正确地忽略**行内代码 | **fixture** |
| 5 | 探针写的规则名 `ambiguous-title` 不存在，实际是 `ambiguous-wikilink`（而且是 **error** 级） | **探针** |

> 第 2 与第 4 条都不是「实现有 bug」。
> **探针与 fixture 也要被验证**——它们的症状与实现坏了**完全一样**：
> 都是「那条断言红了」。第 4 条尤其危险：
> **把要测的东西写成了恰好不会被解析的形状**，于是测试永远测不到它。

## 它证明了什么、没证明什么

**证明了**：核心流程（链接图 / lint / 影响分析 / 检索 / context pack）
在**读自文件、与本站形状不同**的内容集上全部成立。

**没证明**：「接入一个新站点不用改核心」。因为适配层（映射 + slug 规则 +
关系字段翻译）**仍然是接新站点时要写的东西**——这次写了约 20 行。

> 路线图那条退出条件的另一半是「**第二个站点的接入确实减少重复维护，而非只做演示**」。
> **这一条本目录答不了**，它需要第二个站点真的用起来。

## 不要更新它来「修好」那些红

这套语料**刻意包含**会让 lint 报 error 的东西
（一处歧义引用 `[[导出]]`）——那是**要测的形状**，不是要修的缺陷。
探针的断言也把这些写死了（`error 只来自那一条歧义引用`），
所以「顺手把它改好」会让**探针变红**。
