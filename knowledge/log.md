# 维护记录

按时间倒序。每条记录一次「来源 → 影响清单 → 修订 → 复核 → 发布验证」的完整过程。

工具还没建（那是 M1 之后的事），所以这里都是**手工跑通的**——
先证明这条路走得通、走得值，再考虑把它自动化。

## 2026-09-24 · 迭代 BD：把「验证通过 ≠ 验证的是你要交付的东西」变成可执行的检查

上一轮末尾说了那句话，而**它当时只是一句结论**。
先核：仓库里有没有任何东西守着它？`grep --cached` → **零命中**。

而上一轮那次丢修复的机制正是它：修好乱码、验证「0 个」，
之后又改了别的文件，一次 `git add -A` 把两者混在一起提交——
**而门禁当时是绿的**（它核工作区，工作区是对的）。

### 先写进 `AGENTS.md`，因为它本来就是流程约定

原来那里只写「提交前跑 `verify:all`」，**没写「跑完就别再改」**。
补了顺序（改完 → 验证 → 看结论 → 直接提交；还要改就重跑）
与一句判断办法：`git status --short` 空 = 验证后没动过。

**但文档约定挡不住流程失误** —— 上一轮正是「文档写着要跑 verify，
而我没跑够就提交」。所以要有能执行的东西。

### `check-staged`

报的是**「`git add` 过之后又改了文件」**——那正是 `git add -A` 最容易漏看的状态。

变异验证：暂存后追加一行 → 红、点名文件、退出码 1；还原后回绿。
另报未跟踪文件（「改了 A 忘了 add B」是丢东西的另一个方向）。

### ⚠️ 它能做什么、不能做什么——写清楚了

- **能**：在已经 `add` 过之后，报出「暂存区 ≠ 工作区」。
- **不能**：保证「工作区里那份被验证过」。
  **没有任何 git 层面的检查能知道某次 `verify:all` 跑完之后有没有人改过文件**——
  那需要记录时间戳或内容哈希，而**门禁不写状态**。

> 所以它是**提交前的自检**，不是一道能替代 `verify:all` 的门禁。
> 把它挂在 `verify:all` 末尾的意义只是：**跑完它，你至少知道
> 此刻「工作区 = 暂存区」成立**，而那条信息在提交那一刻仍然有效。

## 2026-09-24 · 迭代 BC：一条走不通的路——不能从压缩产物里查「文件引用」

上一轮补完站内 JS 的对账后，想接着查「`pagefind.js` 到底引用了哪些产物文件」
——因为 README 那个更窄的口径（5 个 js）需要知道运行时加载链路。

### 先是一次误判

`grep -oE "pagefind-[a-z-]+\.js" pagefind.js` 的结果只有
`pagefind-entry.js` 与 `pagefind-worker.js`，
而产物目录里**没有** `pagefind-entry.js`（只有 `.json`）——
我一度以为是 bug（若真去 import 一个不存在的文件，搜索会在浏览器里失败）。

读完那行压缩代码才发现：**它引用的是 `pagefind-entry.json`，
我的正则只匹配 `.js`**。

> **用一个不完整的正则下了「文件不存在」的结论。**
> 这是本轮第 N 次「量出来不对的第一反应应该是尺子不对」。

### 然后是这条路本身走不通

改用宽松的 `\w[-\w]*\.(?:js|json|pagefind)` 重扫，
结果 **100+ 条「不存在」**——而绝大多数是误报：
`af.js`（语言码）、`mark.js`（高亮标记）、`this.pagefind`、`b.pagefind`……
那些是**压缩产物里的字符串片段**，不是文件引用。

> **压缩后的 JS 里无法可靠区分「一个路径字符串」与「恰好长得像路径的代码」。**
> 要可靠区分需要真正的词法分析或 source map，
> 而本项目不引那类依赖（与「零依赖、离线可跑」同源）。

**所以这条门禁不做。**「pagefind 产物完整」靠的是
`npm run build` 成功 + `check:search` 验索引覆盖面，不是扫字符串。

> 记下来的价值：**下一个人不必再走一遍**。
> 本项目里这类「看起来很自然的检查」已经试过多次，
> 每次都是「写完 → 大量误报 → 放弃」。

## 2026-09-24 · 迭代 BB：给「只能手抄的那几个数」配上对账

上一轮补了 `measure` 的 gzip 口径，**但没让文档用它，也没人核那几个数**。

核账：README「实测数据」表里的数，哪些有门禁？

| 数 | 有门禁核？ |
|---|---|
| CSS 24.1 KB / gzip 5.1 KB | ✅ `check-formats.mjs:208` |
| 字体 100 KB | ✅（注释里明确「README 写 100 KB 是对的」） |
| **站内 JS：6 个 / 431 KB / 93 KB** | ❌ **一个都没有** |

而 `check-formats.mjs` 里有一段注释写着「**站内 JS 体积刻意不在这里查**」——
理由成立（它只跑 `astro build`、不跑 pagefind，量到 0），
**但结论是「那三个数只能手抄」**，而上一轮刚实测到手抄的下场：
`design-notes.md` 的「实测 gzip 146 KB」活了好几天，而 README 已写明它作废。

### 补对账

`check:manifest-schema` **自己跑 `npm run build`**（含 pagefind），所以能核。
口径与 `measure` 完全一致（`Math.round(bytes/1024)`、`gzipSync(level: 9)`）。

变异验证：把 README 的 `431 KB` 改成 `999 KB` → 红，报错精确：

```
✗ README 的「站内 JS」一行没有 431 KB 这个数（产物实测 441271 bytes）。
  用 `npm run measure` 核对——**它的口径就是门禁的口径**。
```

### ⚠️ 刻意**不核**的那个数

README 另有一个更窄的口径：「访问者真正会加载 5 个、gzip 93 KB」。
**那不核**——它需要浏览器网络面板（`pagefind.js` 内部按需加载哪些 UI 组件
取决于页面配置，Node 里量不出来）。

> **一个门禁能核的数，与一个它核不了的数，要说清哪个是哪个。**
> 否则「93 KB」会和「105 KB」并列成两个「实测」，
> 而读者不知道它们是**上界**与**实测值**的区别。
> 两处文档现在都写明了这一点。

### 又一次「收尾语比判据少」

加了站内 JS 的对账之后，那句总结语仍只说三条
（schema / version / provenance）——**判据加了、总结句没跟上**。
这是本轮第三次（另两次：文档版本号那次、「不该红」那次）。

> **输出的总结句也是断言**：它说「我查了什么」，
> 而读者只能靠它判断这次验证覆盖了什么。

## 2026-09-24 · 迭代 BA：一个在文档里以「实测」身份活着的**不可复现**数字

上一轮说要把「空集合恒真」变成通用判据。扫了全仓 20 处候选，
确认 `check-base.mjs` 那两处是**对的**（遍历范围由前面的 `for` 定、外层有 `try/catch`），
三套金标也都**明确打印了实际量的条数**（23 / 20+3 跳过 / 9）—— **这一族已经做对了**。

于是换个方向：找**文档里那些没有命令能产出、只能手抄的实测数字**。

### 「实测 gzip 146 KB」——而 README 已说它无法复现

`docs/design-notes.md` 写「实测 gzip 146 KB」，
而 `README.md` 同一件事写的是：

> 此前写的「17 个文件、146 KB gzip」在当前环境**已无法复现**
> （pagefind 版本未变而产物结构对不上），故改为可复现的口径

**同一份仓库里，一个说「实测 146 KB」、另一个说「那个数已不可复现」。**

> **一个数在文档里以「实测」的身份活着，就没人会去质疑它**——
> 即使同仓库另一处已经写明它作废了。

### 为什么它会漂：`measure` 只输出未压缩

`npm run measure` 输出 `JS 未压缩合计 431 KB`，**没有 gzip 那一行**。
而文档里流传着三个 gzip 数（93 / 105 / 146），
**没有一个是任何命令能产出的**——所以它们只能靠手抄，也就只能漂。

已给 `measure` 补 gzip（`gzipSync(bytes, { level: 9 })`，与 CSS / 字体那两行同口径）：

```
JS 文件          6
JS 未压缩合计    431 KB
JS gzip 合计     105 KB（全部 6 个，可复现上界）
```

**`docs/design-notes.md` 已改用这个数**，并写明「146 KB 那个数在当前环境
已无法复现」及其原因（pagefind 版本未变而产物结构对不上：17 个文件 → 6 个）。

> **补一行输出比写一句「已修正」有价值得多**：
> 前者让下次漂移立刻能被 `measure` 指出，后者只是又一次「我改过了」。

### 顺带：那个更窄的口径（5 个 js / 93 KB）Node 里测不出来

`search.astro` 只 `import('pagefind.js')`，而它内部**按需加载**哪些 UI 组件
取决于页面配置 —— **那要浏览器网络面板才能确认**。

所以 `measure` 给的是**可复现的上界**（6 个 / 105 KB），
而 README 那个更窄的数是**浏览器实测值**（5 个 / 93 KB）。
**两者不是一回事，也不是矛盾** —— 已在两处都写明这一点。

> 与记忆里那条「本地模拟缺一条语义」同源：
> **Node 里的 Pagefind 不是浏览器里的那个**。

## 2026-09-24 · 迭代 AZ：「门禁报错了自己的数字」——假红比漏报更费时间

上一轮末尾说「把『空集合恒真』变成通用判据」。
先扫全仓哪些门禁的集合可能为空而断言用的是 `every`/`some`，扫出 20 处候选。

**第一处候选就中**：`verify-negotiation.mjs` 里那句
「docs/ 里一处都没提到契约条数——若本来是有的，说明这条检查没覆盖到，
别让它静默失效」。

### 它是「静默失效」本身

```js
check(
  docsMentions.every((d) => … === finalTotal),
  'docs/ 里写到的契约条数与实际一致',
  docsMentions.length === 0
    ? '（docs/ 里一处都没提到——…别让它静默失效）'   // ← 这是「详情」不是「判定」
    : `…`,
);
```

`check(ok, label, detail)` 的第三参是**失败时的详情**。
`docsMentions` 为空时 `every` **恒真** → `ok = true` → **那句提醒永远不会显示**。

> 注释写着「别让它静默失效」，而**它正是那个静默失效**。

已拆成独立的 `check(docsMentions.length > 0, …)`，并用「清空 `docs/` 里所有
「N 项契约」」验证过：两条都红，且文案正是那句提醒。

### ⚠️⚠️ 修它之后，「门禁报错了自己的数字」

契约数从 200 变 201，于是三处对账开始互相矛盾：

```
✗ README 里抄的契约条数与实际一致 — README 写 200，实际 200   ← 两边相等却报红
✗ docs/ 里写到的契约条数与实际一致 — …写 201；…写 201，实际 202
```

**我的第一反应是「我漏改了某处文档」，于是去改了两处本来正确的地方。**
> **假红比漏报更费时间**：漏报让你信错结果，假红让你去改对的东西。

根因试错两次，两次都是「一个『后面还有 N 条』的计数」：

| 试法 | 结果 |
|---|---|
| ① 手写 `reconciliationChecks = 2` | 我加了一条对账 → 少算。**而那段注释早就警告过「再加一条就会错位」，我正好又加了一条** |
| ② 改成「每次调用自增」 | 第二次比较时 `assertions` **已包含第一次对账自己产生的 check** → 多算（202） |

> **「边跑边数」必然自我污染**：被数的那个计数器，
> 会在数的过程中因为「数它的那次操作」而增加。
>
> 而两次失败**都表现为「门禁报错了自己的数字」**——
> 也就是说，这个设计的失败模式**就是「说谎」**，而它每次都装成「某处漂了」。

最终解法：把「会产生的对账条数」写成常量 `RECONCILIATION_CHECKS = 3`，
**在跑任何对账之前冻结** `finalTotal`。

> 这与 `check-single-source` 的教训同源：**同一个事实写两遍就会漂**。
> 差别是这一次「两份」是「一个常量与一串调用」，
> 而我**至少让它错在明处**（改错时门禁立刻报假红，而不是静默放过）。

### 顺带：本次是「空集合恒真」第四次

| # | 形态 |
|---|---|
| 1 | `check-exit-codes` 只认字面数字（已归类的出口不被计数） |
| 2 | `check-manifest-schema` 只查「产物多出来的字段」 |
| 3 | 探针的「若报必是 warn」在 0 条时恒真 |
| 4 | **本次**：`docsMentions.every(...)` 在空时恒真，且**把「该红」的理由写在了 detail 里** |

> 四次形态各异，**共同点是「门禁在空集合上通过了」**——
> 判据要问两件事：**被测的有几个？期望的有几个？**

## 2026-09-24 · 迭代 AY：我说错了一条规则名，而那句话已经被我抄进 log

上一轮（AX）为了给 `AGENTS.md` 写门禁，去对照文档与源码的规则名。
发现文档里有 `ambiguous-title` 而源码 `lint.ts` 里也**有**它——
于是我判定「那条规则名是错的」。

**错在这里**：我以为只有一条歧义规则，实际**有两条，分工不同**：

| 规则 | 级别 | 触发条件 |
|---|---|---|
| `ambiguous-wikilink` | **error** | **有人写了**那个歧义标题 |
| `ambiguous-title` | **warn** | 同名标题存在，**但还没人引用它** |

我上一轮在探针注释与 `knowledge/log.md` 里都写了
「规则名是 `ambiguous-wikilink`，**不是** `ambiguous-title`」——
**那句话是错的，而它已经被抄进 log**（log 是本项目的事实记录）。

> **注释里的错误陈述比没有注释更糟**：
> 读代码的人会拿它当依据，而它**看起来和正确的陈述一模一样**。
> 尤其当它被抄进一份「记录实测」的文档时——**它就获得了不该有的权威**。

断言当时**改对了**（用 `ambiguous-wikilink` + error 级），**只有注释说错了**。
已改注释，并补上一条 `ambiguous-title` 的断言。

### ⚠️ 补那条断言时撞上本轮第三次「恰好不触发」

`ambiguous-title` 在那份 fixture 里**0 条**——因为两篇「导出」都被引用了
（一个真 `[[导出]]`、一个 `audience:` 声明）。

而我第一版写的判据是「**若**报，必是 warn 级」——
**0 条时它恒真**，与「这条规则不存在」**在输出里长得一样**。

已加两篇 `附录-A/B`（同名、无人引用）让它**真的触发**，
判据变成「**必报 1 条且是 warn**」。

> 本轮第三次撞上这个形状：
> ① `check-exit-codes` 只认字面数字（已归类的出口不被计数）；
> ② `check-manifest-schema` 只查「产物多出来的字段」不查「schema 声明的字段」；
> ③ 本次「若报必是 warn」在 0 条时恒真。
>
> **三次都不是「门禁坏了」，而是「门禁在空集合上通过了」**。
> 判据要问两件事：**被测的有几个？期望的有几个？**

### 又一次「字段名传错而断言照样过」

给 `buildContextPack` 传了 `docId`，而 `PackDoc` 要的是 **`slug`**。
于是每篇的 docId 都是 undefined——**而「拿得到证据」那条断言照样通过**，
因为它查的 `sources` / `review` 与 docId 无关。

> 同一个字段名在三处叫三个样（`Doc.slug` / `Page.slug` / `Passage.docId`），
> 传错**不报错、只静默丢值**——与迭代 AO 那次（`refs` vs `sources`）完全同型。

已加断言「每个 passage 都有非空 docId」，变异验证：改回 `docId` → 红，还原 → 绿。

## 2026-09-24 · 迭代 AX：`AGENTS.md` 的可证伪声明——以及「子串匹配是最容易骗过自己的判据」

29 步门禁里**没有一个查 `AGENTS.md`**。而它是**给 agent 读的项目约定**——
agent 按它行事，它若与代码不符，agent 会照着错的改，**而所有门禁都绿**
（它们检查代码，不检查这份文件）。

那份文件里「`verify:all` 上面全部 + N 道门禁」的 N 先后是
**10 / 11 / 13 / 17 / 19 / 26 / 28 / 29**——而 `docs/cli.md` 与 `README.md`
各有一份，**只有后两份有门禁**。

### 只查能被代码直接判真伪的那三类

**不检查整份文档**：大部分是散文，查不动也会误报（改个措辞不是错）。

| 类 | 例 | 怎么验 |
|---|---|---|
| 规则名 | 「lint 会报 `redundant-relation`」 | 造一份「同一页把关系写两遍」的文档，看那条规则**真的触发** |
| 例子 slug | `related: [design-tokens]` | 那个 slug **真的存在**吗 |
| 行为声明 | 「写标题与写 slug 指向同一页」 | `buildGraph` **真的这么解析**吗 |

### ⚠️ 判据试错了两次，而两次都是变异验证抓出来的

**第一次：纯子串匹配（`includes`）**。
变异把 `redundant-relation` 改成 `redundant-relation-XXX`——**门禁全绿**。

> **子串匹配是最容易骗过自己的判据**：
> 它在「什么都没变」时永远通过，而在「多了一点东西」时**也**通过——
> 两种情况在输出里一模一样。

**第二次：改成「逐行全等」**——结果三处**真实**声明全被判成「找不到」，
因为它们在文档里都是**句中的一部分**
（`现在 lint 会报 redundant-relation（警告级）。`）。

**最终判据分两种**：
- `ident`（规则名 / 命令名 / slug）→ **词边界**匹配：`(?<![\w-])X(?![\w-])`；
- `phrase`（中文句子）→ 普通子串。

三个变异全部被抓住（加后缀 / 例子 slug 改不存在 / 删掉中文那句），还原后回绿。

### 探针自己又造错了一次

第一条门禁报「`redundant-relation` 规则不存在或触发不了」——
而**真相是我造的例子错了**：我造的是「甲页链乙页 + 乙页 related 指甲页」
（**互相引用**），而规则要抓的是「**同一页**把同一条关系写两遍」。

> **又一次「探针报错 ≠ 实现有 bug」**。
> 而这次门禁的报错文案（「不存在**或触发不了**」）恰好把两种可能都留了位置——
> **那句「或」是本轮唯一一次我写对了**。

### 顺带：我在核实时差点得出一个错误结论

去验「标题与 slug 指向同一页」时，我造了一篇 `[[自己的标题]]` 的文档，
发现「断链 0、出边 0、入链 0」，一度以为是 bug。

查下去发现 `buildGraph` 里有一行**有意为之**：

```js
if (resolved === doc.slug) continue; // 自链接不构成入链
```

## 2026-09-24 · 迭代 AQ：Knowledge IR 的版本策略——以及「它报了」不等于「它判了」

路线图阶段 4 第 1 项：**发布 Knowledge IR schema 与版本策略**。

### 先核账：那个词在仓库里一次都没出现过

`grep -r "Knowledge IR"` → **零命中**。而路线图把它列成了待办。

**但这份结构其实早就在生产里**：`content-manifest.json` 的
`documents[].provenance`（v2 起，11 篇里 8 篇有，线上可取）——
「依据从哪来 + 有没有被确认过」的结构化表示，就是一份 IR。

> **它只是没被当 IR 命名过。** 路线图写的是一项**待办**，
> 而实际是「**给已有结构补上说明**」。不核账就动手，很容易新造一套
> 平行结构——那正是「同一个事实有几个表面」的开头。

### 结论：不需要第二个版本号

判据写成一问一答（`docs/content-manifest.md`）：

| 问题 | 答案 |
|---|---|
| 版本号在哪 | **就是顶层 `version`**——它是 manifest 文档的一部分，不是独立格式 |
| 为什么不给单独的号 | 单给它一个号，等于要回答「manifest v2 + IR v1 这个组合是什么」；而现实中只会出现「manifest 的某个版本」 |

版本策略沿用 `CONTENT_MANIFEST_VERSION` 上方那条判据
（**「产物里已有文档的 JSON 形状变了，就升」**），
因为 `provenance` 是 `documents[]` 里一条文档的**子结构**——
它变了，manifest 的形状就变了。

### ⚠️ 补文档时立刻撞见一处自相矛盾

> 那句话是迭代 K 升版本时漏下的。**它能活这么久，是因为没有任何东西核对
> 文档里的版本号**——而 `check-single-source` 当时只扫代码。
> **加了检查却只覆盖一半，和没加一样。**

已把文档侧的版本号纳入 `check-single-source`，
并**故意不扫 `knowledge/log.md`**：那里记的是**历史事实**
（迭代 K 那次确实还是 1），改它等于篡改记录。
> 「全仓无一处旧数字」不是目标，**「声称现状的地方没有旧数字」**才是。

## 2026-09-24 · 迭代 AP：JSON 输出——以及门禁里一条**永远走不到**的判据

阶段 4 第 3 项剩的三件事里，错误码（AM）与迁移命令（AN）已做，剩下 JSON 输出。

### 缺口：成功时是 JSON，失败时 stdout 完全空

```
node scripts/wiki-ask.mjs --json
退出码 2 · stdout 0 字节 · stderr「给一个问题。…」
```

消费方能拿到的只有退出码——它回答「哪一类失败」，
回答不了「**什么**失败了」与「**能怎么改**」。

### 形状按「消费方要区分什么」定，不按「我觉得该有哪些字段」

| 消费方要做的判断 | 靠哪个字段 |
|---|---|
| 是「我用法错了」还是「工具坏了」 | `error.code`（与退出码同一个数） |
| 给人看的一句话 | `error.message` |
| 能不能自己修 | `error.hint` |
| 「还有哪些值合法」 | `error.valid`（可选数组） |

**成功时也带 `ok`**：消费方要能写「先 `JSON.parse`，再看 `ok`」，
而不必在解析前先判断这次是不是成功——**很多运行时会丢掉退出码**
（容器、某些 CI 包装），而 stdout 里的 JSON 总是拿得到的。

`wiki:ask` 的「无依据」是**成功不是失败**（`supported: false`），
所以它的 `ok` 仍是 true——**那是一条结论，不是一次错误**。

### ⚠️ JSON 里刻意不写 `checkedAt`

`wiki:review` 人读的输出里有一行 `checkedAt: <今天>`
（那正是「你实际复核的那天」，填当前日期是对的）。但**它不能进 JSON**：

> JSON 输出要能被 diff、能被缓存、能被断言。
> 带当天日期的话，**同一天之外的每次运行结果都不同**——
> 而内容一个字都没变。这与本项目「可复现构建」是同一条主张。

日期由人自己填——反正「我复核过了」是人的承诺。

### 共用模块而不是各写一遍

四个 CLI 的 JSON 形状如果各写一次，**迟早有一处漂**（迭代 AN 的教训）。
所以抽 `src/lib/cli/json-output.mjs`（`jsonOk` / `jsonError` / `failWithJson`）。

`wiki:impact` 的 JSON 分支**放在人读输出之前、复用同一批变量**——
这样「三组互不重叠」那条不变式**只在一个地方成立**。
复制一份到 JSON 里的话，迟早会有一边漏掉重叠检查。

### 新门禁：逐个真跑，不读源码

要验的东西**只在运行时存在**：stdout 有没有、是不是合法 JSON、字段齐不齐、
`error.code` 与退出码一不一致。**没有一样能从源码推断**——
一个 `if (asJson) console.log(…)` 写对了，不代表错误路径也走到了它。

所以对**每个 CLI 的每种失败方式**都真跑一遍。
第一条跑就红了 5 处：4 个 CLI 的失败路径 + 成功时缺 `ok`。

### ⚠️⚠️ 门禁里有一条**结构上永远走不到**的判据

负向验证第三类（`error.code` 与退出码不一致）第一次没报红。

改的是调用点的参数（`EXIT_NOT_FOUND` → `+1`），而
`failWithJson` 用**同一个 `code`** 既写 JSON 又退出——
**两边永远一起变**，我改的那个东西根本产生不了分叉。

改注入点为 `failWithJson` 里的 `process.exit(code)` 那一行，它才真的分叉。
可门禁**还是没报「两边打架」**——它报的是「退出码是 1，期望 5」。

> 真因：判据写成
>
> ```js
> if (r.code !== scenario.expectCode) { fail(...); return; }   // ← 这里 return 了
> …
> else if (payload.error.code !== r.code) { fail('两边会打架') }  // ← 永远到不了
> ```
>
> **一条永远走不到的判据，和没有这条判据是一样的**——
> 区别只在于前者看起来像是覆盖了。
>
> 改成不提前返回，让同一场景里所有问题一次报全。
> 而那次变异之所以能暴露它，是因为**负向验证断言「报的是哪一条」**：
> 它看到门禁红了，但红的是「退出码不对」而不是「两边打架」，
> 于是判定「这次验证不算数」，回头才查出上面那个 `return`。

### 负向验证的注入方式也错了两次

| 错法 | 症状 |
|---|---|
| 注入正则 `[\s\S]*?
  \}\);` | 一路吃到下一个 `});`，把后面几段也删了——门禁红，但**红的原因是「脚本语法坏了」** |
| 改某个 CLI 的调用点 | 只影响一个场景，而门禁读四个场景——**改 `jsonError` 里那一行才是唯一来源** |

> **「门禁报红了」不等于「门禁因为你想的原因报红」。**
> 所以负向验证必须断言**报的是哪一条**。
> 这是本轮第四次「判据要匹配真实输出，而不是匹配你记得的那句话」。

### 变更

| 文件 | 改动 |
|---|---|
| `src/lib/cli/json-output.mjs` | 新增：共用形状 + `failWithJson` |
| 4 个 CLI | 成功路径加 JSON；错误路径走 `failWithJson`；`wiki:review` 的 JSON 不写 `checkedAt` |
| `scripts/check-json-output.mjs` | 新门禁：4 个失败场景 + 1 个成功场景 |
| `scripts/json-output.mutations.mjs` | 负向验证（三类违约） |

`verify:all` 24 → **26 步**。

### ⚠️ 一个**上一轮的**负向验证被本轮改动打死了

跑全量时它红了：

```
✗ ① 写回字面 exit(1)：锚点 "process.exit(EXIT_NOT_FOUND);" 找不到（源码已漂，变异没注入）
```

真因：本轮把 `wiki-review.mjs` 的错误出口改走 `failWithJson(...)`，
而那个锚点**正是那一行**。

> **症状是「全量红」而不是「假绿」，这靠的是变异脚本里那句
> `if (!original.includes(find))`——锚点找不到时显式失败。**
> 少了它，「没注入」与「注入了但门禁没抓到」在输出里**长得一样**，
> 而后者是门禁的洞，前者只是脚本过期。

修的过程绕了两步，都记下来：

1. 改注入点为 `json-output.mjs` 里的 `process.exit(code)` ——
   **门禁抓不到，而抓不到是对的**：`check-exit-codes` 只管面向用户的 CLI，
   库文件不在名单里。**这是范围窄，而不是洞**（门禁文件里写明了「门禁脚本的
   `exit(1)` 不在管辖内」）。
2. 改回 CLI 里，用 `wiki-impact.mjs` 现存的 `process.exit(EXIT_INVARIANT)` ——
   三个变异都报红了。

改完还发现**注释标题写着「换到了 json-output.mjs」而实际是 wiki-impact.mjs** ——
与本轮反复出现的那类同型，只是方向相反：**代码改了、注释没跟上**。

> **负向验证脚本是会被自己的重构打死的。**
> 而它死的时候**必须自己报出来**，否则「门禁失效」会被读成「门禁通过」。
> 这句话本身就该写进每一个变异脚本的头部。

## 2026-09-24 · 迭代 AO：`wiki:review` 把 6 个知识页全报成「未复核」——而它们都是

**6 个全是未复核。** 而它们的 frontmatter 里明明白白写着：

```yaml
review:
  status: reviewed
  checkedAt: 2026-09-24
  contentDigest: ad9e1ec0…
```

### 根因：两份 frontmatter 解析漂开了

| 位置 | 怎么读 status | 结果 |
|---|---|---|
| `src/lib/wiki/read-page.ts` | 解析 `review:` **块** | ✅ `reviewed` |
| `scripts/wiki-review.mjs` | `frontmatterField(source,'status')` 用 `^status:` 匹配**行首** | ❌ `null` |

状态写在 `review:` 块里**缩进两格**，行首正则永远匹配不到。

> 而那个脚本的注释写着「**直接 import TS 源，不在这里重写一份算法**」——
> **紧接着就重写了 `frontmatterField` 与 `bodyOf` 两个函数。**
> 那是本轮**第五次**「注释承诺了而代码没做」。
>
> **为什么这个 bug 能活这么久**：它报的是「未复核」——
> **一个听起来完全合理的默认值**。没有报错、没有异常，
> 而「未复核」在任何页面刚写完时都是对的。
> 要到有人把 status 改成 `reviewed` 才会显形，而**没有检查去比对**。

### 修法：删掉那份实现，用同一份解析

改调 `readContentPage`。**第一版又崩了**（`toLf(undefined)`）：
它**不返回 `summary`**——它是给检索用的，检索不需要摘要。
改用 `frontmatterField` 补 `summary`，而那份**只认顶层字段**
（注释明说「忽略缩进，避免取到 tags 之类的子项」），读 `status` 依然读不到。

> **结论：两个模块分工明确，两个都要，一个都不够。**
> `frontmatter.ts` 取顶层标量，`read-page.ts` 取嵌套块。
> 而这正是原先那份手写实现想糊过去的复杂度——
> **它不复杂，它是「少了一处统一」**。

### ⚠️ 换实现时差点弄坏摘要，而那正是原注释警告的事

改完之后状态对了，但**三个知识页算出的摘要与 frontmatter 全不一样**——
若上线，6 个已复核页会**全部变成 stale**，症状是「机制坏了」。

真因：`readContentPage` 切出的 `body` **以一个空行开头**，
而摘要要求与 Astro 的 `entry.body` 同口径（**trim 过**）。

> 那个 `trim()` 的必要性**原先只写在 `wiki-review.mjs` 自己的注释里**，
> 而那份实现连同注释一起被换掉了。
> **约定写在调用方而不是被调用方，换实现时就丢了**——
> 而丢失之后症状是「静默算错」，不是报错。
>
> 修法落在 `read-page.ts`（它本来就该兑现「与 Astro 同口径」这个语义），
> 并补 11 条直接测试——**那个模块此前没有自己的测试文件**，
> 453 条里只有 `context-pack.test.ts` 间接用到它。

### parseReview 犯过两次同型的错，第二次只修了一半

补 `contentDigest` 时发现读不到。查下来：`parseReview` 的正则
`(?=
[^\s]|?
?$)` 里，**`?
?` 的 `
?` 是可选的**，
而多行模式下 `$` 匹配**每一行**的行尾 —— 于是在 `status` 行末**零消耗**地成立，
捕获组**只有第一行**。

| 时间 | 正则 | 症状 |
|---|---|---|
| 迭代 I 修之前 | `(?=
\S|\s*$)` | 捕获组**恒空**，函数恒返回 `undefined` |
| 迭代 I 修之后 | `(?=
[^\s]\|?
?$)` | 能读到 `status`，**读不到后两行** |
| 本轮修之后 | `^review:?
((?:^[ 	]+.*?
?)+)` | 块里全部缩进行 |

> **「修好了」和「修对了」不是一回事。** 第一次的验收标准是「能读到 status」，
> 那个标准通过了；而「能读到全部三行」从没被测过。
> **判据只覆盖了故障的一个切面**——而那次修复是被另一个症状逼出来的，
> 不是被「完整的行为」逼出来的。

### 一个静默跳过的检查，等于没有检查

给新门禁加第二条判据（摘要对账）时，它输出**一排「跳过」**然后报告通过。

  ...（6 个全跳过）

>
> **所以判据要问两件事**：被测的有几个？期望的有几个？
> **只问「有没有不一致」的话，全跳过时它当然一致。**

### ⚠️ 编排门禁的判据又失效一次——而这次是我自己刚加的

### 当场验掉一个自己登记的「未决」——结果它是真的

上面原本记着一条未决：「`parseReview` 的新正则只测了三种形状，块里夹空行没测」。

**那就当场测**（而不是留在纸上）：

```
块中间一个空行  → {"status":"reviewed"}     ← contentDigest 丢了
两个字段之间都空 → {"status":"reviewed"}     ← 同样丢
```

**它是真的**。`review:` 块里夹一个空行在 YAML 里完全合法，
而 `(?:^[ 	]+.*?
?)+` 遇到空行就停。

而 `?
?` 这种**可选量词**正是让边界悄悄提前成立的元凶。

最终**不用正则**：逐行扫，规则一句话说完——
**缩进行属于块，空行忽略，任何非缩进的非空行结束块**。

七种形状实测全对（无空行 / 中间空行 / 每字段间都空 / 紧跟顶层字段 / CRLF+空行 /
只有 status / 没有 review 块），并补了 3 条回归用例（453 → 464 → **467**）。

> **「已登记为未决」不等于「已想清楚」。** 登记那一刻我只是推测
> 「会不会真这么写」，而**测一次的成本是几十秒**——
> 结论是它真会，而且后果正是今天第三次出现的
> **「静默跳过的检查等于没有检查」**。

## 2026-09-24 · 迭代 AN：写迁移器时挖出一个真 bug——同步器对着本站自己的清单必然失败

路线图阶段 4 第 2 项：「设计 manifest v2，同时保留 v1 读取或转换路径」。

### 先核一个前提，结果推翻了它

我在上一轮（AM）的「未决」里写着：**「v1 从未真正发布过，可评估是否需要迁移」**。

实测线上：

```
curl https://xiaoxusop.github.io/letterpress/content-manifest.json
→ version = 1，11 篇文档，字段里没有 provenance
```

> **那句是错的。v1 有真实消费方**（Demo 线上 + 文档推荐的订阅方式）。
> 我当时是从 git 历史推断的（「加 provenance 那次一并升了号」），
> **没去查线上**——而线上是唯一的事实来源。
>
> **教训：「从提交历史推断线上状态」是推断，不是核实。**
> 有 URL 就该 curl 一次，成本几秒。

### 迁移器最重要的一条：不补 provenance

真实 v1 的 11 篇**一条来源信息都没有**。补默认值都是撒谎：

| 补什么 | 为什么错 |
|---|---|
| `review.status: pending` | 没人复核过，不是「待复核」 |
| `original: { reason }` | 不是原创实践，是**从未进过这个系统** |
| 整键缺席 | ✅ 正确——但与「查过、确认无来源」又长得一样 |

第三种才是真问题。**而这个坑本项目已经踩过**：
`provenance` 字段存在的理由就是「让『没有来源』有两种可区分的含义」。

所以迁移器的立场是：**如实保留「v1 没有这个字段」这个事实**，
逐条 warn 报出，不补任何默认值。

> 「v1 迁到 v2 只是加个可选字段，看起来不需要迁移器」——
> **这个假设本身没有门禁验证过**。迁移器的价值不是「转换」，
> 是把「v1 能不能升到 v2」变成**可执行、可复现、可回归**的事。

### 逐字段列举，而不是 `{ ...input, version: 2 }`

展开运算符会在 v1 日后新增字段时**静默带过去**——
那些字段可能是 v1 独有、v2 已删除的，迁移器会毫无察觉地产出一个
「看着像 v2」的清单。所以：**多出任何一个不认识的键就报错**。

### 退出条件两句都要有证据

路线图写的是「v1 数据可确定性迁移到 v2，**失败时有精确诊断**」。

- **确定性**：跨时区（UTC / America/Los_Angeles）跑三次，`cmp` 逐字节一致。
- **精确诊断**：5 种坏法逐一注入，全部报出**能定位到具体条目**的诊断。
  其中「出现不认识的 v1 字段」最要紧——它对应上面那个展开运算符的坑。

> 写坏法 ⑤ 时我的断言正则写的是 `/不认识的 v1 字段/`，
> 而实际输出是「**不认识**的 v1 字段」——**差一个「**」**。
> 结果实现对了、正则报了错，看起来像「没拦下」。
> 改判据时该做的第一件事是**看一眼它现在到底打印什么**。

### ⚠️⚠️ 真正的发现：同步器对着本站自己的 v2 清单必然失败

为了写迁移器去读 `content-sync.mjs`，看见：

```js

```

|---|---|
| `src/lib/content-manifest.ts`（生产端） | `2` |
| `scripts/lib/content-sync.mjs`（同步器） | **`1`** |
| `scripts/lib/content-sync.test.mjs`（测试固件） | **`1`** |
| `scripts/check-formats.mjs`（门禁期望） | `2` |

提交 `2518438` 把生产端升到 2 时，后两处没跟上。后果：

```

**所以那确实是 bug，不是误报。**

> 测试用了和生产端不同的固件，于是它测的是**另一个版本**。

`content-manifest.ts` 内部用 `.js` 后缀 import，**裸 Node 加载不了**

## 2026-09-24 · 迭代 AM：给 CLI 一份稳定错误码——「这个工具坏了」不该和「你参数写错了」同一个码

路线图阶段 4 第 3 项：「CLI 提供**稳定错误码**、JSON 输出和迁移命令」。
`--json` 迭代 L 有了，**错误码此前一个字都没有**。

### 核账：14 处非零退出，只有 1 和 2

逐处看语义（不看数字）：

| 曾经的码 | 实际语义 | 处数 |
|---|---|---|
| 2 | 用法错（没给参数） | 2 |
| 1 | 环境错（读不到目录 / 同步失败） | 4 |
| 1 | 内容为空（语料 / 来源登记为零） | 3 |
| 1 | 查无此项（slug / sourceId / revision 不存在） | 3 |
| 1 | **内部不变式被破坏**（三组重叠） | 1 |

**最后那类最要紧**：它意味着「本工具的 bug」，却和「用户拼错参数」共用 `exit(1)`。
消费方（CI 包装脚本）没法区分「提示改用法」和「报 bug」。

### 一个刻意的设计：`exit(1)` 被保留，但禁止主动使用

码表（`src/lib/cli/exit-codes.mjs`）给 6 个语义留了 2–6，**`1` 留给「未归类」**。
理由是**让漏归类可见**：

> 若没有 1 这档，某个出口忘了归类就得随便挑一个——而「随便挑的」看起来和
> 「认真挑的」一模一样。若 1 专表「未归类」，忘归类会**退化成 1**，
> 而门禁只禁止主动用它，**于是退化和刻意用法在源码里长得不一样**。

`failWith()` 里也硬性拒绝用 1，并要求新语义先在 `EXIT_MEANINGS` 登记。
**码一旦发布不再改**（消费方会写进 `case` 分支）；废弃时保留码并注明，不复用。

### 门禁只查「有没有漏归类的 1」，不查「这个码对不对」

「slug 不存在该用 4 还是 5」是**语义判断**，脚本判不了；
硬编成表只会多一份需要同步的真相。
而「**你用了 `exit(1)`**」是机械可判的：要么归了类，要么没归。

**范围也刻意窄**：只管 4 个面向用户的 CLI，**门禁脚本的 `exit(1)` 不管**——
它们是二元的（红/绿），退出码只回答「过没过」。
把它们一起管就是误报，而**一个会误报的检查比没有检查更糟**（它训练人忽略输出）。

### 门禁第一版统计口径是错的，差点让我以为改完了

改完 11 处后门禁输出「`wiki-ask` 退出码 0（2 处）」——
可它明明有 5 个 `process.exit`。原因：门禁只认**字面数字**，
`exit(EXIT_USAGE)` 它不认，于是已归类的出口**根本没被计数**。

> **「改了名」不等于「被检查」**。和迭代 AK 的 JSON-LD、
> 迭代 AL 的「选项留着但调用点不传」同一个形状：
> **声明了/改名了，而机制没接上。**
>
> 补法是让门禁同时识别常量名，并**逐个 import 真实常量**而不是靠语义反查。

### 负向验证：三种漏法，第三种最要紧

| 变异 | 门禁表现 | 为什么重要 |
|---|---|---|
| 字面 `exit(1)` | 红（未归类） | 正是要防的 |
| 拼错的常量名 | 红（认不出来） | 本仓库根本 import 不到，自己会暴露 |
| **语法合法但未登记的数字** | 红（没有登记） | **不会自己暴露**——它能编译、能运行，只是「这个码没语义」 |

`exit(9)` 就是第三种：码表只到 6，而 9 既不是 1（未被禁止）也没被登记。
**门禁抓的是「没语义」这个状态本身**，不是某几个具体数字。

### 实测（不只看门禁）

改了 16 处退出码，**逐个真跑一遍**：

```
wiki-ask 无参数            → 2  ✓
wiki-review 不存在的 slug  → 5  ✓
wiki-impact 不存在的来源   → 5  ✓
sync-content 无参数        → 2  ✓
wiki-ask 正常查询          → 0  ✓
```

### 顺带：编排门禁一次抓到三处

新脚本接进 `verify:all` 后，`verify:gates` 同时报出：
第 14 步位置不对、`EXPECTED` 与实际不符、**`docs/cli.md` 的列表落后**。
三处都是真问题——而其中 cli.md 那条**上一轮刚加的检查**第一次就派上用场。
（`package.json` 的顺序是我随手插的，与 `EXPECTED` 不符；对齐了两边。）

### 未决

1. **「稳定」目前只对源码成立。** 这些码第一次发布是本 commit，
   此前 4 个 CLI 用的是 1/2。**算不算破坏性变更取决于有没有外部消费方**——
   本仓库的 CI 只用退出码判成败，不区分 1 和 5，所以对内无破坏。

## 2026-09-24 · 迭代 AL：把「本站才知道的事」从核心里剥出来——以及剥了 5 轮才发现门禁没生效

路线图阶段 4 第 6 项：「记录 API 稳定边界，**剥离仅属于当前站点的展示逻辑**」。

先核账：工作项 4（JSON-LD）迭代 AK 刚做完；工作项 3 有一半；
**工作项 6 检索零命中**——「API 稳定边界」这个说法在仓库里一次都没出现过。

### 核心模块里有两处写死的本站结构

| 位置 | 写死了什么 | 能不能覆盖 |
|---|---|---|
| `graph.ts` `urlFor()` | `/wiki/${slug}/` | ❌ 完全不能 |
| `lint.ts` `checkReservedPostRoutes()` | 本站 7 条根路由 | ❌ **函数签名里没有注入口** |

第二条更隐蔽：`RESERVED_POST_ROUTES` 是模块级 `Map`，
`checkReservedPostRoutes(docs)` 一个参数都不接——**调用方想覆盖都覆盖不了**。

那 7 条也**不是凭印象列的**：按 `src/pages/` 实测得出

### 门禁的第一版判据写错了——两处，一处比误报危险得多

先写 `check-site-agnostic.mjs`，判据是「核心模块里不许出现 `about` 或 `/wiki/` 字面量」。
报 18 处，逐条核对后发现：

1. **误报 4 处**：`Doc['kind']` 的 `'post' | 'wiki'` 枚举与 `d.kind === 'wiki'`
   被当成站点专属——那是**知识层的产品概念**，不是本站目录。
   第二个站点要么有知识层、要么整体关掉，两种都由 `checkWikilinks`/`checkOrphans` 管。
2. **漏报 1 处**：`urlFor` 里的 `/wiki/`。

第 2 条才是要害：**写死与可覆盖的「兜底默认值」在字面上完全一样**。
加了参数之后 `/wiki/` 仍作为默认值留在核心里，字面量判据分不出它俩。
> **改用「字面量」还是改用「结构」，区别就在这里**：
> 字面量判据必须在注释里推理「这条大概能覆盖」——**推理不如直接查**。

判据改成查签名与调用链：`urlFor` 必须收前缀参数、`lint()` 必须真的用
`opts.reservedPostRoutes`（**签名里有不等于用上了**——那正是迭代 AK 在 JSON-LD 上踩的同一个坑）。

### 修门禁时又踩了「注释里的放行没实现」

我给门禁写了「`kind === 'wiki'` 放行」的注释，**代码里没写**。
第一版改完 18 → 14，于是「看起来修好了」。
> 门禁自己的注释里写着放行而代码没实现，同样是「约束写在注释里而没有检查」——
> **只是这次约束长在门禁自己身上**。注释里写了放行就得真的放行，
> 否则门禁会训练人忽略它的报告。

### ⚠️ 判据里多了一个反斜杠，于是真违规被静默放过

PREFIXES 那条我写成 `` `\`${prefix}\`` ``（多了个反斜杠），
匹配的是「反斜杠+反引号」，而源码里是纯反引号——
`graph.ts:185` 的 `` `/wiki/${slug}/` `` **被放过**，门禁全绿。

发现它的方式不是「看门禁输出」，是**对账**：
> 门禁说 14 处，可我逐条核对下来只有 13 处是纯 lint 常量。**数字对不上。**

> **漏报比误报危险得多**：误报会被人修，漏报会让人以为已经修好了。
> 而对账（「报出来的条数与我知道的条数是否一致」）是抓漏报最便宜的手段。

### 负向验证「全绿」，查了 5 轮——真凶是路径少了后缀

写了 4 个变异（删参数 / 删透传 / 删注入口 / 声明了不接线），跑出来**四次全绿**。

按惯例先怀疑门禁，于是依次排除了：cwd 正确 → 逐字比对锚点完全相同 →
`replace` 确实改变了字符串 → `writeFileSync` 正常 → `execFileSync` 确实会抛。

**全部排除之后**才打印绝对路径，看见：

```
patch 目标=D:\...\src\lib\wiki\graph          ← 没有 .ts
```

`patch()` 收到的键是 `'graph'`，写出了一个**没有扩展名的文件**，
而门禁读的 `graph.ts` **从头到尾没被改过**。

> **症状与「门禁坏了」一模一样**：注入成功、门禁全绿。
> 而前 5 轮全在验证「前提」（锚点对不对、cwd 对不对、写盘成功吗），

> **一次不报错、什么都没变、于是看起来像别的东西坏了。**
>
> **教训：查「量出来不对」时，第一反应应该是「尺子不对」；
> 查了 5 轮假设都没排除时，该怀疑的是「东西压根没被改过」，而不是继续换假设。**

变异脚本还在 `.verify/` 里——**那个目录被 `.gitignore` 忽略、也被 `npm run clean` 清掉**，
放那儿等于没写（CI 上根本跑不到）。挪到 `scripts/site-agnostic.mutations.mjs`。

## 2026-09-24 · 迭代 AF：`superseded` 查过了，**现在不做**——没有真实用例

```

1. `status` 加 `superseded`；
2. **必须能指到替代它的那一篇**（否则「被替代」无从核对）；
3. 那篇要出现在**旧路径**上——路线图 §6 写明「保留历史路径和替代关系，
   **不从历史中抹除**」。

「这篇已经并入 XXX」，而不是 404。

## 2026-09-24 · 迭代 AD：两个缺陷各自都成立，合起来才暴露——证据被静默丢掉

核对路线图阶段 3 的退出条件「**固定问题集中的每个答案都能定位到证据，
或明确返回未知**」，随机抽了三个金标问题看证据。第一个就出问题了：

```
问「中文正文的理想行宽是多少，为什么不用 ch？」
主命中 cjk-typography ——它有 5 条来源 + reviewed
而 context pack 里：sources: 0、review: null
```

### 两个缺陷叠在一起

**① 字段名不统一。**

| 模块 | 来源字段 | 复核字段 |
|---|---|---|
| `read-page.ts` | **`refs`** | **不返回** |
| `Doc`（graph.ts） | `sources` | `review` |
| `PackDoc`（context-pack.ts） | `sources` | `review` |

`wiki-ask` 把 `readContentPage()` 的返回**直接**传给 `buildContextPack()`，
于是 `doc.sources` 恒为 `undefined`，**被 `?? []` 变成了「没有来源」**。

> **为什么 TS 没报出来**：`PackDoc.sources` 是**可选**的，
> 而 `readContentPage` 的返回类型里根本没有这个键——
> **「一个字段不存在」与「一个字段是 undefined」在 TS 里是同一件事。**

**② `parseReview` 的正则恒返回空。**

```js
/^review:\s*$([\s\S]*?)(?=
\S|\s*$)/m
```

`(?=
\S|\s*$)` 里的 `\s*$` 在**多行模式**下能匹配**零个字符**，
`$` 又立刻成立——于是它在 `review:` 后面当场截断，**捕获组恒为空**。

### 关键：为什么两个缺陷藏了这么久

**①藏得住**，是因为 `check-questions.mjs` 只需要 `body`，从不读 sources；
`context-pack.ts` 是迭代 L 才有的，而**迭代 L 我抽出它时没核对字段名**。

**②藏得住**，是因为读 review 的只有 `wiki-ask`，而它的输出**没人抽查证据栏**。

> **两个缺陷各自都成立，合起来才暴露。**
> 这与迭代 H 那条「全过 ≠ 都量过」是同一族，但更具体：
> **一个模块用 A 命名、另一个用 B 命名时，没有任何东西会报错**——
> 说得通的命名恰恰是危险的地方。
>
> 修法不是把某一处改成另一处的名字（那样又会与 `Doc` 不一致），
> 而是**统一到 `Doc` 的叫法**：`read-page` 与 `ImpactPage` 都用 `sources`。

### 修完立刻端到端核实

```
wiki-ask  「行宽为什么用 em」  → cjk-typography | sources 5 | review reviewed
wiki-impact --source=css-values-4 → 直接引用者 2 页 × 2 条定位
check-impact → 金标全过 + 两条新检查
```

改 `ImpactPage.refs` 时**又漏了 `wiki-impact.mjs`**（它读 `p.refs`）——
第一次改完跑 `wiki-impact` 仍报 0，才看出来。**改完必须每个消费方都跑一遍。**

### 阶段 3 条件 ③ 现在有了实测

金标 23 条里，「有依据」的那些**答案都带得上来源版本与复核状态**；
「无依据」的那些**明确返回未知**（`supported: false` + 理由）。
这一条不再是「没验过」，而是**验过了**。

### 验证

## 2026-09-24 · 迭代 AA：检查自己的粒度不够，它就一直绿着

迭代 Z 补了 evidence 覆盖检查。本轮顺手复查那条 locator 检查
（迭代 Y 加的）——**结果它自己有个洞，而它绿着。**

### 洞在哪

`css-values-4` 的登记只写了 **§5.1.1 的 `ch`**，而页面引用了 4 次这个来源，
其中 **2 次指的是 `ic`**——`ic` 是 2026-09-24 推翻
「`em` 等于字号所以 34em ≈ 34 个汉字」的**核心依据**（规范专门定义它，
就是为了说明「无法确定全角 advance 时假设 1em」）。

而检查是绿的。原因：**它只比章节号**。

```
ch → §5.1.1
ic → §5.1.1     ← 同一个节，章节号对得上，检查放过
```

### 修粒度时又错了一次

把判据改成「章节 + 符号名」之后，**它还是绿的**。
我以为改好了，跑了一下发现正则抓到的是 `·` **前面**的词：

```
"§5.1.1 长度单位 · ch" -> 符号名提取为「长度单位」
"§5.1.1 长度单位 · ic" -> 符号名提取为「长度单位」
```

而「长度单位」在登记里当然存在 —— **检查一路绿灯，却从没在查符号名。**
第二次修正（取 `·` 之后的部分）之后，它立刻抓到了那两处。

> **这一条是本轮最值得记的**：
> 我「修好」一个检查之后**没有验证它是否真的会红**，
> 于是它继续绿着——**而我以为问题解决了。**
>
> 与迭代 W 那条同族（「刚加的门禁永远量到 0」），
> 但更隐蔽一层：那次是**量不到东西**，这次是**量错了东西**，
> 而两者都表现为「绿灯」。
>
> **每次改一个检查，都要问：把它弄坏，它会红吗？**
> 这次若没问，就会带着一个假绿的门禁交付。

### 补的登记

`css-values-4` 的 locator 现在覆盖 `ch` 与 `ic` 两处，

## 2026-09-24 · 迭代 Y：只登记了弱的那条依据

本轮回到内容层（前面几轮都在核对文档数字），随手查一件事：

> If the desired weight is greater than 500, weights greater than or equal to the
> desired weight are checked in ascending order followed by weights below…

§2.2.2 只说「用附近的」，**没给方向**；§5 给了（**大于 500 时先向上找**）。

> **结论不同的两条依据，只登记了弱的那条。**
> 而 `check-impact.mjs` 只查「revision 能不能解析」，
> **查不到「登记覆盖了页面引用的那一节吗」**——所以它一直绿着。

已把 §5（与 §2.8.1 伪合成的开关）并入同一个版本的 locator，并把两段原文都收进 `evidence`。

**顺带定了一件事**：一开始我把 §5 拆成独立 revision
（`WD-20260913-font-matching`），后来合回去了——
路线图 §5.2 说 `revisionId` 是**规范版本号**，**同一版本的两个章节不是两个版本**。
拆开会让「一个版本对应什么内容」变得不唯一。

### 补了门禁，并说明它为什么这样判

`check-impact.mjs` 现在检查**页面引用的章节号是否被该版本的登记覆盖**。

判据是**章节号**（`§5.1.1` 这种）而不是整段文字比：页面写简写、登记写完整描述，
逐字比会误报。而**登记里没有章节号时不报**——
那说明登记用的是自由文本，机械比对没有判据，**宁可漏报也不误报**。

负向验证：把登记退回迭代 D 之前的状态（只有 §2.2.2），立刻抓出两处：

```
✗ locator 未被登记覆盖：cjk-typography 引用 css-fonts-4@WD-20260913 的 §5
✗ locator 未被登记覆盖：cjk-web-typography 引用 css-fonts-4@WD-20260913 的 §5
```

> 这一类缺口的形状值得记住：**「有登记」不等于「登记到位」**。
> 与迭代 H 那条「全过 ≠ 都量过」同族——
> 那里是集合不完整，这里是**内容不完整**，而检查只看得见前者。

### 顺带核对了全局

九个来源**全部被页面引用，零未使用、零缺失**；19 条带 locator 的引用**全部被覆盖**。
（这一步是本轮唯一「查完发现没别的」的结论——**但它是量出来的，不是想出来的**。）

## 2026-09-24 · 迭代 S：测试名里的声称，与实现的实际行为矛盾

迭代 R 讲「断言通过但比对的是别的东西」。本轮扫同一类问题的另一个形状：
**测试名本身声称了一个与实现相反的性质。**

### 抓到的那一处

`accept.test.ts` 里有一条：

```js
it('宁可高估也不低估（向上取整）', () => {
  expect(estimateTokens('abcde')).toBe(2);
});
```

而 `estimateTokens` 上方的注释写着（**本轮迭代 D 刚改过**）：

> ⚠️ **原注释写的是「宁可偏保守（高估）」——实测是反的，它一直在低估。**
> 用 `o200k_base` 对三个页面复算，稳定低估 9%–14%。

**代码注释改了，测试名没改。** 断言本身是对的（`ceil(5/4) = 2`），
但它的名字声称了一件**实测为假**的事。

> 而且「向上取整」只对**西文那一半**成立（`ceil(other / 4)`），
> 它管不到中文——中文按「1 字 1 token」算，而真实词表把常见双字词合成一个
> token，**低估恰恰都发生在中文那一侧**。
>
> 所以那条测试名不只是过时，是**从一开始就只对一半输入成立**。

已改名为「西文部分向上取整」，并写清它**不声称整体是保守的**。

### 扫了同类声称，其余都准确

`宁可漏给（客户端仍拿到可用的 HTML），不可错给`、`八个里至少要有六个不同`、
`100 个 slug 里至少 90% 的图彼此不同` —— 逐条对照实现与实测基线，**都成立**。

> **这类缺陷不适合做成门禁**：语义矛盾无法机械判定。
> 能做的是**改动那份声称时顺手核对**——
> 而本轮的教训是**改了注释却没改测试名**，
> 也就是说**「改一处」和「改对」不是同一件事**，又一次。

### 顺带做了个盘点脚本（`list:overclaims`）

那类缺陷可以**半自动地找出来**：测试名与注释里出现绝对化措辞
（「永不」「总是」「一定」「宁可…也不」「不低于」）的地方，
就是一个**可被证伪的声称**。

`scripts/list-overclaims.mjs` 扫出 11 处，排除它自己的反例后剩 6 处，
**逐条核对，结论是全部准确**：

| 位置 | 声称 | 核对结果 |
|---|---|---|
| `accept.test.ts:181` | 「宁可高估也不」 | 准确——那是**它刚改掉的旧测试名**的引用 |
| `check-test-count.mjs:14` | 「那个数就**一定会**漂」 | 准确——有实测支撑（263 那次） |

## 2026-09-24 · 迭代 R：给「测试自己」加一层元检查

迭代 Q 的结论是「有检查 ≠ 检查守住了该守的」。
那在**单测**里的形状是什么？**断言通过，但它比对的是别的东西。**

### 这不是设想，本项目第一版就有一个真实的例子

`digest.test.ts` 里有这么一条（那时是绿的）：

```js
it('改**知识类型**（concept → synthesis 是实质变化）', () => {
  expect(contentDigest(doc({ kind: 'synthesis' }))).not.toBe(base);
});
```

写的是 `kind`，而 **`kind` 在知识页上恒为 `'wiki'`**——
所以这条断言测的是一个**永远不变的东西**，它必然通过，
而**真正的知识类型（`wikiKind`）改了摘要纹丝不动**。
**它是绿的，而且什么都没测。**

> 这个 bug 的坏法是**它看起来在测知识类型**，连注释都写着「知识类型」。
> 是「让构建打印它实际看到的字段」才发现的，看代码看不出来——
> 那次修法已经写在 `digest.ts` 的注释里了。

### 把这个形状做成元检查

问题在于：**每一条单测单独看都没法判断自己测对了没有。**
所以加的那组不看单条，而看**组合**：

```js
it('恒定值实现会让「该变的必须变」那组全部失败', () => {
  const changed = [改标题, 改摘要, 改正文, 改 wikiKind].map(contentDigest);
  expect(new Set(changed).size).toBe(changed.length);
});
```

一个恒返回同一个值的 `contentDigest` 能让「同一份内容反复算结果一样」**通过**，
但上面这条必然失败——**四个不同的改动必须给出四个不同的摘要**。

再加一条 golden 覆盖率检查：**逐个改字段，golden 值都必须变**。
若某个字段改了算不出变化，那条 golden 就**只覆盖了部分字段**，
而**覆盖不全的 golden 给了虚假的安全感**。

### 关键：元检查本身也必须被负向验证

加完之后把 `contentDigest` 换成**恒定桩**：

```
注入前：23 passed
注入后：13 failed | 10 passed
恢复后：23 passed
```

**13 条变红**——其中包括新加的三条元检查。
如果元检查自己也「绿而没测」，那这一轮就白做了。
**每加一条「检查检查」的检查，都要问：它自己被弄坏时会红吗？**

### 顺带修正一条容易读错的测试名

`改文档类型不改变摘要（它是恒定的，放进摘要毫无意义）`——
这条**容易被理解成「`kind` 字段进了摘要」**，而恰恰相反：
`digestInput` 里写的是 `kind:${doc.wikiKind ?? ''}`，
那个 `kind:` 是**知识类型**的标签名，不是文档类型。

已改写理由，并补上合起来才完整的那一半：
**文章移入知识层会改变摘要**（`wikiKind` 从空变成 `concept`），
所以搬目录这件事**不需要**把 `doc.kind` 写进摘要就被捕捉到。

### 顺带撞了一次自己批评过的顺序错误

同步测试条数时，我先跑 `vitest` 看到 441 就写进文档，
**而那次运行是在加完新测试之前**——真实值是 442。
条数对账门禁立刻抓出来（第四次），改完才对。

> 「先测再写」是常识，但**我是在同一串命令里把两步连着做的**：
> `npx vitest run && sed -i 's/438/441/'`——
> 看起来很顺，实际上第二步用的是**上一步的输出**，
> 而那一步跑的是旧代码。
>
> **正确顺序永远是：先让门禁算出真值，再把真值写进文档。**
> 反过来做（先猜一个数写进去，再让测试去凑）就是本项目反复记的
> 「手抄数字必然漂」。

### 验证

`npm run verify:all` 13 步全过；442 项单测、196 项契约全绿；
`digest.test.ts` 23 条（新增 4 条元检查与迁移场景）。

## 2026-09-24 · 迭代 O：把 bug 的「形状」写成门禁

迭代 N 抓到 `computeImpact` 在 `refs` 缺失时崩溃，根因是
**类型标必填而实际可为 undefined**，且所有调用方都填了空数组——
**默认值救了它**。本轮做两件事：查同类形状、修它，并把形状固化成门禁。

### 系统排查同类形状

`a?.related.includes(x)` 这个写法是同型的另一面：
**可选链只保护了左边为 null，没保护该字段本身为 undefined**，
抛的是 `undefined.includes`。全库扫了一遍——

```
grep -rnE "\?\.(related|sources|refs|review|declaredRelations)\." src/ scripts/
```

**只此一处**，在 `wiki-ask.mjs`。已修为 `a?.related?.includes(...)`。

顺带把 `content-manifest.ts` 里 `doc.sources.map`（靠外层
`doc.sources?.length` 短路保护）也改成 `?? []`——
**逻辑上本来就安全，但「靠外层条件保护的内层访问」在改代码时极易被挪掉**。

### 写成门禁之后，它先把自己判为违规

`verify:portability` 加了第二条：扫 `?.(可选字段).method(` 这个形状。
第一次跑就报 `check-portability.mjs:34`——
**因为它自己的文档里写着 `a?.related.includes(x)` 这个反例，而反例符合模式。**

> 这件事有两层意思：
> 一是**门禁确实在工作**（它把一个真实的同类形状照出来了，只是照的是自己）；
> 二是**写下反例的检查会被自己的反例绊倒**——
> 所以必须显式排除自身，并在注释里写明为什么。
>
> 顺带又一次印证迭代 J 那条教训：**增量 Python 补丁静默失败**，
> 本轮第三次（第三次是重写整个 `check-portability.mjs` 才修好）。
> **补丁失败的特征是「不报错、什么都没变」**——所以每次补丁后都要看结果。

### 诚实地说：manifest 那 4 条用例加固前也会过

`content-manifest.test.ts` 新增的 4 条「可选字段缺失不崩」用例，
在加固**之前**也是绿的——因为外层短路本来就保护着。
**它们量的是「加固后仍然对」，不是「加固抓到了什么」。**

与 `wiki-ask` 那处不同：那里是**真的会崩**（`undefined.includes`），
而 manifest 那处是**依赖外层条件才不崩**。
两者的区别值得记住：**一个现在崩，一个将来崩**——
而「将来崩」的那一类，正是门禁该管的。

1. `wiki-ask` **仍然零测试**。它现在能被裸 Node 加载了（因为用了 `read-page.ts`），
   也就是说它**可以**被单测覆盖，但本轮没做——它是一个交互式 CLI，
   测试形态需要单独设计。已登记。

## 2026-09-24 · 迭代 N：拿第二份内容集跑一遍，抓到一个只在异构场景出现的崩溃

路线图阶段 4 的退出条件：「**一个全新的真实内容集能在不复制内部代码
的情况下使用核心流程**」。本仓库至今只有一个站点，于是拿一份
**刻意与本站不同**的合成内容集跑了一遍——这是那条退出条件的第一次实测。

（诚实起见：合成语料**不是**真实站点，所以这是「第一次实测」而不是「证明」。
真实站点那一步仍然欠着，已登记在下面的未决里。）

### 先撞上一个约束，才写出门禁

第一版探针直接 `import { buildGraph } from '.../graph.ts'`，
**崩了**：`Cannot find module '.../wikilink.js'`。

> 这些 `scripts/*.mjs` 是**裸 Node** 跑的，而 `graph.ts` 内部用
> `.js` 后缀 import（TS 惯例，bundler 才解析得了）。
> 站内两个脚本能 import 源码，是因为它们 import 的模块**内部没有 `.js` 引用**。
>
> 实测六个「零耦合」核心模块：`retrieve` / `impact` / `slug` / `digest` 可加载，
> **`graph` 与 `lint` 不可加载**——而后者是知识层的地基。
> **「零耦合」不等于「能被直接复用」**，这两件事此前被当成一件。

已修：`graph.ts` 与 `lint.ts` 的 4 处 import 改用 `.ts` 后缀
（不是无后缀——裸 Node 不做 TS 的无后缀解析，那次试过，失败）。
并新增 `verify:portability` 门禁：六个核心模块**必须能被裸 Node import**。

> 判据是「真的 import 一遍」而不是读源码找 `.js`——
> 因为**判据是传递依赖**：本模块干净但它 import 的模块不干净，一样加载不了。
> 读单个文件会漏掉这一层。**唯一可靠的判据是让解析器自己说。**

### 探针第一次跑就抓到一个真 bug

```
TypeError: Cannot read properties of undefined (reading 'some')
```

`computeImpact` 在 `refs` 缺失时崩溃。根因：`ImpactPage.refs` 与 `related`
在类型上都是**必填**，而真实的 `Doc.sources?` / `Doc.declaredRelations?`
**都是可选的**。

> 站内一直没暴露，是因为两个调用方（`read-page.ts` 与 `check-impact.mjs`）
> **都老实填了空数组**。
> **默认值救了它——而那正是最危险的状态**：它掩盖了类型与现实脱节，
> 于是「类型说是必填」与「运行时是 undefined」长期并存而无人发现。
>
> 这与本轮反复出现的「0 有两种来源」同族：
> **一个看起来正常的值（空数组）掩盖了一个不正常的现实（字段可能不存在）。**

## 2026-09-24 · 迭代 M：一条规则写对了，却没人守——版本号门禁

迭代 K 给 manifest 加了 `provenance` 字段，**当时没有升 `version`**。
回头一看，同一份代码里就写着判据：

> 真正该升的是这几种：**字段增删或改名**、字段语义改变……

**规则是对的，我违反了它。** 而更糟的是，那段注释的**开头**写的是
「只在消费方需要改代码时才升」——**两句话对同一次改动给出相反答案**，
所以照哪句做都不算错。这种自相矛盾的判据等于没有判据。

### 统一成一条可执行的判据

> **产物里已有文档的 JSON 形状变了，就升。**

理由不是「下游要改代码」，而是**同一份 `version: 1` 在不同时间会对应两种形状**——
那正是版本号要防的事。「可选字段」也不等于不用升：
`provenance` 是可选的，但它对有来源的页面**真的会出现**。

已升到 v2，并给判据补上边界：**只有「该字段对所有文档恒为缺席」时才可以不升**
（`manifestId` 加显式 `id` 支持就是这一类：产物里的 ID 一个字节都没变）。

### 规则写对了还要有人守

`check-formats.mjs` 补了一条断言，而且**先撞上一个约束才发现它**：

> 我第一版是 `import { CONTENT_MANIFEST_VERSION } from '../src/lib/content-manifest.ts'`，
> 结果 `verify:formats` 直接崩：
> `Cannot find module '.../wiki/graph.js'`。
>
> **原因**：这些脚本是**裸 Node** 跑的，而 `content-manifest.ts` 内部用
> `.js` 后缀 import（TS 惯例，bundler 才解析得了）。
> 仓库里其它脚本能 import 源码，是因为它们 import 的模块内部**没有 `.js` 引用**。
> 全库有 31 个文件是那种写法——改后缀是大动作，**风险远大于收益，不做**。
>
> 所以改成**从源码文本里正则读出常量**，绕开解析问题。

### 单向检查不够

第一版只查「产物 version == 期望值」。**那样源码升了、期望值忘了改，
产物与期望值仍然相等，契约照样绿**——而产物已经和源码声明的对不上了。

改成**双向**：产物、源码常量、契约里的期望值三个数一起比。
负向验证两个方向都试过（只改源码 / 只改期望值），**都会红**。

> 「一个检查写了」和「一个检查有效」之间差的这一步，
> 就是**试着把它弄坏**。本轮第三次这么做，三次都抓到了东西
> （「全过≠都量过」「闸被另一道闸遮住」「单向检查不够」）。

> **这是本项目反复出现的同一个模式**：
> 判据写对了 → 有人违反 → 违反时无人报警 → 于是再写一条判据。
> **光有规则不够，规则要有执法。** 本轮至少给「版本号」这一条配了执法。

### 硬编码的版本号其实有四处，而第一处被抓到时我以为只有一处

`content-export.test.ts` 里写着 `version: 1`——**类型系统先抓到了它**
（`Type '1' is not assignable to type '2'`）。我把它改成引用常量，就以为完事了。

**跑契约又红了一条**：「清单版本为 1」。继续查，发现**同一个数字在四个地方**：
`verify-negotiation.mjs` 两处、`smoke-online.mjs` 两处（两个格式各一处），
加上测试那一处。**全都改成引用常量**，而不是把 `1` 改成 `2`。

> **第一次被抓到不等于只有一个。** 硬编码的常量天然会散落在多处，
> 而「我改了看到的那一处」与「我改了对的那一处」不是同一件事。
> 这与迭代 D 那条「token 表有三个副本」是同一个形状。

另有 5 处未使用导入（`wiki-ask` 4 处、`check-questions` 1 处，

`astro check` 现在是 **0 错误 0 警告 0 hint**。

## 2026-09-24 · 迭代 L：修「报无依据」的那个工具，顺带挖出两层检索缺陷

`wiki-ask` 的处境和迭代 G 之前的 `wiki-impact` 一模一样：**零测试**，
而且只扫 `src/content/wiki/`。实测确认：

```

**而答案明明白白写在 `markdown-for-agents.md` 里**（「七个里三个主动要」）。

> **报「无依据」比答错更坏。** 答错时人还会去核对；
> 报「无依据」时，调用方会以为「知识库里没有这件事」，
> 而实际上有一整页在讲它。**一个把「没看」说成「没有」的工具，
> 会让所有基于它的判断都错下去。**

与迭代 I 修掉的 `wiki:impact` 缺口**完全同构**，修法也一样：
语料扩到 wiki + posts，解析统一走 `read-page.ts`。

> **一个量着 A、跑着 B 的金标，绿灯是没有意义的。**
> 这比「金标漏了一条问题」更难发现，因为它连**条数**都显得正常。
> 已让 `check-questions` 与 `wiki-ask` 共用同一份 `read-page.ts` 与同一份语料。

### 语料一扩大，立刻炸出两层真缺陷

金标变 11 页后，「怎么做 A/B 测试？」翻绿了（期望「无依据」）。
去查它到底命中了什么——**这一查就挖出两个独立的缺陷**：

**① 单个 ASCII 字母有正常权重。**
`A/B` 被切成 `a`、`b`，而它们在任何含英文的文本里都必然出现，
于是「几乎必然命中」变成「贡献虚高覆盖」。
实测 `reproducible-builds` 靠 `['b','a']` 拿到 44% 覆盖被判「有依据」，
**而「测试」一词压根没进命中词**。
修法：`termWeight` 里单字母一律 0。
**判据是长度不是字符集**——`CI` / `MVP` 是真术语，砍掉会误伤。

**② 问句壳自己给自己凑覆盖。**
改完①，`llm-wiki` 仍以 `么做`、`怎么` 两个词拿到 65% 覆盖。

`isSubjectTerm` 一直在做这件事，只是原先只用于闸二、没用于覆盖度。

修完②，只命中问句壳的页面覆盖度变成 **0**（此前 65%），「测试」一词才真正起作用。

> **两个缺陷是同一条链上的两环**：先要把噪声词踢掉，
> 剩下那个词的高覆盖度才是真的。**只修一个的话，会看到「换了个人来凑覆盖」，
> 像是修好了其实没有。**

## 2026-09-24 · 迭代 K：来源与复核状态进机器出口——页面能看见，机器看不见

阶段 3 的退出条件里有一条：「**任何 stale/superseded 内容都不会在
无提示情况下成为首选证据**」。去查机器出口，发现一个实打实的缺口：

| 出口 | 来源 | 复核状态 |
|---|---|---|
| HTML 页面 | ✅ Provenance 组件 | ✅ 显示「已复核 / 待复核 / 已过期」 |
| `content-manifest.json` | ❌ **没有** | ❌ **没有** |
| `content.ndjson` | ❌ **没有** | ❌ **没有** |

**订阅者按 manifest 同步时，无从知道哪一篇已经过期。**
而这正是那条退出条件要防的事——机器侧会比人侧**更信任**一篇已经不可信的内容，
因为它连「不可信」这个信号都收不到。

### 缺口的形状：不是「没做」，是「做了一半」

`Provenance` 组件早就存在且渲染正常，来源登记也早就跑通。
**唯独机器出口没有接。** 这类缺口最难发现：三处里两处是对的，
只有一处不对，而没有任何检查会告诉你「三处应该一样」。

### 实现里有两个刻意的选择

**① 整个 `provenance` 键在两者皆无时缺席，不是空对象。**

空数组 / 空对象读起来像「查过了，没有」；
缺席是「没标」。**这两种含义混成一样，「没量过」就会看起来像「量过且为空」**——
这与迭代 H 那条「全过 ≠ 都量过」是同一个原则的另一个出口。

**② NDJSON 一行代码都不用改。**
`ContentExportRecord extends Omit<ContentManifestDocument, 'markdown'>`，
所以它**自动继承** provenance。这是共用类型的回报——
如果当初 NDJSON 另写了一套字段形状，这一处就得记得同步，
而「记得」是所有事情里最不可靠的一环。

### 单测过了 ≠ 产物里有

`buildContentManifest` 的单测一开始就是绿的（先写用例，确认失败，再实现）。
但那只量了**函数返回的对象**，而产物还要经过「怎么被序列化、怎么被写盘」。

所以在 `check-formats.mjs`（产物级）补了一条断言：**产物里必须真的有 provenance**。
负向验证把实现改成「永远不进产物」，断言立刻报：

> ✗ 内容清单里一篇 provenance 都没有——本站有登记来源的页面，
> 这说明 provenance 没有进入产物（**单测过不代表产物里有**）

> 这条断言的价值不在于它抓到了什么，而在于它**能在将来被删掉时立刻报警**。
> 一个只在出事那天才被想起的检查，不写也照样出事。

### 文档也要跟上

`docs/content-export.md` 原先没有提 `provenance`。
机器出口的字段若不文档化，订阅者就**不知道它存在**——
那等于把这个字段只给看得懂源码的人用。已补上格式与两条语义说明
（缺席 ≠ 空；`stale` 不该被当成新鲜证据）。

### 验证

`npm run verify:all` 14 步全过；412 项单测、196 项契约、107 文件可复现构建全绿。

## 2026-09-24 · 迭代 J：把「两条引用通道」变成可查的事实

迭代 E 的改名实验撞出一个具体问题：正文 `[[wikilink]]` 与 frontmatter `related`
是**两条并行的引用通道**，我只改了其中一条，于是构建被 `broken-wikilink` 拦下。
当时在未决里写的是「搜引用时容易只搜一处」——**本条把那句话变成检查。**

### 先量清楚：重复到底有没有害

动手之前先问「这是正确性问题还是维护成本」。实测结论：

- 链接图用 `Set` 收集出边，**同一目标声明两次不会产生第二条边**；
- 反向链接按 `fromSlug` 去重，**不会重复计数**。

**所以重复是无害的。** 这决定了它是 warn 而不是 error——
两处都写没有坏处，提醒只是让成本可见。**把无害的规则做成 error 是另一种噪声。**

### 手算的数是错的，代码算出来的才是对的

动手前我用脚本粗算了一遍 `related` 与 `[[...]]` 的重叠，报出 **3 页**。
做完规则再跑 lint，报出 **5 页**。

差在哪：我的粗算**按字面比对字符串**，
所以 `related: [cjk-typography]` 与正文 `[[中文排版]]`（同一页、不同写法）
被当成了两个不同的东西。

> **这是本项目又一次「手算不如让代码算」**（前例见迭代 D 那条
> 「手抄数字必然漂」——`66ch ≈ 33em` 的假设、token 表的三个副本、
> 测试条数四处，都是同一类）。
> 而这次更该记的是：**我以为自己在用工具，其实我在用一次性脚本。**

## 2026-09-24 · 迭代 E：稳定身份，以及一次「看起来更对」的改法被实测否掉

路线图阶段 1 的退出条件里有一条：**「每个公开文档只有一个规范 ID 和一个当前 URL」**。
去看实现，发现 `manifestId` 就是 `${kind}:${slug}`——**ID 完全是 URL 的函数**。

后果具体是什么：manifest 是**对外发布**的机器出口，下游按 `id` 同步。
改一次文件名或显式 slug，同一篇内容的 ID 就变了，
订阅者会把它当成一篇新文档，旧文档凭空消失且无从追溯。

而这条**此前没有任何测试覆盖**——`content-manifest.test.ts` 里一条 `manifestId` 用例都没有。
这就是它能长期错着的原因：**没人量的东西不会坏，只会不变。**

### 先试了「内容寻址」，被自己的用例否掉

第一版实现是「没有显式 `id` 时，用 `kind` + 规范化正文摘要的哈希」。
理由听上去很对：正文没变，改名就不影响 ID。

**然后新写的用例直接把它打红了**：

```
FAIL 不同文档不会撞 ID
AssertionError: expected 'post:a1845325f951c9f4' not to be 'post:a1845325f951c9f4'
```

两篇 fixture 的正文都是 `'正文'`，于是**得到同一个 ID**。
这不是 fixture 的问题——**正文相同的两篇不同文档在真实站点里完全可能**，
而 manifest 的 ID 是下游认文档的唯一凭据，**撞 ID 意味着两篇互相覆盖**。

**这比「改名会改 ID」严重得多**，所以这条设计被否掉，回到「显式 id 优先、缺省仍用 slug」。

> **一个更隐蔽的问题我当时没看出来**：内容寻址下**改一个字正文就换 ID**。
> 那等于每次修订都让全体下游重新同步——比改名频繁一个数量级。
> **「更稳定」的方案在这里反而制造了更大的不稳定。**

### 顺带修掉我自己写错的一条断言

新加的用例里我一度写了「不同 slug 也必须得到相同 ID」。
**那是错的**——那等于允许两篇不同内容共用一个身份，正是 manifest 要防的覆盖。
写完读一遍才发现：**它和同一个 describe 里「不同文档不会撞 ID」直接矛盾。**
断言自己内部打架，说明它测的不是一个想清楚的要求。

最终形态：显式 `id` 优先；缺省仍退回 `kind:slug`（**不制造新的破坏**），
并把「没写 id 的文档改名仍会改 ID」这个边界**写在代码注释里**，而不是假装解决了。
schema 两个集合都加了 `id` 字段（**不声明会被 Zod 静默剥离**，见 `content.config.ts` 里 draft 那段注释），
六个 wiki 条目全部写上了显式 id——**知识条目被改名/合并的频率比文章高**，
所以这个字段对 wiki 更值得写。

### 改名实验：ID 确实稳住了，但改名的**成本比想象中高**

不满足于单测绿，实际改了一次名来做证伪实验：把 `design-tokens` 的 slug 改成
`design-tokens-renamed`。结果 ID 仍是 `wiki:design-tokens`，URL 变成
`/wiki/design-tokens-renamed/`——**身份与 URL 成功分离，机制成立**。

但实验过程本身比预想的更有价值：**改名连续撞了三道门**。

1. **两处正文 `[[design-tokens]]` 断链**，构建中止。
2. 改完正文才发现**真正的断链在 frontmatter 的 `related`**——
   `related: [cjk-web-typography, design-tokens]` 里也有它。
   也就是说**一次改名要改三类地方**：正文链接、`related` 声明、以及别处提到它的散文。
3. 修完断链，又被 **`review-stale`** 拦下——改动了正文，
   复核摘要自然对不上。

> **这说明「稳定身份」只解决了 ID 漂移，没解决改名本身。**
> 而且第 2 条是我**改完第一轮才发现的**：第一轮我只搜了 `[[...]]`，
> 没想到 `related` 也是一条引用通道——**同一个概念有两套写法，
> 搜的时候只搜一套，就会漏**。这和 `log.md` 里记过的
> 「frontmatter 有两套解析」是同一族问题：**通道不止一条。**

**教训**：`related` 与 `[[wikilink]]` 在功能上重叠，重复带来的是
「搜引用时容易只搜一处」的成本。真要收敛，应该让 `related` 由
正文链接派生，而不是要求作者两处都维护。**本轮不做**——
那会改 `content.ts` 的取图逻辑，属于路线图阶段 1「统一解析」的范围，
不在这一小步里。

### 门禁又抓了一次漂移

加完 6 条测试后 379 → 385，`verify:testcount` 立刻报出四处 README/docs 写的 379。
已同步。**这是同一个门禁本轮第二次抓到我**（上一次是 token 节省率）。

### 未决

1. **posts 还没写显式 id。** 只给 wiki 六页写了。文章改名的频率低，
   但这意味着**文章的 ID 仍随 slug 变**。要不要全量补齐，
   取决于是否真有外部订阅者——**在有真实消费方之前不补**，
   补了也只是让 11 个 ID 变一次，没有收益。
2. **改 ID 规则会让全体 ID 变一次**，等于让下游全部重新同步。
   manifest 有 `version` 字段就是为此准备的，但**本轮没有升 version**
   ——因为最终实现保持了缺省行为不变，产物里的 ID 一个都没变。

### 验证

### ③ `em` 与汉字容量 —— 上一轮改了算式，没动那句更大的话

原文已抓到。**如果 `em` 就能保证汉字宽度等于字号，规范不必再定义 `ic`。**

原文还留着三句越界的话，全改了：

- `wiki/cjk-typography.md`：「粗估 `66ch` 是粗估，**`em` 不是估算`**」← 最直接的一句

## 2026-09-23 · 可证伪声明：把「页与仓库之间」的陈旧变成 CI 能查的东西

**起因是一次实测**：`llm-wiki.md` 的「已实现 / 计划实现」表里，
**三行写着「计划中，尚未实现」，而它们全都已经落地**
（`knowledge/sources/*.json`、`Doc.sources` / `Doc.review`、
`scripts/wiki-impact.mjs`）。写完那句话的时候它们就存在了。

没有任何检查会发现——lint 管的是断链、重复 slug、孤儿页，
那些都是**页与页之间**的问题。而这一条是**页与仓库之间**的问题。
**它读起来像事实，所以没人会去核实。**

### 做出来的东西

`verify:` 声明写在知识页 frontmatter 里，**每条查两件事**：

```yaml
verify:
  - claim: 来源登记与版本固定
    stated: 来源登记与版本固定 | **已实现**
    path: knowledge/sources/*.json
    expect: exists
```

- `stated`——页面正文里那句原话，必须**逐字**出现；
- `path` / `expect`——那句话对应的文件在不在。

**两个都查，缺一不可。** 只查文件的话，正文改了、声明没改时，
声明还在验一句没人说过的话——检查照样绿，而它绿得毫无意义。

放在 `astro.config.mjs` **加载期**，理由与 frontmatter 校验完全一样：
在 remark 管道里抛错，Astro 不会让构建失败（实测：错误打印 22 次、
页面退化、而 `Build exit code: 0`）。

### `globToRegExp` 被写坏了三次——这是本轮最值得记的一段

这个机制里唯一一处自己写的解析，三次的症状**都是「正则看着挺对、而且测试是绿的」**：

| 版本 | 写法 | 症状 |
|---|---|---|
| ① | `**` → `(?:[^/]+/)*/`，又叠加循环补斜杠 | 要求**至少一层**子目录，`src/config.ts` 匹配不上 |
| ② | 「上一段是 `**` 就不补斜杠」 | `src` 与 `**` 之间那个斜杠丢了，**全都匹配不上** |
| ③ | 分隔符补在 `**` 分支之后 | `src/**` 正常了，`src/**/*.ts` 又全不中 |

三次都是**我盯着 `.source` 数斜杠**，而 `new RegExp` 的 `.source`
会对 `/` 补反斜杠——数出来的是 `\/`，肉眼极容易多数或少数一个。
所以现在测试里的断言**一律用 `test()`**，不碰 `.source`，
并且拿**真实文件树**交叉验证（手写的期望值可以跟实现一起错）。

那个 glob 正好写在知识页的示例里——**金标全绿、功能是坏的**，
本仓库最防的那类 bug，这次踩在自己身上。

### 负向验证抓到一个真缺陷

第一轮注入「把表改回『计划中』但不改声明」时，**检查没红**。
原因：`evaluateClaims` 收到的是**整个文件**，而 `stated` 的字符串
**在 frontmatter 里它自己那一行就有**——**声明在验证自己的字符串**。
改成只喂正文之后，注入立刻变红。

另外两轮注入（改文件路径、反转 `expect`）都正常变红。

### 未决

1. **只有 1 个知识页有 `verify:` 声明。** 其余 5 页还没写——
   而写声明要先把页面里的可证伪说法找出来，那是一次内容审阅。
2. **它只查「文件在不在」，查不了「写对了吗」。** 一条声明能覆盖的范围
   恰好就是「有没有」这个层级，写清楚比写宽重要。
3. `globToRegExp` 的 `**` 只支持「零个或多个目录」这一种语义，

## 2026-09-23 · 迭代 B：统一解析与身份（三处）

`remark-wikilink.ts` 里有一个**手写的 YAML 子集解析器**（注释写着

**第一版修法是错的。** 改成越界就抛，清缓存后注入 `title: >`：

小节 ID 是渲染期 `github-slugger` 生成的（重复标题带 `-1` 后缀），

`check-formats.mjs` 的草稿探针本来就不弱（唯标记 + 遍历 dist + 清单 + 全量导出），

## 2026-09-22 · M0：中文排版的一组算式与归因错误

**动机**：同一组结论散在 6 个载体里，其中两处论证是错的，而现有的检查

### 来源与版本

| 来源 | 固定版本 | 用于 |
|---|---|---|
| [CSS Values and Units Level 4 §ch](https://www.w3.org/TR/2024/WD-css-values-4-20240312/#ch) | W3C Working Draft, 12 March 2024 | `ch` 的定义 |
| [CSS Fonts Module Level 4](https://www.w3.org/TR/2026/WD-css-fonts-4-20260913/#font-style-matching) | W3C Working Draft, 13 September 2026 | 字重匹配（§2.2.2）与伪合成开关 |
| [RFC 9110 §12.5.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-12.5.1) | RFC 9110（STD 97） | Accept 的优先级规则 |
| [Karpathy 的 llm-wiki gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) | gist，2026-04 | 模式定位 |

只改文章不改这里，就是"同一个事实有几个表面、只改一处等于没改"。

### 改了什么

**行宽（算错 + 结论错）**

原话：「一个汉字大约等于两个 `ch`。所以按 66ch 排中文，每行会排出约 130 个汉字
——远超出中文舒适的 30 到 40 字。」

- 按它自己的前提应当**除以 2 得 33**，而不是乘以 2 得 130；
- 33 本来就落在它自己说的 30–40 里，所以「远超」也不成立；
- 被这句话遮住的事实：**66ch ≈ 33em，与本题采用的 34em 宽度几乎相同**。
  这个改动换的是**单位的可预测性**（`em` 等于字号、与字体无关），不是行宽。

**字重（归因错）**

原话：「写 `font-weight: 600` 时浏览器找不到 600，就伪合成一个……正确做法：标题字重写 500。」

- 伪合成的开关是 `font-synthesis-weight`，**不是字重数值**；
  写一个字体没有的字重时，规范要求的是**去找最接近的真实字重**；
- 本站 `base.css` 关掉合成后标题用 600：拉丁拿到 Archivo 的真实 600，
  中文落到 700。**写 500 反而会让中文掉到 400**——比 600 更糟。
- 顺带：`base.css` 的注释里**早就把对的写下来了**，是文章没跟上。

**规范归因**

内容协商那篇原先写「这时按 RFC 的规定，服务端应当认为靠前的那个优先」。
RFC 9110 §12.5.1 规定的是按**具体程度**排优先级，对 q 值相同的只说是
*equally preferred*，**没有给顺序**。所以「并列时靠前优先」是本地策略，
已在文章与 `accept.ts` 注释里都改成这个说法。

**llm-wiki.md**

- posts 原被列为「不可变的输入」，但它们**会被修订**（这篇记录本身就是证据）；
- 「RAG 永不改变、永不连接」太绝对——GraphRAG 就会组织关系与预计算摘要；
- 「一份来源可能改动 10 到 15 个页面」**没有出处**，标注为未核实；
- 补了 gist 的**真实链接**（原先只有文字，`grep -c gist.github.com` 是 0）；
- 补一张「已实现 / 计划实现」表——此前通篇以"本项目怎么做"的口吻描述，
  读者分不清哪些是真的、哪些是打算做的。

### 未决问题

1. **Ahrefs 那 97% 的引用没有可点开的来源。** 试过几种 ahrefs.com/blog 路径都是 404。
   已在文章里标注「待核验，不要转引」。要么找到确切地址，要么撤掉该句。
2. **「1 汉字 ≈ 2ch」仍是粗估。** 严格值取决于字体，本轮没有对每个候选字体实测。
   文章已改成"粗估"措辞，但没有给出实测表。
