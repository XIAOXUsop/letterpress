## 2026-09-23 · 影响分析 `wiki:impact`

**动机**：来源登记做出来之后，下一个问题自然是「来源出了新版，哪些页面要动」。
在此之前**这个问题没有答案**——引用只是一串链接、不带版本，
所以「引了这个来源」与「引了这个来源的**这一版**」分不开。

### 它第一个抓到的真东西

```
① 直接引用者（1）      cjk-typography · WD-20240312 · §5.1.1
② 可能受影响者（1）    design-tokens（经 cjk-typography）
③ 仓库辅助载体（2）    docs/cjk-typography.md
                      src/content/posts/cjk-web-typography.md
```

**③ 里那篇文章**引用了同一个规范，但因为它不是知识层条目、
不在来源登记的范围里，**此前没有任何地方把它和这个来源关联起来**。
"不在发布集合里"恰好是它最容易漏的原因。

### 设计取舍

- **三组互不重叠**（已在①的不再进③）：重叠会让人以为"还有别的地方要改"，
  而那正是这个工具要消除的困惑。
- **不联网**：只回答"已登记的这一版被谁引用了"，不去看远端有没有新版——
  那是另一件事（要网络、要登录、也不可靠）。
- **不改文件**：只出清单。应用修改要校验生成时的 hash（下一步的事）。
- **无引用时照常输出三组并标注「（没有）」**，而不是报错或空转。

### 顺带做的重构

维护脚本要读 frontmatter，而那套解析此前只住在 `remark-wikilink.ts` 里。
**在第二个地方重写就是三份实现**——抽成 `src/lib/wiki/frontmatter.ts`，
没有运行时依赖，脚本与插件都能 import。过程中踩了两个坑：
`collectFiles` 忘了跟着搬（报 `is not defined`，够直白）；
以及 `astro.config.mjs` 从一个**只导入、不再导出**的模块里 import
`collectFrontmatterProblems`，报错是 `not a function`，看不出是 import 错了地方。

### 未决问题

1. **`wiki:impact` 没有自动化测试。** 它是脚本、要读文件系统，
   目前只手工验过三种情形（有引用/无引用/多版本）。
2. **`knowledge/questions.md`（评测问题集）还没建。** 路线图阶段 3 的第二半——
   而"可评测"正是这一整套东西与"看起来在工作"的分界。
3. 前面几条未决仍未动：只有 2 页标了来源、`stale` 状态无端到端用例、
   文章 `updated` 与知识页 `review` 是两套时间概念。

## 2026-09-23 · 迭代 C：来源登记与复核状态机（试点 2 页）

**动机**：路线图阶段 2。在此之前页面上的「依据」只是一串链接——没有版本、
没有定位。规范出新版时没人知道哪些页该复查；读者点过去看到的是**今天的**规范。

### 做了什么

- `knowledge/sources/` 登记 5 个**真实**来源，用带日期的固定 URL。
- wiki schema 加可选的 `sources` / `review`；`Doc` 加 `wikiKind`。
- 构建期三条校验：来源解析得到（`unknown-source`）、reviewed 必须有
  日期与摘要、**摘要对不上就是 stale 并中止构建**（`review-stale`）。
- `src/components/Provenance.astro`：默认收起，不显示摘要值，无来源不渲染。
- `scripts/wiki-review.mjs`：取当前摘要，**不自动写回**。

### 排查「两边摘要不一致」——四处口径差异，全是看不出来的那种

症状是两页都报 stale，看起来像机制坏了。实际是四个独立的口径问题：

1. **`body` 少一个 `trim`**：Astro 的 `entry.body` 去过首尾空白，
   文件里切出来多两个换行。2166 vs 2168 字符。
2. **`kind` 取错字段**：`Doc.kind` 是**文档类型**（恒为 wiki），
   frontmatter 的 `kind` 是**知识类型**。摘要要后者，而 `Doc` 里根本没有它。
   → 补了 `wikiKind`。第一版用的前者，于是知识类型怎么改摘要都不变。
3. **键名错了**：脚本传 `related`，`Doc` 的字段叫 `declaredRelations`。
   `?? []` 静静兜成空数组——摘要照样算得出，只是永远对不上。
4. 导出 `digestInput`，让下次**能 diff 字符串而不是猜哈希**。

**教训**：逐项猜是猜不出来的。最后是靠"让构建打印它实际看到的 body 与字段"
定位的——四个问题里有两个是读代码看不出来的。

### 顺带：新检查抓到两个真 bug

`--color-link` / `--color-link-hover` **只有使用、从未定义**（「复制 markdown」
按钮）。CSS 自定义属性找不到时**整条声明被静默丢弃**，而 `astro check` 0 错误、
196 项契约全过、构建成功。新增 `css-tokens.test.ts` 钉住这类问题。

### 未决问题

1. **只有 2 页标了来源。** 其余 4 个知识页没有来源也没有复核状态——
   按路线图那是刻意的（"先做小范围可选增强"），但**没有门禁要求它们补**。
2. **`stale` 状态没有端到端用例。** `review-stale` 是构建期**报错**，
   而 schema 里还有一个可以手写的 `status: stale` ——那条路径没人走。
3. **文章的 `updated` 与知识页的 `review` 是两套时间概念**，
   目前没有把它们放在一起看过。
4. 来源区块只进 HTML、不进 markdown 孪生。**这是有意的**（机器出口拿的是
   正文），但意味着"HTML 与 NDJSON 三端一致"这条**只对正文成立**。

### 验证

`npm run verify:all` 全绿：100 文件类型检查 0 错、**324 项单测**、196 项契约、
条数对账、搜索、站内链接与锚点、草稿扫描 77 个文本产物、可复现、子路径、格式。

## 2026-09-23 · 迭代 B：统一解析与身份（三处）

**动机**：路线图阶段 1 的四件事——「唯一的解析器」「内容图与导出扫描统一」
「校验锚点与冲突」「draft/private 泄漏测试」。这一轮做了前三件里的三处。

### ① frontmatter 有两套解析，且第二套会静默解析错

`remark-wikilink.ts` 里有一个**手写的 YAML 子集解析器**（注释写着
「简单键值，不需要完整解析」），只服务于 `[[链接]]` 的查找表。

与真实 YAML 逐例比对：**12 个边界用例，6 个分歧**（块标量 `|` `>`、
值写在下一行、行尾注释、双引号转义、单引号 `''`）。
现有内容一条都不触发（11 文件 × 6 字段 = 66 次比对，0 分歧）——
所以是**潜在风险**，而下一位作者写 `title: >` 就会静默踩中。

**第一版修法是错的。** 改成越界就抛，清缓存后注入 `title: >`：

    错误打印 22 次；页面退化（链接 4→3）；Build exit code: 0

**在 remark 管道里抛错，Astro 不会让构建失败**——那比"链接静默指错"更糟。
正解是挪到 `astro.config.mjs` 的**加载期**：什么都不渲染，抛出去就是构建失败。
同一个注入现在 exit 1、指出文件与字段、一个页面都没渲染。

### ② 同名标题按遍历顺序任选一个

`buildGraph` 与 `buildLookup` 都是 `if (!has(title)) set(title, slug)`。
调换输入顺序，同一个 `[[Shared]]` 分别指向 a 和 b，而**两次 lint 都是 0 错误**。

改成「同名就不注册」：用了歧义标题 → error 并列出全部候选；
存在但没被引用 → warn。两处查找表行为一致，不会再各算各的。
端到端验证：把一页标题改成另一页的，构建 exit 1、6 条 `ambiguous-wikilink`。

### ③ 锚点从没被校验过

`[[target#missing-heading]]` 在目标页存在时，`broken` 与 lint **都是空的**。
「详见第 3.2 节」可以指向不存在的小节——**静默跳错位置**。

新增 `scripts/check-anchors.mjs`，在**产物上**查而不是从源码再推一遍：
小节 ID 是渲染期 `github-slugger` 生成的（重复标题带 `-1` 后缀），
从源码推算等于再造第三套解析器。全站 32 页、134 个锚点全部可解析。

### ④ 草稿泄漏扫描有个无声的白名单

`check-formats.mjs` 的草稿探针本来就不弱（唯标记 + 遍历 dist + 清单 + 全量导出），
但它是**按扩展名白名单跳过**的：只扫 `html|md|txt|xml|json|ndjson`。

白名单当时的判断是对的，失败方式却是无声的——将来多一个出口
（换扩展名、加一种导出格式），泄漏检查会**静默地不覆盖它**，
而扫描照样打印「草稿没有进入任何文本出口」。

改成扫全部文件、按 UTF-8 试解码，解不出的跳过但**把跳过数报出来**：

    旧白名单：65 个    新写法：77 个文本 + 30 个二进制跳过

新增覆盖的 12 个正是最可能藏内容的：`pagefind/*.js`（UI / worker）、
`_astro/style.*.css`、`favicon.svg`、`_headers`。

边界写进注释：二进制搜不出明文标记，这是**方法的边界不是保证**；
索引那侧靠另一条性质兜住——索引只能收录实际生成的页面，而草稿页根本没生成。

### ⑤ 语义正文摘要

新增 `src/lib/wiki/digest.ts`。覆盖 kind / title / summary / body / declaredRelations，
**不覆盖** slug（搬家不是改内容）、draft、以及将来的 `review` 字段本身
（自引用会让"标记已复核"这个动作自己改变摘要）。

归一化三条：行尾统一 LF（否则 Windows 检出与 Linux 检出永远是两个值）、
Unicode 归一 NFC、关系排序去重。

18 条用例分两个方向：**该变的必须变**、**不该变的必须不变**。
金标值用**独立的 Python 实现**复算比对过——不是拿被测函数自证。

### 未决问题

1. **`slug` 字段没有同样的越界检查。** 现在 `collectFrontmatterProblems`
   扫的是 `title` 与 `slug` 两个字段，但**其它字段**（`summary`、`updated`…）
   仍由 Astro 用真 YAML 解析——这一层没有分歧风险，因为 remark 根本不读它们。
2. **歧义标题的 warn 没有出现在构建输出里。** lint 的 warn 会打印，
   但没有针对"存在歧义标题"的端到端验证。
3. **draft/private 泄漏测试**（阶段 1 第四件）本轮没做。现有 `verify:formats`
   覆盖了草稿隔离的一部分，但没有对**全部**公开载体逐个断言。

### 验证

`npm run verify:all` 全绿：94 文件类型检查 0 错、**300 项单测**、196 项契约、
条数对账、搜索、**锚点**、时钟、子路径、格式。
三个提交：`31d9941`、`e8ffc6f`（含一次作者名笔误的修正 → `591cf48`）、`8f21f28`。

## 2026-09-23 · 阶段 0 收口：估算 vs 实测、活链接、一条核不掉的引用

**动机**：路线图阶段 0 的退出条件里有三项上一轮没做完——
估算 token 的表述、W3C 固定版本、以及那六项事实问题中的 Ahrefs 一条。

### 来源与版本

| 来源 | 版本 | 用于 |
|---|---|---|
| `tiktoken`（`o200k_base`） | 本地安装，2026-09-23 | 真实 token 用量对照 |
| [Google Search Central, *AI features and your website*](https://developers.google.com/search/docs/appearance/ai-features) | 在线版，2026-09-23 取 | llms.txt 那条的替代依据 |

### 改了什么

**① 估算被当成了实测。** 站点自己的「token 节省率」用的是
`estimateTokens`——一个刻意可解释的启发式（CJK 1 字 1 token、其余 4 字符 1 token），
而 README 与文档写的是「Measured saving」「实测」「真实数字」。

2026-09-23 装 `tiktoken` 用 `o200k_base` 逐页复算：

| 页面 | HTML 估算 / 真实 | MD 估算 / 真实 | 节省 估算 / 真实 |
|---|---:|---:|---:|
| /markdown-for-agents/ | 6,214 / 6,902（−10.0%） | 2,390 / 2,413（−1.0%） | 61.5% / **65.0%** |
| /cjk-web-typography/ | 7,614 / 8,876（−14.2%） | 2,962 / 3,201（−7.5%） | 61.1% / **63.9%** |
| /wiki/content-negotiation/ | 3,681 / 3,963（−7.1%） | 1,106 / 1,103（+0.3%） | 70.0% / **72.2%** |

**② 那个函数的注释在说反话。** `estimateTokens` 的注释写着
「宁可偏保守（**高估**），也不要让 agent 以为塞得下」——实测它**一直在低估**
（HTML 侧稳定偏低 7–14%），也就是它声称要避免的那一侧。
成因是中文：真实词表会把常见双字词合成一个 token，而「1 字 1 token」把它们各算一个。

**③ W3C 链接是活链接。** `/TR/css-values-4/` 会随规范修订移动，半年后回看
不知道引的是哪一版。已换成带日期的固定 URL（W3C 自己推荐的引用方式）：
`/TR/2024/WD-css-values-4-20240312/`、`/TR/2026/WD-css-fonts-4-20260913/`，
三处逐个 HTTP 200 验过。共替换 14 处。

**④ 一条核不掉的引用，删掉。** 原文写「Ahrefs 2026 年 5 月实测 **137,210 个域名：
97% 的 llms.txt 从未被请求过**」。核实过程：
按几种常见路径试 `ahrefs.com/blog/*` **全部 404**；
Ahrefs 自己的 sitemap **没有收录博客**；两个搜索引擎都取不到可解析结果。
**查不到就不留着**——精确到个位数、读者却无从核对，只会因为"看起来很硬"被转引。
换成能点开的 Google 原文（且措辞更准：原文是「**不需要**」，不是「不支持」）。

### 未决问题

1. **`estimateTokens` 要不要改成真的保守？** 现在没改——没有证据表明有消费方
   依赖 `x-markdown-tokens` 做硬约束，而改它就会动到对外行为。先记录，
   等真实失败样本。**但没有实测支撑的"保守"说法已经删掉了。**
2. 真实词表对照依赖 `tiktoken`（Python），**没有进 CI**——它是本地测出来的，
   项目本身不引分词器依赖。所以这张表是快照，不是每次构建复算的值。
3. 上一轮列的「1 汉字 ≈ 2ch」「跨平台字重」仍未实测，不变。

### 验证

`npm run verify` 全绿（196 项契约）。**估算数字按本次真实结果同步了三处**
（`docs/content-negotiation.md`、`README.md` ×2、`accept.ts` 注释），
又是门禁抓出来的——每次改文章都会动到这组数。

## 2026-09-22 · M0：中文排版的一组算式与归因错误

**动机**：同一组结论散在 6 个载体里，其中两处论证是错的，而现有的检查
（lint / 196 项契约 / 272 项单测）**全都测不到**——它们检查结构，不检查事实。

### 来源与版本

| 来源 | 固定版本 | 用于 |
|---|---|---|
| [CSS Values and Units Level 4 §ch](https://www.w3.org/TR/2024/WD-css-values-4-20240312/#ch) | W3C Working Draft, 12 March 2024 | `ch` 的定义 |
| [CSS Fonts Module Level 4](https://www.w3.org/TR/2026/WD-css-fonts-4-20260913/#font-style-matching) | W3C Working Draft, 13 September 2026 | 字重匹配（§2.2.2）与伪合成开关 |
| [RFC 9110 §12.5.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-12.5.1) | RFC 9110（STD 97） | Accept 的优先级规则 |
| [Karpathy 的 llm-wiki gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) | gist，2026-04 | 模式定位 |

取固定的带日期 URL 而不是 `/TR/xxx/`：后者是"最新版"，会随规范修订移动，
半年后回看不知道当时引的是哪一版。

### 影响清单

**方案里列了 4 处载体，实际是 6 处。** 漏掉的两处是靠全库检索才发现的：

| # | 载体 | 原文 | 处置 |
|---|---|---|---|
| 1 | `src/content/posts/cjk-web-typography.md` | 行宽算错 + 字重归因错 | 改写 + 勘误 |
| 2 | `src/content/wiki/cjk-typography.md` | 同上 | 改写 + 勘误 |
| 3 | `docs/cjk-typography.md` | 行宽算错（字重已对） | 改写 + 勘误 |
| 4 | `src/styles/tokens.css` 注释 | 行宽算错 | 改写 |
| 5 | **`docs/compare.md`** | 行宽算错（**方案未列**） | 改写 |
| 6 | **`README.md`** | 行宽算错（**方案未列**） | 改写 |

另有第 7 处不是排版而是归因：`src/lib/negotiate/accept.ts` 的文档注释
**把平局规则列在「依据 RFC」之下**——内容协商那篇文章的错误就是从这儿来的。
只改文章不改这里，就是"同一个事实有几个表面、只改一处等于没改"。

### 改了什么

**行宽（算错 + 结论错）**

原话：「一个汉字大约等于两个 `ch`。所以按 66ch 排中文，每行会排出约 130 个汉字
——远超出中文舒适的 30 到 40 字。」

- 按它自己的前提应当**除以 2 得 33**，而不是乘以 2 得 130；
- 33 本来就落在它自己说的 30–40 里，所以「远超」也不成立；
- 被这句话遮住的事实：**66ch ≈ 33em，与本题采用的 34em 宽度几乎相同**。
  这个改动换的是**单位的可预测性**（`em` 等于字号、与字体无关），不是行宽。

**字重（归因错）**

原话：「写 `font-weight: 600` 时浏览器找不到 600，就伪合成一个……正确做法：标题字重写 500。」

- 伪合成的开关是 `font-synthesis-weight`，**不是字重数值**；
  写一个字体没有的字重时，规范要求的是**去找最接近的真实字重**；
- 本站 `base.css` 关掉合成后标题用 600：拉丁拿到 Archivo 的真实 600，
  中文落到 700。**写 500 反而会让中文掉到 400**——比 600 更糟。
- 顺带：`base.css` 的注释里**早就把对的写下来了**，是文章没跟上。

**规范归因**

内容协商那篇原先写「这时按 RFC 的规定，服务端应当认为靠前的那个优先」。
RFC 9110 §12.5.1 规定的是按**具体程度**排优先级，对 q 值相同的只说是
*equally preferred*，**没有给顺序**。所以「并列时靠前优先」是本地策略，
已在文章与 `accept.ts` 注释里都改成这个说法。
