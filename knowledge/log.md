## 2026-09-24 · 迭代 AJ：一个查不到来源的数字，比不写更糟

上一条定下的原则是「**有客观答案就去查**」。
本轮把它用在**从没查过的外部声称**上——于是立刻抓到一个。

### 「全球覆盖约 72%」：三处文档都写着，而它没有来源

`text-spacing-trim` 的浏览器覆盖率，三处都写「约 72%」
（README、`docs/cjk-typography.md`、wiki 页与文章共四处）。

**去查**：
- `caniuse.com/text-spacing-trim` → **406 拒绝抓取**，
  而 `caniuse-lite` 的数据包里**根本没有这个特性**（太新）；
- 改查 MDN 的 `browser-compat-data` → 拿到权威数据：
  **Chrome 123+ 支持，Safari 与 Firefox 均不支持**。

**全球覆盖率查不到**（caniuse 没有、webstatus 未查）。

> **处置：把那四个字删掉，换成可核实的事实。**
>
> 「约 72%」按浏览器份额**大致合理**（Chrome ~65% + Edge ~5%），
> 但**合理不等于有来源**。而它出现在一个满是实测数字的段落里，
> **读者会以为它是量出来的**。
>
> **一个查不到来源的覆盖率，比不写更糟**——它不提供信息，
> 只提供一种「这里已经核实过了」的错觉。

四处全部改掉，并各自写明「此前那个数字没有来源」。

### 然后我犯了一个流程错误：没看验证结果就提交

改完四处「72%」之后，我跑了一次 `verify:all`——**日志里明明白白写着
「196 项契约中 2 项失败」**——而我**紧接着就 `git add && git commit` 了**。

失败原因是 token 节省率漂了（55.8% → 55.1%）：
我给 `cjk-web-typography.md` 加了 MDN 那段说明，**文章变长了**，
而 README 与 `docs/content-negotiation.md` 里的百分比是上一次量的。

> **我这一整轮在反复记录「改完要查」，然后自己漏掉了最后一次查。**
> 更具体地说：**我看到验证输出里有「2 项失败」，却没有让它阻止我提交。**
>
> 门禁的正确用法不是「跑它」，而是「**看它的结论，并据此决定能不能提交**」。
> 跑了不看，等于没跑——**而那比不跑更坏**，因为它给了「已经验过了」的错觉。

修完（重新用 `o200k_base` 复算三页）才提交第二次。

### `review-stale` 第四次触发

改完三个内容页的正文，构建立刻报「中文排版已复核但正文改过」——
**这正是它该做的**。重新取摘要、复核、写入。
（机制本轮触发次数：迭代 D、E、J、AJ 各一次。）

### 一次关于「查不到」本身的记录

我原本想给 `check:refs` 也加一条「外部 URL 可达性」检查，
**然后意识到那会经常误报**（GitHub 限流、网络抖动、代理）——
**而一个经常误报的检查等于没有检查**。

所以明确**不做**：外部可达性既不稳定、也不在「离线可复现」的立身之本里。
**需要联网才能跑的检查，就不该是门禁。**

### 验证

`npm run verify:all` 17 步全过；446 项单测、196 项契约全绿；
知识库体检 0 错误。

## 2026-09-24 · 迭代 AI：回到内容本身——两处失效链接，以及「卖点漏了最独特的那条」

前面几轮都在给检查补检查。**本条停下这个循环，回到用户实际读的东西。**

### README 的卖点漏了本项目现在最独特的能力

三件卖点是内容协商、中文排版、知识层。但**「结论带出处」这条线完全没出现**
——而它恰恰是本项目现在最独特的东西：

- 9 个来源登记，**10 个被引用版本全部有逐字 evidence**；
- 6 个 wiki 页**全部 reviewed**，3 页声明了「原创实践记录」；
- `provenance` 进了 manifest 与 NDJSON（**订阅者能知道哪篇过期**）；
- 正文一改没重新复核，`review-stale` **让构建失败**（本轮触发过三次）。

查了 `docs/compare.md` 的竞品对照——**它没有这一栏**。
也就是说这不是「别人也有只是没写」，是真的没有。

已在中英两处卖点补上，附真实的 frontmatter 示例（逐字核过字段名）。

### 顺带发现：文档落后于实现

`docs/features.md` 与 `docs/content-manifest.md` 里 **关于 provenance 一个字都没有**——
而 `provenance` 是迭代 K 加的。**代码加了字段，文档没跟。**

> 这与迭代 T 那条「README 的数字漂了没人知道」同族，
> 但更基础：**字段有了、文档没写，于是「有这个能力」这件事只有知道历史的人才知道**。

两处已补，并把 `features.md` 里两处过期的 146 KB 改成实测的 93 KB。

### 然后抓到一个真 bug：**两处锚点链接点不到**

`docs/features.md` 与 `docs/design-notes.md` 都链到
`compare.md#关于站内-js-这一行`，而那个标题的真锚点是
**`关于站内-js这一行`**——**少一个连字符**。标题是 `## 关于「站内 JS」这一行`，
中文引号被删后 `JS」这一行` 的空格与引号组合让 slug 少一个连字符。

**这次我没有靠推理，而是抓了外部事实**：

```
curl https://github.com/XIAOXUsop/letterpress/blob/main/docs/compare.md
  → id="user-content-关于站内-js这一行"
```

> **这是本轮唯一一个「靠查证而非靠推理」抓到的 bug。**
> 前面那些（wasm、`du -sk`、`response.json`、三个平台配置）全是我自己写错的——
> **它们只能靠「写完就查」发现，因为没有外部事实可对。**
> 而这一类（有客观答案可查的）**应该直接去查**。

已新增 `npm run check:anchors`：用**与 GitHub 一致的 slug 规则**逐个核实锚点。
负向验证确认它能抓到本轮这个真实的 bug。

### 一个必要的坦白

我为写这个检查先写的 Python 版本**判据是错的**（它按「删标点」算 slug，
而 GitHub 还会把空格折叠）——**报了 2 处失效，而那 2 处其实是对的**
（链接本来就与真锚点一致，是我算错了）。

**第四次「用错误的尺子量」。** 这次不同的是我**去查了线上的真实 HTML**，
而不是接受自己的脚本输出——**这才是正确的顺序**。

### 顺带：又踩了第七次 Python 转义

写那个临时核对脚本时 `replace('\','/')` 又被写坏。**这条纪律我上一轮
刚写进 log，本轮立刻又犯。** 记忆里已经记下「只要目标文本里出现 `
`
就整体换成 Edit」——**记下来没用，得在动作之前想起它**。

### 验证

`npm run verify:all` **17 步**全过（新增 `check:anchors`）；
446 项单测、196 项契约全绿。

## 2026-09-24 · 迭代 AH：把「顺手写下没查」变成门禁，判据分四类

上一条我在 log.md 里写下：「**改正措施只有一条，而它每次都成立：写完就查。**」
一条纪律不该靠记性。**本条把它变成 `npm run check:refs`。**

### 判据分了四类，因为「像路径」不等于「是路径」

写这个脚本时我误报了 **37 处**（`src/config.ts` 明明在仓库根下面），
逐类修完才收敛。最终判据：

| 类别 | 例子 | 处理 | 我踩的坑 |
|---|---|---|---|
| **仓库内路径** | `src/lib/cover.ts` | 必须存在 | `join()` 在 Windows 把 `/` 转成 `\`，`endsWith` 恒 false → **37 处全误报** |
| **产物路径** | `pagefind.js` | 在 `dist/` 找；**没 dist 就不判** | 把产物当仓库文件 |
| **URL 路径** | `/content-manifest.json` | 跳过（站点路径非文件） | 把它当文件 |
| **运行时路径** | `entry_response.json` | **在 `pagefind.js` 正文里但磁盘上没有** → 归类跳过并打印 | 判成失效 |

另外两类不是路径、也不该判：

- **类型与字段名**：`Doc.sources` / `Doc.review` 被反引号包着像路径
  → 收紧为「扩展名必须在已知表里」（有 dist 时误报 13 处，无 dist 时 0 处，
  **同一个脚本两种结果**——判据不稳的信号）；
- **引述代码写法**：`docs/cli.md` 里「项目里的 import 写的是 `./accept.js`」
  是在解释 TS 的 ESM 约定，不是在让读者找 `accept.js`；
- **引述错误以说明勘误**：`docs/compare.md` 里「头一版写的是 `response.json`
  ——**那个文件不存在**」，**同一行就否认了它**
  → 不跳过的话，**每一处勘误都会变成一个永久红的门禁**，
  等于在惩罚「把错误记下来」这个行为。

> **最后一类是这一轮最要紧的一条**：
> 一个会惩罚「记录错误」的门禁，会让人下次不敢记录错误。
> **那比没有门禁更糟**——它破坏的是产生正确信息的能力。

### 两次 Python 替换静默失败（本轮第二次）

加「运行时路径」的打印代码时，Python 的 replace **匹配上了但没生效**
（文件里根本没那段）。我看输出「没有那行」才发现。

> **我在这件事上的纪律已经写进上一条 log 了，本轮还是犯。**
> 差别是这次我**当场发现**而不是按着不完整的实现往下走——
> 靠的是「改完就看输出」这一个动作。
>
> **真正的修法不是「记得检查」，是别用会静默失败的工具。**

### 门禁放在 `verify:all` 的最后一步

`verify:formats` 与 `verify:reproducible` 跑完都会**清掉 `dist`**
（避免污染后续构建），而本检查**要 dist 才判产物类路径**。
放在最后，并用 `verify:gates` 的清单钉住位置。

### 负向验证

把 `docs/deploy.md` 里的 `middleware.ts` 改成 `middleware-nope.ts` → 立刻红（退出码 1），
恢复后 0。

### 验证

`npm run verify:all` **16 步**全过（新增 `check:refs`，扫 24 份文档 86 处路径引用）；
446 项单测、196 项契约全绿。

## 2026-09-24 · 迭代 AG：改一篇面向新人的文章，又一次「顺手写下的细节没查」

阶段 0–3 的退出条件核对完，本轮回到**内容本身**。
`how-this-works.md` 是 clone 之后的第一篇（写给新用户），
只有 799 汉字，是五篇里最短的——先看它。

### 两处该更新的

**① 体检那段只列了 3 类规则**，而现在有 11 条，
并且**完全没提来源登记与复核状态**——那是本轮大量工作的产物，
新作者读不到。已补，并指向 `AGENTS.md`（「那份是写给 agent 看的，
改规则时两边要一起改」）。

**② 部署那段说「`functions/` 目录，选你用的那个即可」**——
读者照这句话去找 Netlify 与 Vercel 的实现会找不到，
因为它们在 `netlify/edge-functions/` 与 `middleware.ts`。已补成表格。

### 然后我又犯了那个错

补表格时我顺手写了三行「平台配置」：

```
| Cloudflare Pages | … | 仓库根的 `_headers` / `_redirects` |
| Netlify          | … | `netlify.toml`                      |
| Vercel           | … | `vercel.json`                      |
```

**三个里有三个是我编的**——`netlify.toml` 不存在，
`_headers` 在 `public/` 而不是仓库根，`_redirects` 根本不存在。

> 这是本轮**第四次**「顺手写下的细节没查」（前三次：
> 推了个不存在的 wasm、`du -sk` 与 `ceil` 混用、门禁提示里的 `du` 数字算错）。
> **越是「顺手就能写出来」的细节，越容易不查**——
> 而这些细节恰恰是新读者照着做的依据。
>
> ⚠️ 但要说准确：**四次里只有两次是「压根没查」**
> （wasm、这次的三个文件）。另两次（`du -sk`、门禁提示的 `du` 数字）
> 是**查了、但用错了量法**——那不是「没查」，是「查得不够」。
>
> **两类要分开**：没查的补查一次就行；
> 量法错的得先把量法**统一到一处**（这就是 `npm run measure` 存在的原因）。

修完的表（全部实测过）：

| 平台 | 边缘函数 | 平台配置 |
|---|---|---|
| Cloudflare Pages | `functions/[[path]].ts` | `public/_headers` |
| Netlify | `netlify/edge-functions/negotiate.ts` | 无额外配置 |
| Vercel | `middleware.ts` | `vercel.json` |

### 然后我做了一件更系统的事：扫全库文档里的文件名

既然「顺手写下没查」已经是第五次，就不该只查我刚改的那一处。
写了个脚本抽 README / AGENTS.md / docs / 内容页里反引号包着的
`*.ts|*.mjs|*.json|*.css|*.md` 等路径，逐个到仓库里找。

**报出 12 个「找不到」。逐个核实后：11 个是误报，1 个是真的。**

误报的来源有三类，都值得记住：
- **产物文件**：`pagefind.js` / `content-manifest.json` 等只在 `dist/` 里，
  源码树当然没有——**而 `dist` 当时又被探针清空了**，报「不存在」；
- **URL 路径**：`/content-manifest.json` 是站点路径，不是仓库路径；
- **我的匹配逻辑有 bug**：`[[path]]` 里的方括号被当成模式字符，
  于是明明存在的 `functions/[[path]].ts` 报「找不到」。

> **这个脚本本身就是「用错误的尺子量」的又一次**——
> 若我不逐个核实，就会去「修」11 个并不存在的问题。
> **与迭代 U 那次 `du -sk` 完全同型。**

### 真的那一个，是我自己上一轮加的

`docs/compare.md` 里我写「还有 `response.json`（索引分片数据）」——
**那个文件不存在**，真名是 `entry_response.json`。

也就是说：**上一轮我为了「修正措辞」而加的那句，本身又是一个没查的细节。**

> 这是本轮**第五次**「顺手写下的细节没查」，也是最讽刺的一次：
> 那次改动的**动机正是修正一处同类错误**，
> 而**修正 itself 引入了同一类错误**。
>
> **改正措施只有一条，而它每次都成立：写完就查。**

### 顺带发现三处更严重的不一致

`compare.md` 表格里「搜索页按需 **146 KB**（gzip）」与详细表的
「17 个文件 / 206 KB → gzip 146 KB」——**逐项实测后全对不上**：

| | 文档写的 | 实测 |
|---|---|---|
| 运行时 js | 17 个 / 206 KB / gzip 146 KB | **5 个 / 387 KB / gzip 93 KB** |
| 索引分片 | 12 个 / 54 KB | **1 个 / 34 KB** |

**文件数与体积都不对，而它写着「实测」。**

还发现 README（69 KB）与 compare.md（93 KB）**两个都是实测却不同**——
量的是不同东西（前者只算三个 UI 包，后者含 `pagefind.js` + worker），
**但两处都没说清自己量的是什么**，读者会以为其中一处错了。已在两处补口径。

### 门禁自己也被绊了一跤

改完 README 之后跑 `verify:all`，红的不是我改的地方，而是：

```
✗ README 写 CSS gzip 93 KB，实际 5.1 KB
```

CSS 体积那条门禁（迭代 T 写的）用 `/gzip ([\d.]+) KB/` 取值——
**全 README 第一个匹配**，不限于 CSS 那一行。我在新写的句子里
放了「gzip 93 KB」，它就匹到了那句。

> **门禁的报错把人引向了错误的改法**：按它的说法去改 CSS 那行，
> 会把一个正确的 5.1 KB 改成 93 KB。
>
> 这与迭代 AA 那条同源：**检查的判据比它声称的宽**，
> 而宽出来的部分会被别的内容命中。

已收紧成「只取 `| CSS |` 那一行」。负向验证：把 CSS 那行改成 9.9 仍会红（退出码 1），
恢复后绿。**收紧之后仍能抓真错**，这才是有效的收紧。

### 第六次同类失败，而且是同一处

修上面那个语法错误时，我用 Python 插入 `readme.split('\n')`——
`\n` **又一次**被写成真实换行，**与本轮早先那次完全相同**。
（写这段 log 时又踩了一次，三次。）

> **同一个错误在同一轮里犯三次**，而修法（换 Edit 工具）我明明已经用过了。
> **「知道正确答案」不等于「会用对工具」**——
> 连续用 Python 改含转义的代码，就应该**整体**换成 Edit，而不是一次次重试。
>
> 更该记的是：**它已经形成了模式**。
> 本轮 6 次里有 3 次是这一类，而每一次的触发条件都一样——
> **代码或文本里出现了 `\n`**。那就不该用会解释转义的工具去改它。

### 本轮我三次「用错误的尺子量」

这一整轮里，我至少三次**先下结论、再验证**，而结论是整齐地错的：

| # | 我怎么量的 | 我以为 | 实际 |
|---|---|---|---|
| ① | `grep -c "负向\|注入"` 扫脚本，想统计「哪些门禁验过」 | 4 个门禁没验过 | **那 4 个本轮都注入过** |
| ② | 数 `log.md` 里 ``` 的总数，判断代码块是否闭合 | 57 是奇数，**文件坏了** | 独占一行的围栏是 56，**闭合**；多出的 1 个是行内引用 |
| ③ | 写脚本扫文档里的文件名，判「仓库里找不到」 | 12 个文档错误 | **11 个是误报**（产物文件 / URL 路径 / 我的正则有 bug） |

**三次的共同点**：
- ① ② **尺子的口径与问题不匹配**（grep 文字 ≠ 行为；数字符 ≠ 数围栏）；
- ③ **尺子本身有 bug**（`[[path]]` 的方括号被当成模式）。

而**每一次我如果照着结论往下走，都会造成实际损害**：
① 会去「补做」已做过的验证；② 会去「修」一个没坏的文件；③ 会去改 11 处并不存在的问题。

> **「量出来不对」的第一反应应该是「尺子不对」，而不是「东西不对」。**
> 这个项目从头到尾记的都是「结论要核实」，
> 但**这一轮补上的是更前面的一步：先核实尺子。**

### 一条方法论

> **实测数字写下来之后，不只是会过期——它还可能从一开始就是错的，
> 而「实测」这个词会让人不去核对它。**
>
> 本轮 12 个「找不到」里那 1 个真的，就属于后者。

`npm run verify:all` 15 步全过；446 项单测、196 项契约全绿。

## 2026-09-24 · 迭代 AF：`superseded` 查过了，**现在不做**——没有真实用例

阶段 3 最后一条退出条件是「任何 stale/**superseded** 内容都不会在无提示
情况下成为首选证据」。查 `superseded`：**代码里完全不存在**
（`grep -rn superseded src/ scripts/` 零结果），
而路线图 §5.1 把它列为 status 之一、§6 的状态机画了它的转换。

### 为什么不建

先问「当前有没有被替代的页面」：

```
grep -rn "已废弃|已弃用|不再维护|被.*替代|已移到" src/content/   → 零结果
```

**一个都没有。** 那就是**没有真实用例**——
按路线图 §12 风险一（元数据比内容更难维护）与本项目一贯的
「**不为将来可能需要而建**」，现在加一个状态值只会多一处要维护的枚举。

**而且它比 `stale` 贵得多**：`stale` 是**机械可判定**的
（正文摘要变了 → 现算比对），而 `superseded` 需要**人工指认**
「这一篇被那一篇替代了」——那是一条**必须有人负责的声明**，
不是加个枚举值就有的。

### 记下来，而不是忘掉

写在 `knowledge/log.md` 里是为了将来有人问「为什么没有 superseded」时
**不必重新推一遍**：它不是被忘了，是**查过并判断为现在不需要**。

真出现「这一页被那一页取代了」的需求时，要做的是：
1. `status` 加 `superseded`；
2. **必须能指到替代它的那一篇**（否则「被替代」无从核对）；
3. 那篇要出现在**旧路径**上——路线图 §6 写明「保留历史路径和替代关系，
   **不从历史中抹除**」。

前两条是机制，第三条是**承诺**：访客点着旧链接进来，要看得见
「这篇已经并入 XXX」，而不是 404。

### 顺带：`stale` 那一半已经在了

阶段 3 那条条件的另一半（**stale 不成为首选证据**）已经落地：
- `review-stale` 门禁会在正文改动后让构建失败（迭代 D 实测过三次触发）；
- `provenance.review.status` 进了 manifest 与 NDJSON（迭代 K）；
- `check:answers` 会在答案**没有来源也没有复核状态**时报红（迭代 AE）。

所以**那条退出条件的一半是真达成的**，另一半（superseded）**不适用**——
不是没做，是**没有适用的对象**。

## 2026-09-24 · 迭代 AD：两个缺陷各自都成立，合起来才暴露——证据被静默丢掉

核对路线图阶段 3 的退出条件「**固定问题集中的每个答案都能定位到证据，
或明确返回未知**」，随机抽了三个金标问题看证据。第一个就出问题了：

```
问「中文正文的理想行宽是多少，为什么不用 ch？」
主命中 cjk-typography ——它有 5 条来源 + reviewed
而 context pack 里：sources: 0、review: null
```

### 两个缺陷叠在一起

**① 字段名不统一。**

| 模块 | 来源字段 | 复核字段 |
|---|---|---|
| `read-page.ts` | **`refs`** | **不返回** |
| `Doc`（graph.ts） | `sources` | `review` |
| `PackDoc`（context-pack.ts） | `sources` | `review` |

`wiki-ask` 把 `readContentPage()` 的返回**直接**传给 `buildContextPack()`，
于是 `doc.sources` 恒为 `undefined`，**被 `?? []` 变成了「没有来源」**。

> **为什么 TS 没报出来**：`PackDoc.sources` 是**可选**的，
> 而 `readContentPage` 的返回类型里根本没有这个键——
> **「一个字段不存在」与「一个字段是 undefined」在 TS 里是同一件事。**

**② `parseReview` 的正则恒返回空。**

```js
/^review:\s*$([\s\S]*?)(?=
\S|\s*$)/m
```

`(?=
\S|\s*$)` 里的 `\s*$` 在**多行模式**下能匹配**零个字符**，
`$` 又立刻成立——于是它在 `review:` 后面当场截断，**捕获组恒为空**。

### 关键：为什么两个缺陷藏了这么久

**①藏得住**，是因为 `check-questions.mjs` 只需要 `body`，从不读 sources；
`context-pack.ts` 是迭代 L 才有的，而**迭代 L 我抽出它时没核对字段名**。

**②藏得住**，是因为读 review 的只有 `wiki-ask`，而它的输出**没人抽查证据栏**。

> **两个缺陷各自都成立，合起来才暴露。**
> 这与迭代 H 那条「全过 ≠ 都量过」是同一族，但更具体：
> **一个模块用 A 命名、另一个用 B 命名时，没有任何东西会报错**——
> 说得通的命名恰恰是危险的地方。
>
> 修法不是把某一处改成另一处的名字（那样又会与 `Doc` 不一致），
> 而是**统一到 `Doc` 的叫法**：`read-page` 与 `ImpactPage` 都用 `sources`。

### 修完立刻端到端核实

```
wiki-ask  「行宽为什么用 em」  → cjk-typography | sources 5 | review reviewed
wiki-impact --source=css-values-4 → 直接引用者 2 页 × 2 条定位
check-impact → 金标全过 + 两条新检查
```

改 `ImpactPage.refs` 时**又漏了 `wiki-impact.mjs`**（它读 `p.refs`）——
第一次改完跑 `wiki-impact` 仍报 0，才看出来。**改完必须每个消费方都跑一遍。**

### 阶段 3 条件 ③ 现在有了实测

金标 23 条里，「有依据」的那些**答案都带得上来源版本与复核状态**；
「无依据」的那些**明确返回未知**（`supported: false` + 理由）。
这一条不再是「没验过」，而是**验过了**。

### 验证

`npm run verify:all` 14 步全过；446 项单测、196 项契约全绿。

## 2026-09-24 · 迭代 AA：检查自己的粒度不够，它就一直绿着

>

因为本站的文章确实会被修订（**本项目自己的 `log.md` 就是证据**）。
照抄「不可变」会是一条假陈述。

> **引用原文，也要标出自己的不同。**
> 否则「有出处」就变成了「我说了原文没说的话」。

RFC 7763 那条也写明了边界：**它只登记媒体类型**，
内容协商的判定规则（q 值、具体程度优先、并列怎么办）**全部来自 RFC 9110**。
两者别混。

### 补了门禁，判据是「被引用」而不是「已登记」

`check-impact.mjs` 现在检查：**被页面引用的版本必须有逐字 evidence**。

⚠️ **一个没人引用的来源没有 evidence 是可接受的**（备查而已），
**而一个支撑着正文数字的来源没有 evidence 是不可接受的**——
所以判据必须落在「被引用」上，否则会误报一批正当的备查条目。

负向验证：删掉 RFC 7763 的 evidence，立刻红，恢复后 0。

### 顺带一个「本轮唯一没抓到别的」

十个被引用的版本现在**全部有 evidence、locator 全被覆盖、零未使用来源**。
三条检查都绿。这是本轮第三次「查完发现没别的」——
而每一次都是**量出来的**，不是想出来的。

### 验证

`npm run verify:all` 13 步全过；442 项单测、196 项契约全绿；

## 2026-09-24 · 迭代 Y：只登记了弱的那条依据

本轮回到内容层（前面几轮都在核对文档数字），随手查一件事：
**页面引用的来源版本，与 `knowledge/sources/` 登记的定位对不对得上。**

### 找到的缺口

`css-fonts-4` 当时**只登记了 §2.2.2**：

> When a weight is specified for which no face exists, a face with a **nearby**
> weight is used.

而文章与 wiki 页**同时引用了 §5 的字重匹配算法**——
**§5 才是「请求 600 会不会落 700」这个问题的答案**：

> If the desired weight is greater than 500, weights greater than or equal to the
> desired weight are checked in ascending order followed by weights below…

§2.2.2 只说「用附近的」，**没给方向**；§5 给了（**大于 500 时先向上找**）。

> **结论不同的两条依据，只登记了弱的那条。**
> 而 `check-impact.mjs` 只查「revision 能不能解析」，
> **查不到「登记覆盖了页面引用的那一节吗」**——所以它一直绿着。

**顺带定了一件事**：一开始我把 §5 拆成独立 revision
（`WD-20260913-font-matching`），后来合回去了——
路线图 §5.2 说 `revisionId` 是**规范版本号**，**同一版本的两个章节不是两个版本**。
拆开会让「一个版本对应什么内容」变得不唯一。

`check-impact.mjs` 现在检查**页面引用的章节号是否被该版本的登记覆盖**。

判据是**章节号**（`§5.1.1` 这种）而不是整段文字比：页面写简写、登记写完整描述，
逐字比会误报。而**登记里没有章节号时不报**——
那说明登记用的是自由文本，机械比对没有判据，**宁可漏报也不误报**。

✗ locator 未被登记覆盖：cjk-web-typography 引用 css-fonts-4@WD-20260913 的 §5
```

> 与迭代 H 那条「全过 ≠ 都量过」同族——
> 那里是集合不完整，这里是**内容不完整**，而检查只看得见前者。

九个来源**全部被页面引用，零未使用、零缺失**；19 条带 locator 的引用**全部被覆盖**。

## 2026-09-24 · 迭代 S：测试名里的声称，与实现的实际行为矛盾

而 `estimateTokens` 上方的注释写着（**本轮迭代 D 刚改过**）：

> ⚠️ **原注释写的是「宁可偏保守（高估）」——实测是反的，它一直在低估。**
> 用 `o200k_base` 对三个页面复算，稳定低估 9%–14%。

**代码注释改了，测试名没改。** 断言本身是对的（`ceil(5/4) = 2`），
但它的名字声称了一件**实测为假**的事。

> 而且「向上取整」只对**西文那一半**成立（`ceil(other / 4)`），
> 它管不到中文——中文按「1 字 1 token」算，而真实词表把常见双字词合成一个
> token，**低估恰恰都发生在中文那一侧**。
>
> 所以那条测试名不只是过时，是**从一开始就只对一半输入成立**。

已改名为「西文部分向上取整」，并写清它**不声称整体是保守的**。

### 扫了同类声称，其余都准确

`宁可漏给（客户端仍拿到可用的 HTML），不可错给`、`八个里至少要有六个不同`、
`100 个 slug 里至少 90% 的图彼此不同` —— 逐条对照实现与实测基线，**都成立**。

> **这类缺陷不适合做成门禁**：语义矛盾无法机械判定。
> 能做的是**改动那份声称时顺手核对**——
> 而本轮的教训是**改了注释却没改测试名**，
> 也就是说**「改一处」和「改对」不是同一件事**，又一次。

### 顺带做了个盘点脚本（`list:overclaims`）

那类缺陷可以**半自动地找出来**：测试名与注释里出现绝对化措辞
（「永不」「总是」「一定」「宁可…也不」「不低于」）的地方，
就是一个**可被证伪的声称**。

`scripts/list-overclaims.mjs` 扫出 11 处，排除它自己的反例后剩 6 处，
**逐条核对，结论是全部准确**：

| 位置 | 声称 | 核对结果 |
|---|---|---|
| `accept.test.ts:181` | 「宁可高估也不」 | 准确——那是**它刚改掉的旧测试名**的引用 |
| `check-test-count.mjs:14` | 「那个数就**一定会**漂」 | 准确——有实测支撑（263 那次） |
| `check-search.mjs:124` | 「保证**全站一致**」 | 准确——它确实检查一致性 |
| `check-anchors.mjs:8` | lint「**从不**」看 `#` 后面 | 准确——2026-09-22 实测过 |
| `check-search.mjs:329` | 「**从不**请求的那部分」 | 准确——那是描述分类逻辑 |

> **它的退出码恒为 0，这是刻意的。**
> 「宁可漏给」「至少 90%」是经核对的实测基线——把它们判成错误就是误报，
> 而**一个会误报的检查比没有检查更糟**：它训练人忽略输出。
>
> 所以它的产物是**一份清单而不是一个判定**：
> 把「待核对」从「不知道」变成「6 条，逐条核过，都对」——
> **这本身就是它全部的价值。**
>
> 它也**不进 `verify:all`**（那是要判定的地方），只作为 `npm run list:overclaims`。

`npm run verify:all` 13 步全过；442 项单测、196 项契约全绿。

## 2026-09-24 · 迭代 R：给「测试自己」加一层元检查

迭代 Q 的结论是「有检查 ≠ 检查守住了该守的」。
那在**单测**里的形状是什么？**断言通过，但它比对的是别的东西。**

### 这不是设想，本项目第一版就有一个真实的例子

`digest.test.ts` 里有这么一条（那时是绿的）：

```js
it('改**知识类型**（concept → synthesis 是实质变化）', () => {
  expect(contentDigest(doc({ kind: 'synthesis' }))).not.toBe(base);
});
```

写的是 `kind`，而 **`kind` 在知识页上恒为 `'wiki'`**——
所以这条断言测的是一个**永远不变的东西**，它必然通过，
而**真正的知识类型（`wikiKind`）改了摘要纹丝不动**。
**它是绿的，而且什么都没测。**

> 这个 bug 的坏法是**它看起来在测知识类型**，连注释都写着「知识类型」。
> 是「让构建打印它实际看到的字段」才发现的，看代码看不出来——
> 那次修法已经写在 `digest.ts` 的注释里了。

### 把这个形状做成元检查

问题在于：**每一条单测单独看都没法判断自己测对了没有。**
所以加的那组不看单条，而看**组合**：

```js
it('恒定值实现会让「该变的必须变」那组全部失败', () => {
  const changed = [改标题, 改摘要, 改正文, 改 wikiKind].map(contentDigest);
  expect(new Set(changed).size).toBe(changed.length);
});
```

一个恒返回同一个值的 `contentDigest` 能让「同一份内容反复算结果一样」**通过**，
但上面这条必然失败——**四个不同的改动必须给出四个不同的摘要**。

再加一条 golden 覆盖率检查：**逐个改字段，golden 值都必须变**。
若某个字段改了算不出变化，那条 golden 就**只覆盖了部分字段**，
而**覆盖不全的 golden 给了虚假的安全感**。

### 关键：元检查本身也必须被负向验证

加完之后把 `contentDigest` 换成**恒定桩**：

```
注入前：23 passed
注入后：13 failed | 10 passed
恢复后：23 passed
```

**13 条变红**——其中包括新加的三条元检查。
如果元检查自己也「绿而没测」，那这一轮就白做了。
**每加一条「检查检查」的检查，都要问：它自己被弄坏时会红吗？**

### 顺带修正一条容易读错的测试名

`改文档类型不改变摘要（它是恒定的，放进摘要毫无意义）`——
这条**容易被理解成「`kind` 字段进了摘要」**，而恰恰相反：
`digestInput` 里写的是 `kind:${doc.wikiKind ?? ''}`，
那个 `kind:` 是**知识类型**的标签名，不是文档类型。

已改写理由，并补上合起来才完整的那一半：
**文章移入知识层会改变摘要**（`wikiKind` 从空变成 `concept`），
所以搬目录这件事**不需要**把 `doc.kind` 写进摘要就被捕捉到。

### 顺带撞了一次自己批评过的顺序错误

同步测试条数时，我先跑 `vitest` 看到 441 就写进文档，
**而那次运行是在加完新测试之前**——真实值是 442。
条数对账门禁立刻抓出来（第四次），改完才对。

> 「先测再写」是常识，但**我是在同一串命令里把两步连着做的**：
> `npx vitest run && sed -i 's/438/441/'`——
> 看起来很顺，实际上第二步用的是**上一步的输出**，
> 而那一步跑的是旧代码。
>
> **正确顺序永远是：先让门禁算出真值，再把真值写进文档。**
> 反过来做（先猜一个数写进去，再让测试去凑）就是本项目反复记的
> 「手抄数字必然漂」。

### 验证

`npm run verify:all` 13 步全过；442 项单测、196 项契约全绿；
`digest.test.ts` 23 条（新增 4 条元检查与迁移场景）。

## 2026-09-24 · 迭代 Q：给四个「没人量过的门禁」做负向验证，抓到一个真缺口

本轮已经四次栽在「尺子坏了」（ANSI 锚点、patch 静默、探针自身、
`astro check` 不查 `.mjs` 运行时语法）。于是去问一个更根本的问题：
**`verify:all` 里那 13 步，哪些从来没被验证过「坏了会不会红」？**

扫了一遍脚本里的负向验证说明，`testcount` / `search` / `anchors` / `base`
**四个都没有**。注意这**不代表它们坏**，只代表**没人量过**——
而「没量过」与「没问题」在这个项目里已经被反复证明不是一回事。

### 四个门禁逐个注入

| 门禁 | 注入 | 结果 |
|---|---|---|
| `testcount` | 把 README 里的 438 改成 999 | ✅ 红 |
| `anchors` | 造一个指向不存在锚点的链接 | ✅ 红 |
| `base` | 注入一处绕过 `path()` 的硬编码绝对路径 | ✅ 红（32 个页面） |

✓ 索引语言与页面语言一致：xx-yy
✓ 内容清单里的 11 个条目全部进了索引
```

**它只查「全站一致」，不查「这个 lang 是不是配置里声明的那个」。**
而 README 明确写着「`lang` 别改错，浏览器的中文标点规则依赖它」——
**门禁管得了「丢」，管不了「错」**。

后果正是 `check-search.mjs` 自己在文件头警告的那件事：
Pagefind 按 `lang` 选分词器，`xx-YY` 选不出中文分词器，
**搜「中文排版」会退化**——页面还在、构建还绿、测试全过，

已补：比对 `src/config.ts` 里声明的 `site.lang`。
读文本而不是 import，因为那是 `.ts` 且内部有 `.js` 后缀 import，
裸 Node 加载不了（那个约束这轮已经栽过三次，见 `check-portability.mjs`）。

负向验证：注入 `xx-YY` 立刻红（退出码 1），恢复后 0。

> **这一条是本轮最值得记的**：门禁**通过了**，而且通过了三次，
> 而它守的东西是错的。**「有检查」与「检查守住了该守的」是两件事**，
> 区别只有一个——**试着把它弄坏**。

### 附带：三个门禁的注入方式本身也说明了各自测什么

- `base` 对「markdown 链接改成绝对路径」**不红**——因为 markdown 链接
  会经 `path()` 正确处理，**那不是缺陷**。换成组件里的硬编码 `href` 才红。
  也就是说这个门禁量的确实是「绕过 `path()` 的硬编码」，不是「所有绝对路径」。
- 第一次测 `search` 时忘了重建 `dist`，Pagefind 索引缺失导致**恢复后仍红**——
  **尺子坏了的时候结论会整齐地错一遍**（迭代 L 已记过一次，本轮又遇上）。

`graph.ts` / `lint.ts` / `lint.ts` 此前都标着「本模块是纯函数」，

> 可选字段的健壮性（可选链形状）、版本号一致性（双向比对）。
> **每一条都是先违规、再补执法**——不是先想到要检查什么。

问「中文排版的行宽为什么用 em」
主命中 = cjk-web-typography 的「参考」小节，覆盖 100%
第二   = cjk-typography 的「正文开头」，覆盖 80%（答案在这一节）
```

> 这个是「**找到了对的东西但排在后面**」。影响可控（两段都在 pack 里），

> **登记为第三条已知局限，不修。**

## 2026-09-24 · 迭代 O：把 bug 的「形状」写成门禁

迭代 N 抓到 `computeImpact` 在 `refs` 缺失时崩溃，根因是
**类型标必填而实际可为 undefined**，且所有调用方都填了空数组——
**默认值救了它**。本轮做两件事：查同类形状、修它，并把形状固化成门禁。

### 系统排查同类形状

`a?.related.includes(x)` 这个写法是同型的另一面：
**可选链只保护了左边为 null，没保护该字段本身为 undefined**，
抛的是 `undefined.includes`。全库扫了一遍——

```
grep -rnE "\?\.(related|sources|refs|review|declaredRelations)\." src/ scripts/
```

**只此一处**，在 `wiki-ask.mjs`。已修为 `a?.related?.includes(...)`。

顺带把 `content-manifest.ts` 里 `doc.sources.map`（靠外层
`doc.sources?.length` 短路保护）也改成 `?? []`——
**逻辑上本来就安全，但「靠外层条件保护的内层访问」在改代码时极易被挪掉**。

### 写成门禁之后，它先把自己判为违规

`verify:portability` 加了第二条：扫 `?.(可选字段).method(` 这个形状。
第一次跑就报 `check-portability.mjs:34`——
**因为它自己的文档里写着 `a?.related.includes(x)` 这个反例，而反例符合模式。**

> 这件事有两层意思：
> 一是**门禁确实在工作**（它把一个真实的同类形状照出来了，只是照的是自己）；
> 二是**写下反例的检查会被自己的反例绊倒**——
> 所以必须显式排除自身，并在注释里写明为什么。
>
> 顺带又一次印证迭代 J 那条教训：**增量 Python 补丁静默失败**，
> 本轮第三次（第三次是重写整个 `check-portability.mjs` 才修好）。
> **补丁失败的特征是「不报错、什么都没变」**——所以每次补丁后都要看结果。

### 诚实地说：manifest 那 4 条用例加固前也会过

`content-manifest.test.ts` 新增的 4 条「可选字段缺失不崩」用例，
在加固**之前**也是绿的——因为外层短路本来就保护着。
**它们量的是「加固后仍然对」，不是「加固抓到了什么」。**

与 `wiki-ask` 那处不同：那里是**真的会崩**（`undefined.includes`），
而 manifest 那处是**依赖外层条件才不崩**。
两者的区别值得记住：**一个现在崩，一个将来崩**——
而「将来崩」的那一类，正是门禁该管的。

1. `wiki-ask` **仍然零测试**。它现在能被裸 Node 加载了（因为用了 `read-page.ts`），
   也就是说它**可以**被单测覆盖，但本轮没做——它是一个交互式 CLI，
   测试形态需要单独设计。已登记。

路线图阶段 4 的退出条件：「**一个全新的真实内容集能在不复制内部代码
的情况下使用核心流程**」。本仓库至今只有一个站点，于是拿一份

### 先撞上一个约束，才写出门禁

第一版探针直接 `import { buildGraph } from '.../graph.ts'`，
**崩了**：`Cannot find module '.../wikilink.js'`。

> 这些 `scripts/*.mjs` 是**裸 Node** 跑的，而 `graph.ts` 内部用
> `.js` 后缀 import（TS 惯例，bundler 才解析得了）。
> 站内两个脚本能 import 源码，是因为它们 import 的模块**内部没有 `.js` 引用**。
>
> 实测六个「零耦合」核心模块：`retrieve` / `impact` / `slug` / `digest` 可加载，
> **`graph` 与 `lint` 不可加载**——而后者是知识层的地基。
> **「零耦合」不等于「能被直接复用」**，这两件事此前被当成一件。

已修：`graph.ts` 与 `lint.ts` 的 4 处 import 改用 `.ts` 后缀
（不是无后缀——裸 Node 不做 TS 的无后缀解析，那次试过，失败）。
并新增 `verify:portability` 门禁：六个核心模块**必须能被裸 Node import**。

> 判据是「真的 import 一遍」而不是读源码找 `.js`——
> 因为**判据是传递依赖**：本模块干净但它 import 的模块不干净，一样加载不了。
> 读单个文件会漏掉这一层。**唯一可靠的判据是让解析器自己说。**

### 探针第一次跑就抓到一个真 bug

```
TypeError: Cannot read properties of undefined (reading 'some')
```

`computeImpact` 在 `refs` 缺失时崩溃。根因：`ImpactPage.refs` 与 `related`
在类型上都是**必填**，而真实的 `Doc.sources?` / `Doc.declaredRelations?`

> 站内一直没暴露，是因为两个调用方（`read-page.ts` 与 `check-impact.mjs`）
> **都老实填了空数组**。
> **默认值救了它——而那正是最危险的状态**：它掩盖了类型与现实脱节，
> 于是「类型说是必填」与「运行时是 undefined」长期并存而无人发现。
>
> 这与本轮反复出现的「0 有两种来源」同族：
> **一个看起来正常的值（空数组）掩盖了一个不正常的现实（字段可能不存在）。**

修法不是「让调用方记得填」，是**类型接受现实**：字段改可选、实现兜底、3 条用例。

### 探针自己也写错了三次

> 探针本身是需要验证的东西——**它跑绿了不说明被测对象对，只说明探针没写错**。
> 而写错探针的代价与写错检查一样：结论会整齐地错一遍。

## 2026-09-24 · 迭代 M：一条规则写对了，却没人守——版本号门禁

迭代 K 给 manifest 加了 `provenance` 字段，**当时没有升 `version`**。
回头一看，同一份代码里就写着判据：

> 真正该升的是这几种：**字段增删或改名**、字段语义改变……

**规则是对的，我违反了它。** 而更糟的是，那段注释的**开头**写的是
「只在消费方需要改代码时才升」——**两句话对同一次改动给出相反答案**，
所以照哪句做都不算错。这种自相矛盾的判据等于没有判据。

### 统一成一条可执行的判据

> **产物里已有文档的 JSON 形状变了，就升。**

理由不是「下游要改代码」，而是**同一份 `version: 1` 在不同时间会对应两种形状**——
那正是版本号要防的事。「可选字段」也不等于不用升：
`provenance` 是可选的，但它对有来源的页面**真的会出现**。

已升到 v2，并给判据补上边界：**只有「该字段对所有文档恒为缺席」时才可以不升**
（`manifestId` 加显式 `id` 支持就是这一类：产物里的 ID 一个字节都没变）。

### 规则写对了还要有人守

`check-formats.mjs` 补了一条断言，而且**先撞上一个约束才发现它**：

> 我第一版是 `import { CONTENT_MANIFEST_VERSION } from '../src/lib/content-manifest.ts'`，
> 结果 `verify:formats` 直接崩：
> `Cannot find module '.../wiki/graph.js'`。
>
> **原因**：这些脚本是**裸 Node** 跑的，而 `content-manifest.ts` 内部用
> `.js` 后缀 import（TS 惯例，bundler 才解析得了）。
> 仓库里其它脚本能 import 源码，是因为它们 import 的模块内部**没有 `.js` 引用**。
> 全库有 31 个文件是那种写法——改后缀是大动作，**风险远大于收益，不做**。
>
> 所以改成**从源码文本里正则读出常量**，绕开解析问题。

### 单向检查不够

第一版只查「产物 version == 期望值」。**那样源码升了、期望值忘了改，
产物与期望值仍然相等，契约照样绿**——而产物已经和源码声明的对不上了。

改成**双向**：产物、源码常量、契约里的期望值三个数一起比。
负向验证两个方向都试过（只改源码 / 只改期望值），**都会红**。

> 「一个检查写了」和「一个检查有效」之间差的这一步，
> 就是**试着把它弄坏**。本轮第三次这么做，三次都抓到了东西
> （「全过≠都量过」「闸被另一道闸遮住」「单向检查不够」）。

> **这是本项目反复出现的同一个模式**：
> 判据写对了 → 有人违反 → 违反时无人报警 → 于是再写一条判据。
> **光有规则不够，规则要有执法。** 本轮至少给「版本号」这一条配了执法。

### 硬编码的版本号其实有四处，而第一处被抓到时我以为只有一处

`content-export.test.ts` 里写着 `version: 1`——**类型系统先抓到了它**
（`Type '1' is not assignable to type '2'`）。我把它改成引用常量，就以为完事了。

**跑契约又红了一条**：「清单版本为 1」。继续查，发现**同一个数字在四个地方**：
`verify-negotiation.mjs` 两处、`smoke-online.mjs` 两处（两个格式各一处），
加上测试那一处。**全都改成引用常量**，而不是把 `1` 改成 `2`。

> **第一次被抓到不等于只有一个。** 硬编码的常量天然会散落在多处，
> 而「我改了看到的那一处」与「我改了对的那一处」不是同一件事。
> 这与迭代 D 那条「token 表有三个副本」是同一个形状。

另有 5 处未使用导入（`wiki-ask` 4 处、`check-questions` 1 处，
都是本轮删代码的残留；`remark-wikilink` 那处是更早遗留的）。

`astro check` 现在是 **0 错误 0 警告 0 hint**。

### 顺带核了 lint 的规则遮蔽问题

上一轮发现「一道闸被另一道闸遮住」，就去查 lint 会不会有同样的问题。

结论是 lint 这边没有这个问题——**但这结论是靠实测拿到的，不是靠读代码猜的。**

## 2026-09-24 · 迭代 L：修「报无依据」的那个工具，顺带挖出两层检索缺陷

`wiki-ask` 的处境和迭代 G 之前的 `wiki-impact` 一模一样：**零测试**，
而且只扫 `src/content/wiki/`。实测确认：

```
问「七个 agent 里哪几个主动要 markdown」
→ supported: false，理由是「实词『主动』在整个知识层里一次都没出现过」
```

**而答案明明白白写在 `markdown-for-agents.md` 里**（「七个里三个主动要」）。

> **报「无依据」比答错更坏。** 答错时人还会去核对；
> 报「无依据」时，调用方会以为「知识库里没有这件事」，
> 而实际上有一整页在讲它。**一个把「没看」说成「没有」的工具，
> 会让所有基于它的判断都错下去。**

与迭代 I 修掉的 `wiki:impact` 缺口**完全同构**，修法也一样：
语料扩到 wiki + posts，解析统一走 `read-page.ts`。
（顺带发现这是**第四份** frontmatter 解析拷贝——`wiki-ask` 里也有一份。）

### 更该记的：金标与被测对象脱节了

修好 `wiki-ask` 之后跑金标，**19 条全过**——但输出里写着「语料 6 页」。
也就是说：**金标量的语料与用户实际问到的语料不是同一份。**

> **一个量着 A、跑着 B 的金标，绿灯是没有意义的。**
> 这比「金标漏了一条问题」更难发现，因为它连**条数**都显得正常。
> 已让 `check-questions` 与 `wiki-ask` 共用同一份 `read-page.ts` 与同一份语料。

### 语料一扩大，立刻炸出两层真缺陷

金标变 11 页后，「怎么做 A/B 测试？」翻绿了（期望「无依据」）。
去查它到底命中了什么——**这一查就挖出两个独立的缺陷**：

**① 单个 ASCII 字母有正常权重。**
`A/B` 被切成 `a`、`b`，而它们在任何含英文的文本里都必然出现，
于是「几乎必然命中」变成「贡献虚高覆盖」。
实测 `reproducible-builds` 靠 `['b','a']` 拿到 44% 覆盖被判「有依据」，
**而「测试」一词压根没进命中词**。
修法：`termWeight` 里单字母一律 0。
**判据是长度不是字符集**——`CI` / `MVP` 是真术语，砍掉会误伤。

**② 问句壳自己给自己凑覆盖。**
改完①，`llm-wiki` 仍以 `么做`、`怎么` 两个词拿到 65% 覆盖。
`junctionsOf` 拦不住：它的判据是「该词在语料里没出现过」，
而 `怎么` **出现过 7 次**。要判的不是「接缝」，是「**整组都是虚词字**」——
`isSubjectTerm` 一直在做这件事，只是原先只用于闸二、没用于覆盖度。

修完②，只命中问句壳的页面覆盖度变成 **0**（此前 65%），「测试」一词才真正起作用。

> **两个缺陷是同一条链上的两环**：先要把噪声词踢掉，
> 剩下那个词的高覆盖度才是真的。**只修一个的话，会看到「换了个人来凑覆盖」，
> 像是修好了其实没有。**

### 金标自己也会过期——这轮撞了三次

1. 「A/B 测试」那条的**前提**（`a`/`b` 是缺席 token）已不成立。
2. 「已知局限」第 4 条写着「闸一没有任何金标量到，实测把 `MIN_COVERAGE` 改成 0
   **20 条一条都不变红**」——**语料一扩，这条就不真了**：
   实测改成 0 会红 2 处。已划掉并注明。
   **然后我发现自己的「修好」也是错的**，见下面那一节。
3. 「覆盖度按文档合并」那条引着「逐段 0.24 / 按页 0.37」——
   问句壳被剔除后逐段已达 0.534，**那条金标当初量到的东西，现在量不到了**。

> 第 2 条尤其值得记：**「20 条一条都不变红」是一个会被语料变化推翻的实测结论**，
> 却写在「已知局限」里，看起来像客观事实。
> 它其实是**关于当时那批语料的观察**。
> **决策文档里的实测数字也是断言**——而且是最容易被当成事实的那一种。

## 2026-09-24 · 迭代 K：来源与复核状态进机器出口——页面能看见，机器看不见

阶段 3 的退出条件里有一条：「**任何 stale/superseded 内容都不会在
无提示情况下成为首选证据**」。去查机器出口，发现一个实打实的缺口：

| 出口 | 来源 | 复核状态 |
|---|---|---|
| HTML 页面 | ✅ Provenance 组件 | ✅ 显示「已复核 / 待复核 / 已过期」 |
| `content-manifest.json` | ❌ **没有** | ❌ **没有** |
| `content.ndjson` | ❌ **没有** | ❌ **没有** |

**订阅者按 manifest 同步时，无从知道哪一篇已经过期。**
而这正是那条退出条件要防的事——机器侧会比人侧**更信任**一篇已经不可信的内容，
因为它连「不可信」这个信号都收不到。

### 缺口的形状：不是「没做」，是「做了一半」

`Provenance` 组件早就存在且渲染正常，来源登记也早就跑通。
**唯独机器出口没有接。** 这类缺口最难发现：三处里两处是对的，
只有一处不对，而没有任何检查会告诉你「三处应该一样」。

### 实现里有两个刻意的选择

**① 整个 `provenance` 键在两者皆无时缺席，不是空对象。**

空数组 / 空对象读起来像「查过了，没有」；
缺席是「没标」。**这两种含义混成一样，「没量过」就会看起来像「量过且为空」**——
这与迭代 H 那条「全过 ≠ 都量过」是同一个原则的另一个出口。

**② NDJSON 一行代码都不用改。**
`ContentExportRecord extends Omit<ContentManifestDocument, 'markdown'>`，
所以它**自动继承** provenance。这是共用类型的回报——
如果当初 NDJSON 另写了一套字段形状，这一处就得记得同步，
而「记得」是所有事情里最不可靠的一环。

### 单测过了 ≠ 产物里有

`buildContentManifest` 的单测一开始就是绿的（先写用例，确认失败，再实现）。
但那只量了**函数返回的对象**，而产物还要经过「怎么被序列化、怎么被写盘」。

所以在 `check-formats.mjs`（产物级）补了一条断言：**产物里必须真的有 provenance**。
负向验证把实现改成「永远不进产物」，断言立刻报：

> ✗ 内容清单里一篇 provenance 都没有——本站有登记来源的页面，
> 这说明 provenance 没有进入产物（**单测过不代表产物里有**）

> 这条断言的价值不在于它抓到了什么，而在于它**能在将来被删掉时立刻报警**。
> 一个只在出事那天才被想起的检查，不写也照样出事。

### 文档也要跟上

`docs/content-export.md` 原先没有提 `provenance`。
机器出口的字段若不文档化，订阅者就**不知道它存在**——
那等于把这个字段只给看得懂源码的人用。已补上格式与两条语义说明
（缺席 ≠ 空；`stale` 不该被当成新鲜证据）。

### 验证

## 2026-09-24 · 迭代 J：把「两条引用通道」变成可查的事实

## 2026-09-24 · 迭代 E：稳定身份，以及一次「看起来更对」的改法被实测否掉

路线图阶段 1 的退出条件里有一条：**「每个公开文档只有一个规范 ID 和一个当前 URL」**。
去看实现，发现 `manifestId` 就是 `${kind}:${slug}`——**ID 完全是 URL 的函数**。

后果具体是什么：manifest 是**对外发布**的机器出口，下游按 `id` 同步。
改一次文件名或显式 slug，同一篇内容的 ID 就变了，
订阅者会把它当成一篇新文档，旧文档凭空消失且无从追溯。

而这条**此前没有任何测试覆盖**——`content-manifest.test.ts` 里一条 `manifestId` 用例都没有。
这就是它能长期错着的原因：**没人量的东西不会坏，只会不变。**

### 先试了「内容寻址」，被自己的用例否掉

第一版实现是「没有显式 `id` 时，用 `kind` + 规范化正文摘要的哈希」。
理由听上去很对：正文没变，改名就不影响 ID。

**然后新写的用例直接把它打红了**：

```
FAIL 不同文档不会撞 ID
AssertionError: expected 'post:a1845325f951c9f4' not to be 'post:a1845325f951c9f4'
```

两篇 fixture 的正文都是 `'正文'`，于是**得到同一个 ID**。
这不是 fixture 的问题——**正文相同的两篇不同文档在真实站点里完全可能**，
而 manifest 的 ID 是下游认文档的唯一凭据，**撞 ID 意味着两篇互相覆盖**。

**这比「改名会改 ID」严重得多**，所以这条设计被否掉，回到「显式 id 优先、缺省仍用 slug」。

> **一个更隐蔽的问题我当时没看出来**：内容寻址下**改一个字正文就换 ID**。
> 那等于每次修订都让全体下游重新同步——比改名频繁一个数量级。
> **「更稳定」的方案在这里反而制造了更大的不稳定。**

### 顺带修掉我自己写错的一条断言

新加的用例里我一度写了「不同 slug 也必须得到相同 ID」。
**那是错的**——那等于允许两篇不同内容共用一个身份，正是 manifest 要防的覆盖。
写完读一遍才发现：**它和同一个 describe 里「不同文档不会撞 ID」直接矛盾。**
断言自己内部打架，说明它测的不是一个想清楚的要求。

最终形态：显式 `id` 优先；缺省仍退回 `kind:slug`（**不制造新的破坏**），
并把「没写 id 的文档改名仍会改 ID」这个边界**写在代码注释里**，而不是假装解决了。
schema 两个集合都加了 `id` 字段（**不声明会被 Zod 静默剥离**，见 `content.config.ts` 里 draft 那段注释），
六个 wiki 条目全部写上了显式 id——**知识条目被改名/合并的频率比文章高**，
所以这个字段对 wiki 更值得写。

### 改名实验：ID 确实稳住了，但改名的**成本比想象中高**

不满足于单测绿，实际改了一次名来做证伪实验：把 `design-tokens` 的 slug 改成
`design-tokens-renamed`。结果 ID 仍是 `wiki:design-tokens`，URL 变成
`/wiki/design-tokens-renamed/`——**身份与 URL 成功分离，机制成立**。

但实验过程本身比预想的更有价值：**改名连续撞了三道门**。

1. **两处正文 `[[design-tokens]]` 断链**，构建中止。
2. 改完正文才发现**真正的断链在 frontmatter 的 `related`**——
   `related: [cjk-web-typography, design-tokens]` 里也有它。
   也就是说**一次改名要改三类地方**：正文链接、`related` 声明、以及别处提到它的散文。
3. 修完断链，又被 **`review-stale`** 拦下——改动了正文，
   复核摘要自然对不上。

> **这说明「稳定身份」只解决了 ID 漂移，没解决改名本身。**

## 2026-09-23 · 可证伪声明：把「页与仓库之间」的陈旧变成 CI 能查的东西

**起因是一次实测**：`llm-wiki.md` 的「已实现 / 计划实现」表里，
**三行写着「计划中，尚未实现」，而它们全都已经落地**
（`knowledge/sources/*.json`、`Doc.sources` / `Doc.review`、
`scripts/wiki-impact.mjs`）。写完那句话的时候它们就存在了。

没有任何检查会发现——lint 管的是断链、重复 slug、孤儿页，
那些都是**页与页之间**的问题。而这一条是**页与仓库之间**的问题。
**它读起来像事实，所以没人会去核实。**

### 做出来的东西

`verify:` 声明写在知识页 frontmatter 里，**每条查两件事**：

```yaml
verify:
  - claim: 来源登记与版本固定
    stated: 来源登记与版本固定 | **已实现**
    path: knowledge/sources/*.json
    expect: exists
```

- `stated`——页面正文里那句原话，必须**逐字**出现；
- `path` / `expect`——那句话对应的文件在不在。

**两个都查，缺一不可。** 只查文件的话，正文改了、声明没改时，
声明还在验一句没人说过的话——检查照样绿，而它绿得毫无意义。

放在 `astro.config.mjs` **加载期**，理由与 frontmatter 校验完全一样：
在 remark 管道里抛错，Astro 不会让构建失败（实测：错误打印 22 次、
页面退化、而 `Build exit code: 0`）。

### `globToRegExp` 被写坏了三次——这是本轮最值得记的一段

这个机制里唯一一处自己写的解析，三次的症状**都是「正则看着挺对、而且测试是绿的」**：

| 版本 | 写法 | 症状 |
|---|---|---|
| ① | `**` → `(?:[^/]+/)*/`，又叠加循环补斜杠 | 要求**至少一层**子目录，`src/config.ts` 匹配不上 |
| ② | 「上一段是 `**` 就不补斜杠」 | `src` 与 `**` 之间那个斜杠丢了，**全都匹配不上** |
| ③ | 分隔符补在 `**` 分支之后 | `src/**` 正常了，`src/**/*.ts` 又全不中 |

三次都是**我盯着 `.source` 数斜杠**，而 `new RegExp` 的 `.source`
会对 `/` 补反斜杠——数出来的是 `\/`，肉眼极容易多数或少数一个。
所以现在测试里的断言**一律用 `test()`**，不碰 `.source`，
并且拿**真实文件树**交叉验证（手写的期望值可以跟实现一起错）。

那个 glob 正好写在知识页的示例里——**金标全绿、功能是坏的**，
本仓库最防的那类 bug，这次踩在自己身上。

### 负向验证抓到一个真缺陷

第一轮注入「把表改回『计划中』但不改声明」时，**检查没红**。
原因：`evaluateClaims` 收到的是**整个文件**，而 `stated` 的字符串
**在 frontmatter 里它自己那一行就有**——**声明在验证自己的字符串**。
改成只喂正文之后，注入立刻变红。

另外两轮注入（改文件路径、反转 `expect`）都正常变红。

### 未决

1. **只有 1 个知识页有 `verify:` 声明。** 其余 5 页还没写——
   而写声明要先把页面里的可证伪说法找出来，那是一次内容审阅。
2. **它只查「文件在不在」，查不了「写对了吗」。** 一条声明能覆盖的范围
   恰好就是「有没有」这个层级，写清楚比写宽重要。
3. `globToRegExp` 的 `**` 只支持「零个或多个目录」这一种语义，

## 2026-09-23 · 影响分析 `wiki:impact`

**动机**：来源登记做出来之后，下一个问题自然是「来源出了新版，哪些页面要动」。
在此之前**这个问题没有答案**——引用只是一串链接、不带版本，
所以「引了这个来源」与「引了这个来源的**这一版**」分不开。

### 它第一个抓到的真东西

```
① 直接引用者（1）      cjk-typography · WD-20240312 · §5.1.1
② 可能受影响者（1）    design-tokens（经 cjk-typography）
③ 仓库辅助载体（2）    docs/cjk-typography.md
                      src/content/posts/cjk-web-typography.md
```

**③ 里那篇文章**引用了同一个规范，但因为它不是知识层条目、
不在来源登记的范围里，**此前没有任何地方把它和这个来源关联起来**。
"不在发布集合里"恰好是它最容易漏的原因。

### 设计取舍

- **三组互不重叠**（已在①的不再进③）：重叠会让人以为"还有别的地方要改"，
  而那正是这个工具要消除的困惑。
- **不联网**：只回答"已登记的这一版被谁引用了"，不去看远端有没有新版——
  那是另一件事（要网络、要登录、也不可靠）。

## 2026-09-23 · 迭代 B：统一解析与身份（三处）

**动机**：路线图阶段 1 的四件事——「唯一的解析器」「内容图与导出扫描统一」

### ① frontmatter 有两套解析，且第二套会静默解析错

`remark-wikilink.ts` 里有一个**手写的 YAML 子集解析器**（注释写着
「简单键值，不需要完整解析」），只服务于 `[[链接]]` 的查找表。

与真实 YAML 逐例比对：**12 个边界用例，6 个分歧**（块标量 `|` `>`、
值写在下一行、行尾注释、双引号转义、单引号 `''`）。
现有内容一条都不触发（11 文件 × 6 字段 = 66 次比对，0 分歧）——
所以是**潜在风险**，而下一位作者写 `title: >` 就会静默踩中。

**第一版修法是错的。** 改成越界就抛，清缓存后注入 `title: >`：

    错误打印 22 次；页面退化（链接 4→3）；Build exit code: 0

**在 remark 管道里抛错，Astro 不会让构建失败**——那比"链接静默指错"更糟。
正解是挪到 `astro.config.mjs` 的**加载期**：什么都不渲染，抛出去就是构建失败。
同一个注入现在 exit 1、指出文件与字段、一个页面都没渲染。

### ② 同名标题按遍历顺序任选一个

`buildGraph` 与 `buildLookup` 都是 `if (!has(title)) set(title, slug)`。
调换输入顺序，同一个 `[[Shared]]` 分别指向 a 和 b，而**两次 lint 都是 0 错误**。

改成「同名就不注册」：用了歧义标题 → error 并列出全部候选；
存在但没被引用 → warn。两处查找表行为一致，不会再各算各的。
端到端验证：把一页标题改成另一页的，构建 exit 1、6 条 `ambiguous-wikilink`。

### ③ 锚点从没被校验过

`[[target#missing-heading]]` 在目标页存在时，`broken` 与 lint **都是空的**。
「详见第 3.2 节」可以指向不存在的小节——**静默跳错位置**。

新增 `scripts/check-anchors.mjs`，在**产物上**查而不是从源码再推一遍：
小节 ID 是渲染期 `github-slugger` 生成的（重复标题带 `-1` 后缀），
从源码推算等于再造第三套解析器。全站 32 页、134 个锚点全部可解析。

### ④ 草稿泄漏扫描有个无声的白名单

`check-formats.mjs` 的草稿探针本来就不弱（唯标记 + 遍历 dist + 清单 + 全量导出），
但它是**按扩展名白名单跳过**的：只扫 `html|md|txt|xml|json|ndjson`。

白名单当时的判断是对的，失败方式却是无声的——将来多一个出口
（换扩展名、加一种导出格式），泄漏检查会**静默地不覆盖它**，
而扫描照样打印「草稿没有进入任何文本出口」。

改成扫全部文件、按 UTF-8 试解码，解不出的跳过但**把跳过数报出来**：

    旧白名单：65 个    新写法：77 个文本 + 30 个二进制跳过

新增覆盖的 12 个正是最可能藏内容的：`pagefind/*.js`（UI / worker）、
`_astro/style.*.css`、`favicon.svg`、`_headers`。

边界写进注释：二进制搜不出明文标记，这是**方法的边界不是保证**；
索引那侧靠另一条性质兜住——索引只能收录实际生成的页面，而草稿页根本没生成。

### ⑤ 语义正文摘要

新增 `src/lib/wiki/digest.ts`。覆盖 kind / title / summary / body / declaredRelations，
**不覆盖** slug（搬家不是改内容）、draft、以及将来的 `review` 字段本身

### 改了什么

**① 估算被当成了实测。** 站点自己的「token 节省率」用的是
`estimateTokens`——一个刻意可解释的启发式（CJK 1 字 1 token、其余 4 字符 1 token），
而 README 与文档写的是「Measured saving」「实测」「真实数字」。

2026-09-23 装 `tiktoken` 用 `o200k_base` 逐页复算：

| 页面 | HTML 估算 / 真实 | MD 估算 / 真实 | 节省 估算 / 真实 |

| /wiki/content-negotiation/ | 3,681 / 3,963（−7.1%） | 1,106 / 1,103（+0.3%） | 70.0% / **72.2%** |

**② 那个函数的注释在说反话。** `estimateTokens` 的注释写着

`/TR/2024/WD-css-values-4-20240312/`、`/TR/2026/WD-css-fonts-4-20260913/`，
三处逐个 HTTP 200 验过。共替换 14 处。

**④ 一条核不掉的引用，删掉。** 原文写「Ahrefs 2026 年 5 月实测 **137,210 个域名：

**查不到就不留着**——精确到个位数、读者却无从核对，只会因为"看起来很硬"被转引。

## 2026-09-22 · M0：中文排版的一组算式与归因错误

**动机**：同一组结论散在 6 个载体里，其中两处论证是错的，而现有的检查

### 来源与版本

| 来源 | 固定版本 | 用于 |
|---|---|---|
| [CSS Values and Units Level 4 §ch](https://www.w3.org/TR/2024/WD-css-values-4-20240312/#ch) | W3C Working Draft, 12 March 2024 | `ch` 的定义 |
| [CSS Fonts Module Level 4](https://www.w3.org/TR/2026/WD-css-fonts-4-20260913/#font-style-matching) | W3C Working Draft, 13 September 2026 | 字重匹配（§2.2.2）与伪合成开关 |
| [RFC 9110 §12.5.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-12.5.1) | RFC 9110（STD 97） | Accept 的优先级规则 |

**把平局规则列在「依据 RFC」之下**——内容协商那篇文章的错误就是从这儿来的。
只改文章不改这里，就是"同一个事实有几个表面、只改一处等于没改"。

### 改了什么

**行宽（算错 + 结论错）**

原话：「一个汉字大约等于两个 `ch`。所以按 66ch 排中文，每行会排出约 130 个汉字
——远超出中文舒适的 30 到 40 字。」

- 按它自己的前提应当**除以 2 得 33**，而不是乘以 2 得 130；
- 33 本来就落在它自己说的 30–40 里，所以「远超」也不成立；
- 被这句话遮住的事实：**66ch ≈ 33em，与本题采用的 34em 宽度几乎相同**。
  这个改动换的是**单位的可预测性**（`em` 等于字号、与字体无关），不是行宽。

**字重（归因错）**

原话：「写 `font-weight: 600` 时浏览器找不到 600，就伪合成一个……正确做法：标题字重写 500。」

- 伪合成的开关是 `font-synthesis-weight`，**不是字重数值**；
  写一个字体没有的字重时，规范要求的是**去找最接近的真实字重**；
- 本站 `base.css` 关掉合成后标题用 600：拉丁拿到 Archivo 的真实 600，
  中文落到 700。**写 500 反而会让中文掉到 400**——比 600 更糟。
- 顺带：`base.css` 的注释里**早就把对的写下来了**，是文章没跟上。

**规范归因**

内容协商那篇原先写「这时按 RFC 的规定，服务端应当认为靠前的那个优先」。
RFC 9110 §12.5.1 规定的是按**具体程度**排优先级，对 q 值相同的只说是
*equally preferred*，**没有给顺序**。所以「并列时靠前优先」是本地策略，
已在文章与 `accept.ts` 注释里都改成这个说法。

**llm-wiki.md**

- posts 原被列为「不可变的输入」，但它们**会被修订**（这篇记录本身就是证据）；
- 「RAG 永不改变、永不连接」太绝对——GraphRAG 就会组织关系与预计算摘要；
- 「一份来源可能改动 10 到 15 个页面」**没有出处**，标注为未核实；
- 补了 gist 的**真实链接**（原先只有文字，`grep -c gist.github.com` 是 0）；
- 补一张「已实现 / 计划实现」表——此前通篇以"本项目怎么做"的口吻描述，
  读者分不清哪些是真的、哪些是打算做的。

### 未决问题

1. **Ahrefs 那 97% 的引用没有可点开的来源。** 试过几种 ahrefs.com/blog 路径都是 404。
   已在文章里标注「待核验，不要转引」。要么找到确切地址，要么撤掉该句。
2. **「1 汉字 ≈ 2ch」仍是粗估。** 严格值取决于字体，本轮没有对每个候选字体实测。
   文章已改成"粗估"措辞，但没有给出实测表。
3. **跨平台字重结论未实测。** 「苹方/微软雅黑只有 400 与 700」来自 `base.css` 的既有注释，
