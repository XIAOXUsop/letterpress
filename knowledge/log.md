## 2026-09-24 · 迭代 Q：给四个「没人量过的门禁」做负向验证，抓到一个真缺口

本轮已经四次栽在「尺子坏了」（ANSI 锚点、patch 静默、探针自身、
`astro check` 不查 `.mjs` 运行时语法）。于是去问一个更根本的问题：
**`verify:all` 里那 13 步，哪些从来没被验证过「坏了会不会红」？**

扫了一遍脚本里的负向验证说明，`testcount` / `search` / `anchors` / `base`
**四个都没有**。注意这**不代表它们坏**，只代表**没人量过**——
而「没量过」与「没问题」在这个项目里已经被反复证明不是一回事。

### 四个门禁逐个注入

| 门禁 | 注入 | 结果 |
|---|---|---|
| `testcount` | 把 README 里的 438 改成 999 | ✅ 红 |
| `anchors` | 造一个指向不存在锚点的链接 | ✅ 红 |
| `base` | 注入一处绕过 `path()` 的硬编码绝对路径 | ✅ 红（32 个页面） |
| `search` | 把全站 `<html lang>` 改成 `xx-YY` | ❌ **全绿** |

**前三个守住了。第四个没有** —— 而且它守的正是本项目最提防的那类失败。

### 抓到的缺口：一致 ≠ 正确

把 `<html lang={site.lang}>` 改成 `<html lang="xx-YY">`（一个不存在的语言），
`verify:search` **三项全绿**：

```
✓ 32 个页面都声明了 lang="xx-YY"
✓ 索引语言与页面语言一致：xx-yy
✓ 内容清单里的 11 个条目全部进了索引
```

**它只查「全站一致」，不查「这个 lang 是不是配置里声明的那个」。**
而 README 明确写着「`lang` 别改错，浏览器的中文标点规则依赖它」——
**门禁管得了「丢」，管不了「错」**。

后果正是 `check-search.mjs` 自己在文件头警告的那件事：
Pagefind 按 `lang` 选分词器，`xx-YY` 选不出中文分词器，
**搜「中文排版」会退化**——页面还在、构建还绿、测试全过，
只是用户再也搜不到那篇文章。

已补：比对 `src/config.ts` 里声明的 `site.lang`。
读文本而不是 import，因为那是 `.ts` 且内部有 `.js` 后缀 import，
裸 Node 加载不了（那个约束这轮已经栽过三次，见 `check-portability.mjs`）。

负向验证：注入 `xx-YY` 立刻红（退出码 1），恢复后 0。

> **这一条是本轮最值得记的**：门禁**通过了**，而且通过了三次，
> 而它守的东西是错的。**「有检查」与「检查守住了该守的」是两件事**，
> 区别只有一个——**试着把它弄坏**。

### 附带：三个门禁的注入方式本身也说明了各自测什么

- `base` 对「markdown 链接改成绝对路径」**不红**——因为 markdown 链接
  会经 `path()` 正确处理，**那不是缺陷**。换成组件里的硬编码 `href` 才红。
  也就是说这个门禁量的确实是「绕过 `path()` 的硬编码」，不是「所有绝对路径」。
- 第一次测 `search` 时忘了重建 `dist`，Pagefind 索引缺失导致**恢复后仍红**——
  **尺子坏了的时候结论会整齐地错一遍**（迭代 L 已记过一次，本轮又遇上）。

### 验证

`npm run verify:all` 13 步全过；438 项单测、196 项契约全绿；
`verify:search` 现在多一条「页面 lang 与 site.lang 一致」。

## 2026-09-24 · 迭代 P：给 `wiki-ask` 装上尺子，以及增量补丁的失败模式

迭代 O 登记的未决：`wiki-ask` 仍零测试。迭代 N 之后它已经能被裸 Node 加载
（因为用了 `read-page.ts`），所以技术条件具备了——本条补上。

### 为什么它此前测不了

`wiki-ask.mjs` **顶层就有 `process.exit`**，逻辑整个写在顶层。
**无法 import 就无法单测**——与迭代 G 之前的 `wiki-impact` 同一个处境。
这已是本项目第三次为同一个原因做同一件事（抽出纯函数、脚本只做 I/O）。

抽出 `src/lib/wiki/context-pack.ts`，15 条测试，其中一组直接对着
**路线图 §3 的退出条件**逐样断言：文档 ID、片段、来源版本、状态、关系路径。
**那五样正是在这个文件里组装的**——也就是说这个文件就是那条退出条件的实现，
而它此前一行测试都没有。

### 顺带修掉的：`context-pack.ts` 一开始也带 `.js` 后缀

写完才发现它 import 了 `./retrieve.js`，裸 Node 加载不了。
这正是 `verify:portability` 要守的东西——**而新模块不在清单里**。
已加入 `CORE`，并做负向验证（把后缀改回去，门禁立刻报，退出码 1）。

### 本轮最值得记的：增量补丁在含转义的任务上不可靠

用 Python 脚本批量改 `wiki-ask.mjs` 的输出段，**连续失败四次**，
而且**失败特征是「不报错、什么都没变」**：

1. `
` 被写成真实换行 → 字符串被拆开、语法错误（`astro check` 报 35 个 error）；
2. 第二次替换**匹配不上**（字符串已被改坏），于是「没报错、也没修好」；
3. `astro check` 修好了，但**它不检查 `.mjs` 的运行时语法**，
   于是还有一处坏字符串直到实跑才暴露；
4. 最后连文档注释里的反引号内容都被 bash 吃掉。

> **同一个教训，迭代 J 记过一次，本轮又撞上。**
> 区别是这次我**当场改用 Edit 工具逐处修**，而不是继续修补脚本。
>
> **教训的教训**：当同一个方法连续失败两次，就该换方法，
> 而不是第三次换个参数再试——尤其当失败模式是「静默无变化」时。

### 另一条：「零耦合」是设计意图，「可加载」是它的兑现

`graph.ts` / `lint.ts` / `lint.ts` 此前都标着「本模块是纯函数」，
**注释里的约束从来没被检查过**。迭代 N 发现它们加载不了之后
才给约束配了门禁。

> **约束写在注释里而没有检查，就只是愿望。**
> 本项目这轮给三条这样的约束配了执法：零耦合（可加载性）、
> 可选字段的健壮性（可选链形状）、版本号一致性（双向比对）。
> **每一条都是先违规、再补执法**——不是先想到要检查什么。

### 顺带实测出第三个检索局限：「参考」小节会盖过答案

改完之后人读输出正常，于是拿真实问题跑了一遍：

```
问「中文排版的行宽为什么用 em」
主命中 = cjk-web-typography 的「参考」小节，覆盖 100%
第二   = cjk-typography 的「正文开头」，覆盖 80%（答案在这一节）
```

**文章末尾的「参考」小节列着全部规范链接，于是它是元信息最密集的一段**——
`em`、`ch`、字重、合成，几乎每个查询词都能在那里命中。
而真正论述行宽的那一节反而只有 80%。

> 词法检索分不出「这一段是答案」与「这一段是引文清单」——
> **两者都是术语密集的技术文本，而二元组只看词的共现。**
>
> 这与前两个局限同源但方向不同：那两个是「找到了错的东西」，
> 这个是「**找到了对的东西但排在后面**」。影响可控（两段都在 pack 里），
> 但排序确实把引文清单放在了第一位。
>
> 修它要靠段落类型识别（`## 参考` 这种约定，脆弱）或向量（与立身之本冲突）。
> **登记为第三条已知局限，不修。**

### 验证

`npm run verify:all` 16 步全过；438 项单测、196 项契约、
107 文件可复现构建全绿；`verify:portability` 现在覆盖 7 个核心模块；
检索金标 23 条、**3 条已知局限可见**。

## 2026-09-24 · 迭代 O：把 bug 的「形状」写成门禁

迭代 N 抓到 `computeImpact` 在 `refs` 缺失时崩溃，根因是
**类型标必填而实际可为 undefined**，且所有调用方都填了空数组——
**默认值救了它**。本轮做两件事：查同类形状、修它，并把形状固化成门禁。

### 系统排查同类形状

`a?.related.includes(x)` 这个写法是同型的另一面：
**可选链只保护了左边为 null，没保护该字段本身为 undefined**，
抛的是 `undefined.includes`。全库扫了一遍——

```
grep -rnE "\?\.(related|sources|refs|review|declaredRelations)\." src/ scripts/
```

**只此一处**，在 `wiki-ask.mjs`。已修为 `a?.related?.includes(...)`。

顺带把 `content-manifest.ts` 里 `doc.sources.map`（靠外层
`doc.sources?.length` 短路保护）也改成 `?? []`——
**逻辑上本来就安全，但「靠外层条件保护的内层访问」在改代码时极易被挪掉**。

### 写成门禁之后，它先把自己判为违规

`verify:portability` 加了第二条：扫 `?.(可选字段).method(` 这个形状。
第一次跑就报 `check-portability.mjs:34`——
**因为它自己的文档里写着 `a?.related.includes(x)` 这个反例，而反例符合模式。**

> 这件事有两层意思：
> 一是**门禁确实在工作**（它把一个真实的同类形状照出来了，只是照的是自己）；
> 二是**写下反例的检查会被自己的反例绊倒**——
> 所以必须显式排除自身，并在注释里写明为什么。
>
> 顺带又一次印证迭代 J 那条教训：**增量 Python 补丁静默失败**，
> 本轮第三次（第三次是重写整个 `check-portability.mjs` 才修好）。
> **补丁失败的特征是「不报错、什么都没变」**——所以每次补丁后都要看结果。

### 诚实地说：manifest 那 4 条用例加固前也会过

`content-manifest.test.ts` 新增的 4 条「可选字段缺失不崩」用例，
在加固**之前**也是绿的——因为外层短路本来就保护着。
**它们量的是「加固后仍然对」，不是「加固抓到了什么」。**

与 `wiki-ask` 那处不同：那里是**真的会崩**（`undefined.includes`），
而 manifest 那处是**依赖外层条件才不崩**。
两者的区别值得记住：**一个现在崩，一个将来崩**——
而「将来崩」的那一类，正是门禁该管的。

### 未决

1. `wiki-ask` **仍然零测试**。它现在能被裸 Node 加载了（因为用了 `read-page.ts`），
   也就是说它**可以**被单测覆盖，但本轮没做——它是一个交互式 CLI，
   测试形态需要单独设计。已登记。

### 验证

`npm run verify:all` 16 步全过；423 项单测、196 项契约、
107 文件可复现构建全绿；两道新门禁（可加载性、可选链形状）都在链路里。

## 2026-09-24 · 迭代 N：拿第二份内容集跑一遍，抓到一个只在异构场景出现的崩溃

路线图阶段 4 的退出条件：「**一个全新的真实内容集能在不复制内部代码
的情况下使用核心流程**」。本仓库至今只有一个站点，于是拿一份
**刻意与本站不同**的合成内容集跑了一遍——这是那条退出条件的第一次实测。

（诚实起见：合成语料**不是**真实站点，所以这是「第一次实测」而不是「证明」。
真实站点那一步仍然欠着，已登记在下面的未决里。）

### 先撞上一个约束，才写出门禁

第一版探针直接 `import { buildGraph } from '.../graph.ts'`，
**崩了**：`Cannot find module '.../wikilink.js'`。

> 这些 `scripts/*.mjs` 是**裸 Node** 跑的，而 `graph.ts` 内部用
> `.js` 后缀 import（TS 惯例，bundler 才解析得了）。
> 站内两个脚本能 import 源码，是因为它们 import 的模块**内部没有 `.js` 引用**。
>
> 实测六个「零耦合」核心模块：`retrieve` / `impact` / `slug` / `digest` 可加载，
> **`graph` 与 `lint` 不可加载**——而后者是知识层的地基。
> **「零耦合」不等于「能被直接复用」**，这两件事此前被当成一件。

已修：`graph.ts` 与 `lint.ts` 的 4 处 import 改用 `.ts` 后缀
（不是无后缀——裸 Node 不做 TS 的无后缀解析，那次试过，失败）。
并新增 `verify:portability` 门禁：六个核心模块**必须能被裸 Node import**。

> 判据是「真的 import 一遍」而不是读源码找 `.js`——
> 因为**判据是传递依赖**：本模块干净但它 import 的模块不干净，一样加载不了。
> 读单个文件会漏掉这一层。**唯一可靠的判据是让解析器自己说。**

### 探针第一次跑就抓到一个真 bug

```
TypeError: Cannot read properties of undefined (reading 'some')
```

`computeImpact` 在 `refs` 缺失时崩溃。根因：`ImpactPage.refs` 与 `related`
在类型上都是**必填**，而真实的 `Doc.sources?` / `Doc.declaredRelations?`
**都是可选的**。

> 站内一直没暴露，是因为两个调用方（`read-page.ts` 与 `check-impact.mjs`）
> **都老实填了空数组**。
> **默认值救了它——而那正是最危险的状态**：它掩盖了类型与现实脱节，
> 于是「类型说是必填」与「运行时是 undefined」长期并存而无人发现。
>
> 这与本轮反复出现的「0 有两种来源」同族：
> **一个看起来正常的值（空数组）掩盖了一个不正常的现实（字段可能不存在）。**

修法不是「让调用方记得填」，是**类型接受现实**：字段改可选、实现兜底、3 条用例。

### 探针自己也写错了三次

修完 bug 仍有 2 项不成立。逐个查，**两次都是探针错、实现对**：

1. 我以为 `ledger` 是孤儿页——其实 `payments` 正文里 `[[ledger]]` 链到它了；
2. 影响分析返回 0——我传了 `sources`，而 `ImpactPage` 要的字段名是 `refs`；
3. 孤儿页那项仍红——`shared-two` 是 `entity`，而孤儿页**只算 `kind === 'wiki'`**（设计如此）。

> **每次都是「探针报错」被我当成「实现有 bug」。**
> 探针本身是需要验证的东西——**它跑绿了不说明被测对象对，只说明探针没写错**。
> 而写错探针的代价与写错检查一样：结论会整齐地错一遍。

### 未决

1. **真实第二站点仍然欠着。** 合成语料只证明了「核心函数不依赖本站」，
   证不了「接入一个新站点不用改核心」——后者要一个真实的第二内容集。
2. **`graph.ts` / `lint.ts` 之外的模块没查。** 门禁只覆盖 `src/lib/wiki/`
   下的六个核心模块；`content-manifest.ts` 等仍用 `.js` 后缀，
   它们**本来就不该**被裸 Node 加载（有 fs / Astro 依赖），所以是合理边界。

### 验证

`npm run verify:all` 16 步全过（新增 `verify:portability` 与 `verify:second-site`）；
419 项单测、196 项契约、107 文件可复现构建全绿。

## 2026-09-24 · 迭代 M：一条规则写对了，却没人守——版本号门禁

迭代 K 给 manifest 加了 `provenance` 字段，**当时没有升 `version`**。
回头一看，同一份代码里就写着判据：

> 真正该升的是这几种：**字段增删或改名**、字段语义改变……

**规则是对的，我违反了它。** 而更糟的是，那段注释的**开头**写的是
「只在消费方需要改代码时才升」——**两句话对同一次改动给出相反答案**，
所以照哪句做都不算错。这种自相矛盾的判据等于没有判据。

### 统一成一条可执行的判据

> **产物里已有文档的 JSON 形状变了，就升。**

理由不是「下游要改代码」，而是**同一份 `version: 1` 在不同时间会对应两种形状**——
那正是版本号要防的事。「可选字段」也不等于不用升：
`provenance` 是可选的，但它对有来源的页面**真的会出现**。

已升到 v2，并给判据补上边界：**只有「该字段对所有文档恒为缺席」时才可以不升**
（`manifestId` 加显式 `id` 支持就是这一类：产物里的 ID 一个字节都没变）。

### 规则写对了还要有人守

`check-formats.mjs` 补了一条断言，而且**先撞上一个约束才发现它**：

> 我第一版是 `import { CONTENT_MANIFEST_VERSION } from '../src/lib/content-manifest.ts'`，
> 结果 `verify:formats` 直接崩：
> `Cannot find module '.../wiki/graph.js'`。
>
> **原因**：这些脚本是**裸 Node** 跑的，而 `content-manifest.ts` 内部用
> `.js` 后缀 import（TS 惯例，bundler 才解析得了）。
> 仓库里其它脚本能 import 源码，是因为它们 import 的模块内部**没有 `.js` 引用**。
> 全库有 31 个文件是那种写法——改后缀是大动作，**风险远大于收益，不做**。
>
> 所以改成**从源码文本里正则读出常量**，绕开解析问题。

### 单向检查不够

第一版只查「产物 version == 期望值」。**那样源码升了、期望值忘了改，
产物与期望值仍然相等，契约照样绿**——而产物已经和源码声明的对不上了。

改成**双向**：产物、源码常量、契约里的期望值三个数一起比。
负向验证两个方向都试过（只改源码 / 只改期望值），**都会红**。

> 「一个检查写了」和「一个检查有效」之间差的这一步，
> 就是**试着把它弄坏**。本轮第三次这么做，三次都抓到了东西
> （「全过≠都量过」「闸被另一道闸遮住」「单向检查不够」）。

> **这是本项目反复出现的同一个模式**：
> 判据写对了 → 有人违反 → 违反时无人报警 → 于是再写一条判据。
> **光有规则不够，规则要有执法。** 本轮至少给「版本号」这一条配了执法。

### 硬编码的版本号其实有四处，而第一处被抓到时我以为只有一处

`content-export.test.ts` 里写着 `version: 1`——**类型系统先抓到了它**
（`Type '1' is not assignable to type '2'`）。我把它改成引用常量，就以为完事了。

**跑契约又红了一条**：「清单版本为 1」。继续查，发现**同一个数字在四个地方**：

## 2026-09-24 · 迭代 K：来源与复核状态进机器出口——页面能看见，机器看不见

阶段 3 的退出条件里有一条：「**任何 stale/superseded 内容都不会在
无提示情况下成为首选证据**」。去查机器出口，发现一个实打实的缺口：

| 出口 | 来源 | 复核状态 |
|---|---|---|
| HTML 页面 | ✅ Provenance 组件 | ✅ 显示「已复核 / 待复核 / 已过期」 |
| `content-manifest.json` | ❌ **没有** | ❌ **没有** |
| `content.ndjson` | ❌ **没有** | ❌ **没有** |

**订阅者按 manifest 同步时，无从知道哪一篇已经过期。**
而这正是那条退出条件要防的事——机器侧会比人侧**更信任**一篇已经不可信的内容，
因为它连「不可信」这个信号都收不到。

### 缺口的形状：不是「没做」，是「做了一半」

`Provenance` 组件早就存在且渲染正常，来源登记也早就跑通。
**唯独机器出口没有接。** 这类缺口最难发现：三处里两处是对的，
只有一处不对，而没有任何检查会告诉你「三处应该一样」。

### 实现里有两个刻意的选择

**① 整个 `provenance` 键在两者皆无时缺席，不是空对象。**

空数组 / 空对象读起来像「查过了，没有」；
缺席是「没标」。**这两种含义混成一样，「没量过」就会看起来像「量过且为空」**——
这与迭代 H 那条「全过 ≠ 都量过」是同一个原则的另一个出口。

**② NDJSON 一行代码都不用改。**
`ContentExportRecord extends Omit<ContentManifestDocument, 'markdown'>`，
所以它**自动继承** provenance。这是共用类型的回报——
如果当初 NDJSON 另写了一套字段形状，这一处就得记得同步，
而「记得」是所有事情里最不可靠的一环。

### 单测过了 ≠ 产物里有

`buildContentManifest` 的单测一开始就是绿的（先写用例，确认失败，再实现）。
但那只量了**函数返回的对象**，而产物还要经过「怎么被序列化、怎么被写盘」。

所以在 `check-formats.mjs`（产物级）补了一条断言：**产物里必须真的有 provenance**。
负向验证把实现改成「永远不进产物」，断言立刻报：

> ✗ 内容清单里一篇 provenance 都没有——本站有登记来源的页面，
> 这说明 provenance 没有进入产物（**单测过不代表产物里有**）

> 这条断言的价值不在于它抓到了什么，而在于它**能在将来被删掉时立刻报警**。
> 一个只在出事那天才被想起的检查，不写也照样出事。

### 文档也要跟上

`docs/content-export.md` 原先没有提 `provenance`。
机器出口的字段若不文档化，订阅者就**不知道它存在**——
那等于把这个字段只给看得懂源码的人用。已补上格式与两条语义说明
（缺席 ≠ 空；`stale` 不该被当成新鲜证据）。

### 验证

`npm run verify:all` 14 步全过；412 项单测、196 项契约、107 文件可复现构建全绿。

**为什么文章恰恰最需要这一层**：文章里写的正是那些**日期化的规范 URL**
（`WD-css-values-4-20240312`）——日期化写出来就是为了不被移动版本顶掉，
**不登记等于白写**。

> 登记的含义是「这条结论有据可查」。把顺带提及的链接也登记进去，
> 会让「已登记」从「我验证过」退化成「我见过这个链接」——
> **而那正是这套东西最容易制造出来的错觉。**
> 保持「只在值得单独治理的结论上标」比多登记几个要难。

## 2026-09-24 · 迭代 E：稳定身份，以及一次「看起来更对」的改法被实测否掉

路线图阶段 1 的退出条件里有一条：**「每个公开文档只有一个规范 ID 和一个当前 URL」**。
去看实现，发现 `manifestId` 就是 `${kind}:${slug}`——**ID 完全是 URL 的函数**。

后果具体是什么：manifest 是**对外发布**的机器出口，下游按 `id` 同步。
改一次文件名或显式 slug，同一篇内容的 ID 就变了，
订阅者会把它当成一篇新文档，旧文档凭空消失且无从追溯。

而这条**此前没有任何测试覆盖**——`content-manifest.test.ts` 里一条 `manifestId` 用例都没有。
这就是它能长期错着的原因：**没人量的东西不会坏，只会不变。**

### 先试了「内容寻址」，被自己的用例否掉

第一版实现是「没有显式 `id` 时，用 `kind` + 规范化正文摘要的哈希」。
理由听上去很对：正文没变，改名就不影响 ID。

**然后新写的用例直接把它打红了**：

```
FAIL 不同文档不会撞 ID
AssertionError: expected 'post:a1845325f951c9f4' not to be 'post:a1845325f951c9f4'
```

两篇 fixture 的正文都是 `'正文'`，于是**得到同一个 ID**。
这不是 fixture 的问题——**正文相同的两篇不同文档在真实站点里完全可能**，
而 manifest 的 ID 是下游认文档的唯一凭据，**撞 ID 意味着两篇互相覆盖**。

**这比「改名会改 ID」严重得多**，所以这条设计被否掉，回到「显式 id 优先、缺省仍用 slug」。

> **一个更隐蔽的问题我当时没看出来**：内容寻址下**改一个字正文就换 ID**。
> 那等于每次修订都让全体下游重新同步——比改名频繁一个数量级。
> **「更稳定」的方案在这里反而制造了更大的不稳定。**

### 顺带修掉我自己写错的一条断言

新加的用例里我一度写了「不同 slug 也必须得到相同 ID」。
**那是错的**——那等于允许两篇不同内容共用一个身份，正是 manifest 要防的覆盖。
写完读一遍才发现：**它和同一个 describe 里「不同文档不会撞 ID」直接矛盾。**
断言自己内部打架，说明它测的不是一个想清楚的要求。

最终形态：显式 `id` 优先；缺省仍退回 `kind:slug`（**不制造新的破坏**），
并把「没写 id 的文档改名仍会改 ID」这个边界**写在代码注释里**，而不是假装解决了。
schema 两个集合都加了 `id` 字段（**不声明会被 Zod 静默剥离**，见 `content.config.ts` 里 draft 那段注释），
六个 wiki 条目全部写上了显式 id——**知识条目被改名/合并的频率比文章高**，
所以这个字段对 wiki 更值得写。

### 改名实验：ID 确实稳住了，但改名的**成本比想象中高**

不满足于单测绿，实际改了一次名来做证伪实验：把 `design-tokens` 的 slug 改成
`design-tokens-renamed`。结果 ID 仍是 `wiki:design-tokens`，URL 变成
`/wiki/design-tokens-renamed/`——**身份与 URL 成功分离，机制成立**。

但实验过程本身比预想的更有价值：**改名连续撞了三道门**。

1. **两处正文 `[[design-tokens]]` 断链**，构建中止。
2. 改完正文才发现**真正的断链在 frontmatter 的 `related`**——
   `related: [cjk-web-typography, design-tokens]` 里也有它。
   也就是说**一次改名要改三类地方**：正文链接、`related` 声明、以及别处提到它的散文。
3. 修完断链，又被 **`review-stale`** 拦下——改动了正文，
   复核摘要自然对不上。

> **这说明「稳定身份」只解决了 ID 漂移，没解决改名本身。**
> 而且第 2 条是我**改完第一轮才发现的**：第一轮我只搜了 `[[...]]`，
> 没想到 `related` 也是一条引用通道——**同一个概念有两套写法，
> 搜的时候只搜一套，就会漏**。这和 `log.md` 里记过的
> 「frontmatter 有两套解析」是同一族问题：**通道不止一条。**

**教训**：`related` 与 `[[wikilink]]` 在功能上重叠，重复带来的是
「搜引用时容易只搜一处」的成本。真要收敛，应该让 `related` 由
正文链接派生，而不是要求作者两处都维护。**本轮不做**——
那会改 `content.ts` 的取图逻辑，属于路线图阶段 1「统一解析」的范围，
不在这一小步里。

### 门禁又抓了一次漂移

加完 6 条测试后 379 → 385，`verify:testcount` 立刻报出四处 README/docs 写的 379。
已同步。**这是同一个门禁本轮第二次抓到我**（上一次是 token 节省率）。

### 未决

1. **posts 还没写显式 id。** 只给 wiki 六页写了。文章改名的频率低，
   但这意味着**文章的 ID 仍随 slug 变**。要不要全量补齐，
   取决于是否真有外部订阅者——**在有真实消费方之前不补**，
   补了也只是让 11 个 ID 变一次，没有收益。
2. **改 ID 规则会让全体 ID 变一次**，等于让下游全部重新同步。
   manifest 有 `version` 字段就是为此准备的，但**本轮没有升 version**
   ——因为最终实现保持了缺省行为不变，产物里的 ID 一个都没变。

### 验证

`npm run verify:all` 13 步全过；385 项单测、196 项契约、107 文件可复现构建全绿。

### ③ `em` 与汉字容量 —— 上一轮改了算式，没动那句更大的话

`em` 等于**计算后的 font-size**，规范保证且与字体无关。
但**「一个汉字正好 1em 宽」不是规范保证** —— 汉字 advance 取决于具体字体。

**决定性证据是规范自己**：CSS Values 4 专门定义了 `ic` 来表示
「字体中全角字形的典型 advance」，并规定**无法确定时假设为 1em**。
原文已抓到。**如果 `em` 就能保证汉字宽度等于字号，规范不必再定义 `ic`。**

原文还留着三句越界的话，全改了：

- `posts/cjk-web-typography.md`：「一个汉字约 1em 宽……**而且不随字体变**」
- `wiki/cjk-typography.md`：「粗估 `66ch` 是粗估，**`em` 不是估算`**」← 最直接的一句
- `tokens.css` 注释 + `docs/cjk-typography.md`：「能写成**确定的换算式**」

改后的表述统一为：**保证的是容器宽度稳定跟随字号，不是每行字数确定。**

### ④ 苹方字重 —— 与 Apple 官方清单直接冲突

`base.css` 写着「苹方、微软雅黑只有 400 与 700，写 600 会落到 700」，
而同一篇文章第 31 行承认「苹方有 Ultralight 到 Semibold」——**自相矛盾**。

抓 Apple 官方系统字体清单核对：PingFang SC 下**确有 `PingFang SC Semibold`**
（连 TC 也有）。已登记为 `apple-system-fonts.json`。

**更重要的是把「最接近」的方向查准了**。§2.2.2 只说
`a face with a nearby weight is used`，精确定义在 §5 的字重匹配算法：

> If the desired weight is greater than 500, weights greater than or equal to the
> desired weight are checked in ascending order followed by weights below…

**即请求 600 时先向上找（600→700→800→900），找不到才向下。**
所以有真 600 的字体**直接命中 600**，只有 400/700 的才落到 700。
**上一轮把它当成对所有中文字体都成立的规则，是把条件句套成了普遍句。**

## 2026-09-23 · 可证伪声明：把「页与仓库之间」的陈旧变成 CI 能查的东西

**起因是一次实测**：`llm-wiki.md` 的「已实现 / 计划实现」表里，
**三行写着「计划中，尚未实现」，而它们全都已经落地**
（`knowledge/sources/*.json`、`Doc.sources` / `Doc.review`、
`scripts/wiki-impact.mjs`）。写完那句话的时候它们就存在了。

没有任何检查会发现——lint 管的是断链、重复 slug、孤儿页，
那些都是**页与页之间**的问题。而这一条是**页与仓库之间**的问题。
**它读起来像事实，所以没人会去核实。**

### 做出来的东西

`verify:` 声明写在知识页 frontmatter 里，**每条查两件事**：

```yaml
verify:
  - claim: 来源登记与版本固定
    stated: 来源登记与版本固定 | **已实现**
    path: knowledge/sources/*.json
    expect: exists
```

- `stated`——页面正文里那句原话，必须**逐字**出现；
- `path` / `expect`——那句话对应的文件在不在。

**两个都查，缺一不可。** 只查文件的话，正文改了、声明没改时，
声明还在验一句没人说过的话——检查照样绿，而它绿得毫无意义。

放在 `astro.config.mjs` **加载期**，理由与 frontmatter 校验完全一样：
在 remark 管道里抛错，Astro 不会让构建失败（实测：错误打印 22 次、
页面退化、而 `Build exit code: 0`）。

### `globToRegExp` 被写坏了三次——这是本轮最值得记的一段

这个机制里唯一一处自己写的解析，三次的症状**都是「正则看着挺对、而且测试是绿的」**：

| 版本 | 写法 | 症状 |
|---|---|---|
| ① | `**` → `(?:[^/]+/)*/`，又叠加循环补斜杠 | 要求**至少一层**子目录，`src/config.ts` 匹配不上 |
| ② | 「上一段是 `**` 就不补斜杠」 | `src` 与 `**` 之间那个斜杠丢了，**全都匹配不上** |
| ③ | 分隔符补在 `**` 分支之后 | `src/**` 正常了，`src/**/*.ts` 又全不中 |

三次都是**我盯着 `.source` 数斜杠**，而 `new RegExp` 的 `.source`
会对 `/` 补反斜杠——数出来的是 `\/`，肉眼极容易多数或少数一个。
所以现在测试里的断言**一律用 `test()`**，不碰 `.source`，
并且拿**真实文件树**交叉验证（手写的期望值可以跟实现一起错）。

那个 glob 正好写在知识页的示例里——**金标全绿、功能是坏的**，
本仓库最防的那类 bug，这次踩在自己身上。

### 负向验证抓到一个真缺陷

第一轮注入「把表改回『计划中』但不改声明」时，**检查没红**。
原因：`evaluateClaims` 收到的是**整个文件**，而 `stated` 的字符串
**在 frontmatter 里它自己那一行就有**——**声明在验证自己的字符串**。
改成只喂正文之后，注入立刻变红。

另外两轮注入（改文件路径、反转 `expect`）都正常变红。

### 未决

1. **只有 1 个知识页有 `verify:` 声明。** 其余 5 页还没写——
   而写声明要先把页面里的可证伪说法找出来，那是一次内容审阅。
2. **它只查「文件在不在」，查不了「写对了吗」。** 一条声明能覆盖的范围
   恰好就是「有没有」这个层级，写清楚比写宽重要。
3. `globToRegExp` 的 `**` 只支持「零个或多个目录」这一种语义，
   没有 `**` 出现在段中间的形态（如 `a/**/b/**/c`）的测试——

## 2026-09-23 · 迭代 B：统一解析与身份（三处）

**动机**：路线图阶段 1 的四件事——「唯一的解析器」「内容图与导出扫描统一」

### ① frontmatter 有两套解析，且第二套会静默解析错

`remark-wikilink.ts` 里有一个**手写的 YAML 子集解析器**（注释写着
「简单键值，不需要完整解析」），只服务于 `[[链接]]` 的查找表。

与真实 YAML 逐例比对：**12 个边界用例，6 个分歧**（块标量 `|` `>`、

现有内容一条都不触发（11 文件 × 6 字段 = 66 次比对，0 分歧）——
所以是**潜在风险**，而下一位作者写 `title: >` 就会静默踩中。

**第一版修法是错的。** 改成越界就抛，清缓存后注入 `title: >`：

    错误打印 22 次；页面退化（链接 4→3）；Build exit code: 0

**在 remark 管道里抛错，Astro 不会让构建失败**——那比"链接静默指错"更糟。
正解是挪到 `astro.config.mjs` 的**加载期**：什么都不渲染，抛出去就是构建失败。
同一个注入现在 exit 1、指出文件与字段、一个页面都没渲染。

### ② 同名标题按遍历顺序任选一个

`buildGraph` 与 `buildLookup` 都是 `if (!has(title)) set(title, slug)`。
调换输入顺序，同一个 `[[Shared]]` 分别指向 a 和 b，而**两次 lint 都是 0 错误**。

改成「同名就不注册」：用了歧义标题 → error 并列出全部候选；
存在但没被引用 → warn。两处查找表行为一致，不会再各算各的。
端到端验证：把一页标题改成另一页的，构建 exit 1、6 条 `ambiguous-wikilink`。

## 2026-09-23 · 阶段 0 收口：估算 vs 实测、活链接、一条核不掉的引用

**动机**：路线图阶段 0 的退出条件里有三项上一轮没做完——
估算 token 的表述、W3C 固定版本、以及那六项事实问题中的 Ahrefs 一条。

### 来源与版本

| 来源 | 版本 | 用于 |
|---|---|---|
| `tiktoken`（`o200k_base`） | 本地安装，2026-09-23 | 真实 token 用量对照 |

### 改了什么

**① 估算被当成了实测。** 站点自己的「token 节省率」用的是
`estimateTokens`——一个刻意可解释的启发式（CJK 1 字 1 token、其余 4 字符 1 token），
而 README 与文档写的是「Measured saving」「实测」「真实数字」。

2026-09-23 装 `tiktoken` 用 `o200k_base` 逐页复算：

| 页面 | HTML 估算 / 真实 | MD 估算 / 真实 | 节省 估算 / 真实 |
|---|---:|---:|---:|
| /markdown-for-agents/ | 6,214 / 6,902（−10.0%） | 2,390 / 2,413（−1.0%） | 61.5% / **65.0%** |
| /cjk-web-typography/ | 7,614 / 8,876（−14.2%） | 2,962 / 3,201（−7.5%） | 61.1% / **63.9%** |
| /wiki/content-negotiation/ | 3,681 / 3,963（−7.1%） | 1,106 / 1,103（+0.3%） | 70.0% / **72.2%** |

**② 那个函数的注释在说反话。** `estimateTokens` 的注释写着
「宁可偏保守（**高估**），也不要让 agent 以为塞得下」——实测它**一直在低估**
（HTML 侧稳定偏低 7–14%），也就是它声称要避免的那一侧。
成因是中文：真实词表会把常见双字词合成一个 token，而「1 字 1 token」把它们各算一个。

**③ W3C 链接是活链接。** `/TR/css-values-4/` 会随规范修订移动，半年后回看
不知道引的是哪一版。已换成带日期的固定 URL（W3C 自己推荐的引用方式）：
`/TR/2024/WD-css-values-4-20240312/`、`/TR/2026/WD-css-fonts-4-20260913/`，
三处逐个 HTTP 200 验过。共替换 14 处。

**④ 一条核不掉的引用，删掉。** 原文写「Ahrefs 2026 年 5 月实测 **137,210 个域名：
97% 的 llms.txt 从未被请求过**」。核实过程：

**查不到就不留着**——精确到个位数、读者却无从核对，只会因为"看起来很硬"被转引。
换成能点开的 Google 原文（且措辞更准：原文是「**不需要**」，不是「不支持」）。

### 未决问题

1. **`estimateTokens` 要不要改成真的保守？** 现在没改——没有证据表明有消费方
   依赖 `x-markdown-tokens` 做硬约束，而改它就会动到对外行为。先记录，

## 2026-09-22 · M0：中文排版的一组算式与归因错误

**动机**：同一组结论散在 6 个载体里，其中两处论证是错的，而现有的检查
（lint / 196 项契约 / 272 项单测）**全都测不到**——它们检查结构，不检查事实。

### 来源与版本

| 来源 | 固定版本 | 用于 |
|---|---|---|
| [CSS Values and Units Level 4 §ch](https://www.w3.org/TR/2024/WD-css-values-4-20240312/#ch) | W3C Working Draft, 12 March 2024 | `ch` 的定义 |
| [CSS Fonts Module Level 4](https://www.w3.org/TR/2026/WD-css-fonts-4-20260913/#font-style-matching) | W3C Working Draft, 13 September 2026 | 字重匹配（§2.2.2）与伪合成开关 |
| [RFC 9110 §12.5.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-12.5.1) | RFC 9110（STD 97） | Accept 的优先级规则 |
| [Karpathy 的 llm-wiki gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) | gist，2026-04 | 模式定位 |

取固定的带日期 URL 而不是 `/TR/xxx/`：后者是"最新版"，会随规范修订移动，
半年后回看不知道当时引的是哪一版。

### 影响清单

**方案里列了 4 处载体，实际是 6 处。** 漏掉的两处是靠全库检索才发现的：

| 4 | `src/styles/tokens.css` 注释 | 行宽算错 | 改写 |

另有第 7 处不是排版而是归因：`src/lib/negotiate/accept.ts` 的文档注释
**把平局规则列在「依据 RFC」之下**——内容协商那篇文章的错误就是从这儿来的。
只改文章不改这里，就是"同一个事实有几个表面、只改一处等于没改"。

### 改了什么

**行宽（算错 + 结论错）**

原话：「一个汉字大约等于两个 `ch`。所以按 66ch 排中文，每行会排出约 130 个汉字
——远超出中文舒适的 30 到 40 字。」

- 按它自己的前提应当**除以 2 得 33**，而不是乘以 2 得 130；
- 33 本来就落在它自己说的 30–40 里，所以「远超」也不成立；
- 被这句话遮住的事实：**66ch ≈ 33em，与本题采用的 34em 宽度几乎相同**。
  这个改动换的是**单位的可预测性**（`em` 等于字号、与字体无关），不是行宽。

**字重（归因错）**

原话：「写 `font-weight: 600` 时浏览器找不到 600，就伪合成一个……正确做法：标题字重写 500。」

- 伪合成的开关是 `font-synthesis-weight`，**不是字重数值**；
  写一个字体没有的字重时，规范要求的是**去找最接近的真实字重**；
- 本站 `base.css` 关掉合成后标题用 600：拉丁拿到 Archivo 的真实 600，
  中文落到 700。**写 500 反而会让中文掉到 400**——比 600 更糟。
- 顺带：`base.css` 的注释里**早就把对的写下来了**，是文章没跟上。

**规范归因**

内容协商那篇原先写「这时按 RFC 的规定，服务端应当认为靠前的那个优先」。
RFC 9110 §12.5.1 规定的是按**具体程度**排优先级，对 q 值相同的只说是
*equally preferred*，**没有给顺序**。所以「并列时靠前优先」是本地策略，
已在文章与 `accept.ts` 注释里都改成这个说法。

**llm-wiki.md**

- posts 原被列为「不可变的输入」，但它们**会被修订**（这篇记录本身就是证据）；
- 「RAG 永不改变、永不连接」太绝对——GraphRAG 就会组织关系与预计算摘要；
- 「一份来源可能改动 10 到 15 个页面」**没有出处**，标注为未核实；
- 补了 gist 的**真实链接**（原先只有文字，`grep -c gist.github.com` 是 0）；
- 补一张「已实现 / 计划实现」表——此前通篇以"本项目怎么做"的口吻描述，
  读者分不清哪些是真的、哪些是打算做的。

### 未决问题

1. **Ahrefs 那 97% 的引用没有可点开的来源。** 试过几种 ahrefs.com/blog 路径都是 404。
   已在文章里标注「待核验，不要转引」。要么找到确切地址，要么撤掉该句。
2. **「1 汉字 ≈ 2ch」仍是粗估。** 严格值取决于字体，本轮没有对每个候选字体实测。
   文章已改成"粗估"措辞，但没有给出实测表。
3. **跨平台字重结论未实测。** 「苹方/微软雅黑只有 400 与 700」来自 `base.css` 的既有注释，
   本轮**没有**在这些系统上实测渲染结果。文章已避免声称跨平台实测结论。
4. **`ch` 在几个候选字体下的真实宽度没有测量**，所以「66ch ≈ 33em」是推算而非实测。
