# 门禁的负向验证记录

**每条门禁都记着：它被弄坏过吗？红了没有？**

## 为什么要有这份文件

「这个检查有效吗」这个问题，**光看它绿着无法回答**——
一个永远绿的检查和一个真在守的检查，在正常运行时长得一模一样。

本项目已经吃过好几次同族亏：

- `verify:search` 三项全绿，而它只查「全站 lang 一致」不查「lang 正确」；
- 刚加的「站内 JS 体积」门禁**永远量到 0**（`check-formats` 不跑 pagefind）；
- locator 检查只比章节号，`ch` 与 `ic` 同在 §5.1.1，于是 `ic` 没登记也放过。

**共同点：它们都绿过，而绿是它们没在工作的证据。**

## 怎么读这份表

- **验过 = 我真的注入过故障，并确认它变红。** 不是「理论上会红」。
- 没验过的行写「**未验**」——那不是缺陷，是**已知的空白**。
- 日期是注入的日期，不是脚本的日期。

## 同一个字段的两个真值：`readContentDirs` 重算了一遍（2026-09-28）

`readContentDirs` 把 `summary` / `original` / `slug` / `date` / `tags`
**全部重算了一遍**——而 `readContentPage` 也在算。

**那不是「无害的保险」，是同一个字段有两个真值**：改一处，另一处悄悄不同。
`check:field-coverage` 抓到它的后果时，差异恰好是**两个方向各缺一半**
（`summary` / `original` 只在单读有，而多处读取那里补的是另两个）。

处置：`readContentPage` 读全，`readContentDirs` **只做它做不到的事**
（`relationField` 换字段名、`docKind` 带站点事实）；
并在 `check:two-paths` 加第 5 条「单读与多读对同一页逐字段一致」
（拿**本站真实内容**比 11 页，而不是临时固件——真实内容里那些**没写的字段**
才是分歧高发处，`undefined` / `''` / 键不存在，三种都「看起来对」）。

> 那条「只做做不到的事」很容易在下次重构时又长回来，
> 所以**把「两条路逐字段相同」变成门禁**，而不是靠代码整洁。

⚠️ **探针第一版把前两类报成「没有」**——判据是「该门禁的脚本文件名

那是形态十一的反向：**「没查到」≠「不存在」**，而方向恰好与
`check:questions.mjs` 注释里记的那个坑相反。
**一个探针也会骗人，所以探针的结论在被采信之前必须自己核一遍。**

### 20 道里挑一道去验，抓到**一处真 bug**（2026-09-28 收尾）

挑 `check:onboarding-doc`（「文档里的实测数字与现在跑出来的一致」）。
它写得很扎实——语料非空断言、判据从文档表格里**解析**而不是抄常量。
三条变异全部被抓（断链数 3→7、lint 条数 10→13、正文里写不存在的命令）。

**但第三条本不该需要**：我去找锚点时才发现，那份文档里有两处
`npm run check:portability`，**而 `package.json` 里没有这个脚本**
（真名是 `verify:portability`——**这正是本文件前面记过的那个坑，
在同一份文档里又出现了一次**）。

> **读者会照着敲**，而它躲在白名单外。

**根因是白名单写错了形状。** 原来的取舍是：

> 只核 `docs/cli.md` 与 `README.md`——正文里举例写的 `npm run xxx`
> 可能在讲「假如有这样一个命令」，不判。

那是**按文件豁免一类通病**。「文档里的命令名会漂」是**通例**，
不是「只有那两份会漂」；而 `onboarding-a-new-site.md` 里那两处**不是举例**，
是**行内引用一个真实存在的门禁**，所以假设不成立。

**改成按位置排除**：围栏代码块（``` ）里的一律不核（那里确实可能在举例），
**其余每一处 `npm run <名字>` 都要有定义**。变异实测会红。

> **白名单是「我不打算核」的意思。**
> 写白名单之前先问：**这是「这份文件特殊」，还是「这类情况特殊」？**
> 答错的话，豁免会静默扩大——**而且不会有人发现，因为豁免的正是检查本身。**
>
> 同一条：那份文档的同一段话（解释「为什么是这四个模块」）**逐字出现了两次**，
> 一次在代码块内、一次在代码块外——`check:no-duplicate-lists` 量不到它，
> 因为它量的不是数组字面量。**每道门禁的盲区都写在它的注释里，
> 而「都写在注释里」不等于「有人会去看」。**

### 顺手核了另外三道文档类门禁：白名单只有那一处（2026-09-28 收尾）

改完就把同一类问题在别处找了一遍——**因为「一处是缺陷」与「一处是通例」
的处置完全不同**，而这个区别只能靠核，不能靠猜。

| 门禁 | 它有没有白名单 | 核的结果 |
|---|---|---|
| `check-doc-refs` | 有（产物路径 / URL 路径 / 源码路径三类分开） | **有理由**——「`/content-manifest.json` 是站点路径不是文件」，写得出理由 |

## 「决定所有门禁在不在」的那道门禁，自己没人守（2026-09-28 收尾）

`check:gate-list`（`verify:gates`）是 `verify:all` 的**第 2 步**，
而探针把它归在「20 道没有负向验证」里。**一道决定「所有门禁都在不在」的门禁，
自己没有任何东西证明它会红** —— 这比单个门禁失效更值得查。

它是 479 行、**20 条判据**，逐条注入：README 步数改成错的 → 红；
豁免理由引用的文件不存在 → 红；理由变成散文 → 红。

### 第 4 条判据是坏的，而且它坏在**自己记着的那个教训上**（2026-09-28 收尾）

前三条判据把「第 \d+ 步」算作**可验证的引用**。于是往理由里塞一句
「见 verify:all 的第 999 步」——**格式合法、指向一个不存在的步骤**——
门禁**照样绿**（实测）。

而讽刺的是：**`verify:only` 那条豁免当初真的就是栽在这里**。
它的理由写「被 verify:all 的第 3 步调用」，而第 3 步早就是 `npm test`。
门禁在自己的注释里**记着这个教训**，却只挡住了「没有引用」，
**没挡住「引用了一个已经漂掉的步骤号」**。

> **判据只认「格式像不像引用」，不认「引用还成不成立」**——
> 与 ①②（命令要真存在、文件要真存在）相比，它只做了一半。
> 而那**恰恰是它自己的注释里写着要防的那一半**。

修法要处理一个反向问题：`verify:only` 的理由里那句「**而**第 3 步现在是
`npm test`」是**被否定的历史陈述**，它的「第 3 步」不是「我指向第 3 步」。
所以判据靠**紧邻的词**分两种读法：否定式（`而第 N 步` / `原为第 N 步` / …）
不判，肯定式必须落在编排范围内。**两种都实测过。**

⚠️ **「靠一个词区分」是脆弱的，这是已知代价**，已写进门禁注释：
真正的替代是「理由改用结构化字段」，而那会把这个表从可读的注释变成配置。
**判据太宽会漏、太严会逼人绕开 —— 选一个错的代价更小的，然后写明代价。**

|---|---|---|---|
| ① | 守卫：`skip` 不是字符串就报错 | — | 没理由的登记**完全静默** |
| ② | 守卫 + `else`（合法跳过） | 守卫 | `{ what: 'x' }` 被打印成 `ℹ …——undefined` 并放行 |

> 只要 `problems.push` 在某个 `if` 里面，

> 打印与记账都只看这份数据。**于是拆掉任何 `if` 都改不了「结论是什么」。**

> ⚠️ 这**不防**「把整段分析删掉」——那任何门禁都防不住。

> 它没发作**只因为没有变异以它为 target**，**那是埋着的雷**。一并改了。

> **判据：任何 `spawnSync` 的结果，先看 `r.error` 再看 `r.status`。**
> `status: null` **不是**「退出码 0」也不是「非 0」，它是**「没拿到」**——
> **而「没拿到」被当成「非 0」时，一条环境问题会伪装成 34 条门禁失败。**

## 第三列「含义」：11 条里只有 5 条能机械核，而核不了的要写明（2026-09-28 收尾）

那张表三列都核完之后，最后一块是**第三列「含义」** —— 唯一一列**写给人看的**
（「agent 照着它理解每条规则到底在做什么」）。

**11 条里只有 5 条能机械核**（其余 6 条描述的是**机制**，而机制由
`check:field-coverage` 在字段层核过）。5 条全部成立：

| 规则 | 可核的断言 | 怎么核 |
|---|---|---|
| `cjk-slug` | 「**默认关闭**，可在配置里开」 | 默认跑一次不报、开选项跑一次报 |
| `orphan-page` | 「**没有任何页面指向它**」 | 有入链的不在 `orphans` 里、没入链的在 |
| `empty-body` | 「没写完就加 `draft: true`」 | 加了草稿标记就不再报 |
| `summary-too-long` | 「摘要过长」 | 恰好 200 字不报、201 字报 |
| `ambiguous-title` | 「**还没有人引用它**」 | 被引用后改报 `ambiguous-wikilink` |

> **核不了的那 5 条必须显式列在输出里**——
> 否则「核了 5 条」会被读成「11 条都核了」。那正是今天第三次记的形态
> （「扫到 0 处」被读成「通过」）。

### `orphan-page` 那条第一次红了，而**规则完全正确**（2026-09-28）

我第一版断言「整份语料不该报 `orphan-page`」——**错得很有代表性**：
语料只有 2 篇，而**入口那篇自己没有任何入链**，所以它**必然是孤儿**、
必然被报（`orphans` 实测就是 `["入口"]`）。

正解是断言**「被链那篇不在 `orphans` 里」且「入口那篇在」** ——
两条都断言，才能证明「有没有入链」真的决定了报不报。

> **这是 2026-09-28 第四次「我以为对不上，其实量错了东西」**：
> 前三次是「注释量 HTML 侧而 docs 量 MD 侧」、「静态分析只捞到 1 条」、
> 「探针正则漏了『检查了 N 个』」。**四次里有三次的错都在我的尺子上。**

### 第三列第一版只核行为，把文档反过来说它照样绿（2026-09-28）

`cjk-slug` 那条我第一版只核「默认下报不报」。于是把文档里的「默认关闭」
改成「**默认开启**」（**而实现一行没动**），门禁**照样绿** ——
**行为对、文档错，判据无感**。

> 与形态十一同源：**核的是「实现是什么」，声称要核的是「文档说了什么」。**
> 而这一列的每个说法都是可判真假的——**只要把它从文档里读出来再比**。

改成从 `AGENTS.md` 那一行**解析出「默认开/关」**再与实测比，变异立刻被抓住。

⚠️ 顺带发现我**自己加的一个条件恒假**：
`actuallyOff`（「默认**不**报」）与 `actuallyOn`（「**开选项后**报」）
**本来就是两个都 true**（「默认不报」与「开选项会报」并不矛盾），
而我把「两句话」当成「一对互斥取值」来比 —— **干净态就红了**。
核它要两件独立的事：① 文档说的默认行为与实测一致 ② **那个选项真能打开它**。

### 顺带：`ensureDist` 修不了「并发」，而那不是它的锅（2026-09-28）

把「`dist` 在不在」改成「清单里点名的每个 `.md` 都在 `dist` 里」之后，
那两条 `verify:negotiation` 的红**仍然出现**，而它打出的诊断是
**`⚠ build 失败，下面依赖产物的门禁结果不可信（那不是变异造成的）`** ——
**那条诊断按预期救了场**（它把「环境」与「我的错」分开了）。

单独跑 `npm run build` **成功**，所以是 `mutate()` 内部那次失败：
`ensureDist()` 判定不一致 → build，而 **build 自己会 `clean`** ——
**若此时有另一个进程在读 `dist`，就会读到中间态**。

**这不是 `ensureDist` 能修的**：`docs/cli.md` 里写明那几道门禁
**必须串行**（`verify:base` 清空 `dist`、`verify:formats` 往里塞探针），
**而并发正是它要防的事**。记在此处，**不在这一轮硬修**——
**修它要先解决编排的串行保证，那比这一轮大**。

## 静态分析量不出「级别」——只能真跑，而真跑要造三件事（2026-09-28 收尾）

补了「规则集相等」之后，表上**第二列（级别）一条都没核** ——
而「`broken-wikilink` 是 error（会让构建失败）」正是 **agent 最会照着用的那一列**。

**先试静态分析，不可靠**：`level:` 散在各规则函数内部，
「从 `rule:` 往上找 12 行」只捞到 **1/11** 条（与 `check:field-coverage`
那次「字面匹配三次自己失败」同族）。**级别是运行期属性，只能跑出来。**

真跑之后发现造语料要满足三件事，**每一条都是撞上去才知道的**：

| # | 坑 | 症状 |
|---|---|---|
| ① | **必须跑两轮**（`docKind: 'post'` + wiki） | `post` 那轮 `orphan-page`/`redundant-relation` 不报，wiki 那轮 `reserved-post-slug` 不报。**只跑一轮 7/11**，我一度以为是「语料不对」 |
| ② | **同名标题要造两对** | 被引用的报 `ambiguous-wikilink`、没人引用的报 `ambiguous-title`。**只有一对时后者被盖掉** |
| ③ | **两个「同名但不同」别搞混** | `duplicate-slug` 是 **slug 同、标题不同**；`ambiguous-*` 是**标题同、slug 不同**。我第一次造反了，只触发到后者 |

还有一处：`summary-too-long` 的语料**不能走那个 `page()` 助手** ——
助手会再写一个 `summary:`，**后者覆盖前者**，于是那条永远不触发。

> **每一条的共同点：「结果少了几条」被我读成「实现有问题」，
> 而真相是「我量错了东西」。** 这是今天记了一整天的形态第三次现身。
> **判据：结果与预期不符时，先查是不是量错了东西，再改实现。**

新门禁 `check:rule-levels`，语料触发 11/11，**逐条与文档声称一致**；
并加了一条「**语料没触发到的规则必须报**」——「没触发」与「都对」在结果上无法区分。

### 顺带把 `ensureDist` 的判据修对了（2026-09-28）

`mutate()` 跑「恢复后仍红」那一步时，`verify-negotiation` 报
「`markdown-for-agents.md` 存在于产物中」——**而那个文件当下并不存在**。

第一版 `ensureDist()` 只查 `dist/content-manifest.json` **在不在**：
那挡住了「没有产物」，**挡不住「产物在、但是上一次门禁留下的旧的那份」**。

> **「产物在」与「产物对得上现在的源码」是两件事**，
> 而第一版把前者当成了后者的**充分条件**。

改成：清单里点名的每个 `.md` 是否真的在 `dist` 里。

⚠️ **但要诚实说清一件事**：改完之后我立刻重跑，34/34 全绿——
**而那两条红在我手动 `npm run build` 过一次之后就不再出现了**。
所以**我无法区分「修法有效」与「只是 dist 那次恰好是好的」**。
唯一的证据是 `build` 本身要一分多钟，而 `mutate()` 每条变异跑两次门禁——
**34 条里两次 build 就是好几分钟**，而那两条红正出现在 build 还没跑完时。
**这个不确定性没有消除，只是缩小了。**

## 「文档里说的还对吗」与「文档该说的都说了吗」是两个方向（2026-09-28 收尾）

顺着「第三件事」（文档与门禁之间没有「哪几条被核了」的对照表）去读 `AGENTS.md`。
13 个小节，`check:agents-doc` 核 4 组。**第五个规则小节没被它核**——
但那不是漏核，是**那道声明的判据在别处**（`check:staged` 守着
「验证通过之后、提交之前」那节）。

**真正的缺口在另一处**：`AGENTS.md` 有一张「**每次构建会跑体检**」的表，
写着「分三级」、列了 9 条规则 —— 而 `lint.ts` 里有 **11 条**。

| 缺的两条 | 级别 | 在哪出现过 |
|---|---|---|
| `ambiguous-wikilink` | **error**（会让构建失败） | 只有 `knowledge/fixtures/README.md`（测试语料说明） |
| `ambiguous-title` | warn | 同上 |

> **漏掉的是 error 级那条。** 而这张表是 **agent 照着判断「什么会让构建失败」的地方**
> ——`AGENTS.md` 开头就写着「那是**给 agent 读的约定**」。

> 而**缺的项永远不会触发「这一句还对吗」**。
> 所以「全部通过」与「漏了一条」**可以同时成立**。
>
> 与形态四同源但方向相反：那一条是「集合空了还说通过」，
> 这一条是「**集合没满也说通过**」。

### 「绿色」这个输出有**两种**含义，而它们长得一模一样（2026-09-28 收尾）

做 `check:no-duplicate-lists` 时，连栽**两次**，而且两次都是同一个形状：

| # | 我看到的 | 我差点读成 | 真相 |
|---|---|---|---|
| 1 | 注入「跨行的重复清单」后门禁仍绿 | 「判据漏了跨行」 | **注入压根没写进去**——锚点 `export interface ReadPage` 在 `read-page.ts` 里不存在，`String.replace` 找不到就原样返回 |
| 2 | 往 `read-page.ts` 注入后门禁仍绿 | 同上 | 注入只写了**一份**清单——**一个重复本来就该是绿** |

> **「绿」既可能是「它没看见」，也可能是「压根没被喂进去」。**
> 而这两种的输出**完全一样**。
>
> 这是「它报了 ≠ 它判了」那条的**反面**：那条讲「报了不代表判了」，
> 这条讲**「没报也分不清是没看见、还是没被喂进去」**。
> 所以**每次注入都必须自证注入成功**——
> `new-gates.mutations.mjs` 的 `mutate()` 现在写回之后立刻
> **比对文件是否真的变了**，没变就报「注入无效，本条结论不可用」。
>
> 顺带一条更老的同族教训：**查锚点存不存在，比跑一次变异便宜得多**。
> 我是先跑变异（绿）才去 grep 锚点的，顺序反了。

### 判据自己也得先被验一遍（2026-09-28 收尾）

`check:no-duplicate-lists` 写完先跑自测（5 条**临时副本**，
写进 `.verify/no-dup-lists/`，**不碰真源码**），**当场抓到一条真盲区**：

> 归一化用 `\s+`（吃掉**全部**空白），而元素切分按 `,`（**保留**元素内首尾空白）。
> 于是 `['x', 'y']` 与 `['x','y']` 归一化后**不等**——本该判为「逐字相同」的
> 两种排版被判成两个不同的清单。

修法是**先切分去空白、再拼**：`items.map(s => s.replace(/\s+/g,'')).join(',')`。

> 这条盲区**是靠自测抓到的，不是靠变异**——
> 变异验证的粒度是「缺陷注入后门禁会不会红」，
> 而**根本没注入成功的变异**（上表第 1 条）**恰好被这条覆盖不到**。
> 两种验证手段量的是不同的东西，缺一不可。

### 覆盖率会被悄悄收窄，而输出一个字都不变（2026-09-28 收尾）

`check-no-duplicate-lists` 的 `ROOT_DIRS = ['scripts','src']`
是个**决定覆盖面**的字面量——把它改成 `['src']`，
「0 处重复」这个结论**一个字都不会变**，因为 `src/` 里确实没有重复。

所以补了一条**实测下限**：`scripts/` ≥ 54 个文件、`src/` ≥ 70 个
（这两个数是**实跑得到**的——第一版我凭印象写 `100 / 5`，
门禁立刻报 scripts 只有 54 个，**尺子自己先量错了**）。

> **下限定的是下限，往上不红**——仓库会长，钉住上限就会天天误报。
> 这是形态五「被测集合是空的」的变体：
> **不是集合空了，是集合被人改小了，而报告没跟着改。**

### 「同一份清单写两遍」这一天栽了四次，第四次成了门禁

| # | 清单 | 漏在哪 | 处置 |
|---|---|---|---|
| 1 | `check-portability` 的 `CORE` | 手写 8 个，**漏了 5 个** | 改成从文件系统推导 |
| 2 | `check-exit-codes` 的 `USER_CLIS` | 手写 4 个，**漏了 3 个** | 改成从文件系统推导 |
| 3 | `check-gate-list` 的 `NOT_IN_ALL` ↔ 变异脚本的 `file` 值 | 改了 A 忘了改 B | 当场手工同步 |
| 4 | `new-gates.mutations.mjs` 的 `GATES` ↔ 干净态检查的数组 | 加了第 5 道忘了同步 | 当场手工同步 + **这次加了机械检查** |

前两次的结论是「手写名单必然漏」，于是改成推导；后两次是**「两处字面量要手工同步」**——
那是推导解决不了的，只能机械拦住。所以有了 `check:no-duplicate-lists`：
**同一文件里内容逐字相同、且 ≥2 元素的 `const X = [...]` 出现两次就红。**

⚠️ 它的**边界必须写清楚**，否则下一个用它的人会高估它：

- ⚠️ **它量「字面量重复」，量不到「逻辑重复」**——后者要读懂每个函数；
- ⚠️ **它排除 `*.test.ts` / `*.mutations.mjs`**——那些是造固件的，
  `const pages = [makePage(), makePage()]` 两份**是巧合不是清单**
  （不排除时 26 处 → 排除后 0 处，26 : 3 的比例就是「判据太宽就变成噪声」）；
- ⚠️ **只报「逐字相同」的**——同名不同内容是两个碰巧同名的清单，不一定是错。

### 「量到了盲区大小」比「再加一道门禁」更该先做（2026-09-28 收尾）

`check:no-duplicate-lists` 写完、验完、接进编排之后，我**第一件事是量它还漏什么**，
而不是继续加规则。一次探针（跑完即删的临时脚本）的结果：

> 126 个文件里 **56 份不同的清单，其中跨文件重复的只有 1 份**——
> 而那 1 份还是这道门禁**自己刚写进去的** `['scripts','src']`。

两处收窄因此是**有数据支撑的**：

1. **跨文件那份**收敛成 `scripts/lib/source-dirs.mjs` 的 `SOURCE_DIRS`
   （`check-portability` 的 `PROD_CALLERS` 与 `check-no-duplicate-lists` 的
   `ROOT_DIRS` 本来就是同一个事实）；
2. **不再加跨文件判据**——1/56 的比例，加一道门禁去守它不值；
   而门禁的注释里写明了这个边界，免得下一个用它的人高估它。

⚠️ **同时纠正了一个我自己的误判**：我原以为「今天四次里的前两次
（`CORE` 漏 5 个、`USER_CLIS` 漏 3 个）本门禁也抓不到」。
**那是错的**——手写 8 个、实际 13 个，手写那份是**子集而不是副本**，
而**子集根本不是「重复」**。那两次的形态是「名单没从数据源推导」，
本门禁对它们**从来就没有任何覆盖**，现在写进注释了。
**高估一把尺子比低估它更危险**：以为漏了会去补（其实没什么可补），
以为够了就再也不会有人看它。

### 一道门禁会**把自己的锚点改没**——而那正是它该被抓住的时刻（2026-09-28 收尾）

收敛 `ROOT_DIRS` 之后，`new-gates.mutations.mjs` 里那条变异的锚点
（`const ROOT_DIRS = ['scripts','src'];`）就不存在了，于是全量跑**红了**：

```
✗ 锚点出现 0 次，变异未生效
```

这条红**是那个半小时前刚加的自检救下来的**。没有它，同一个情形会被读成
「`check:no-duplicate-lists` 对收窄覆盖没反应，判据有盲区」，
然后**为了迁就一个已经失效的锚点，去把刚收敛掉的东西重新拆开**。

> **负向验证脚本自己也是需要维护的代码**，而它腐化的方式很隐蔽：
> **重构会让它的锚点指向不存在的东西，而它的失败信息读起来像「被判据有盲区」。**
>
> 所以「锚点出现 N 次」必须是一条**独立的、自证的**失败分支——
> 它说的是「**本条变异不成立**」，而**不是**「被测门禁有问题」。
> 这两种混在一起，就会有人去修错的对象。

## 「同一件事两处实现」——2026-09-28 一天内的第四处

### 一次**误报**，以及它与真缺口的区别

同一个下午我用同一个方法（「系统性对比」）做了两件事：

| | 声称的缺口 | 实际 |
|---|---|---|
| ✅ | `docs/cli.md` 写着 `npm run check:portability`，而真实名字是 `verify:portability` | **真缺口**——照着敲得到 `Missing script` |
| ❌ | `README.md` 指向 `docs/cli.md#搜索的加载器…` 的锚点「不存在」 | **误报**——那个标题真实存在（`##` 级，不是 `###`，我 grep 时只查了 `^###`） |

两者用的是同一套推理，**结果一真一假**。分它们的不是方法，是**有没有真的去核**：

- 真缺口那条，我跑了 `package.json` 确认 `check:portability` 不存在；
- 误报那条，我**只跑了 `grep '^###.*搜索的加载器'`**（0 命中）就下了结论，
  **没去看它是不是别的标题层级**。

> **「grep 没命中」与「它不存在」之间隔着一个「grep 的模式对不对」。**
> 而我今天已经栽在这上面一次：查平台依赖时用
> `grep -lE "\\\\\\\\|/tmp|chmod"`，那个 `\\\\` 匹配的是**任何**反斜杠或 `/`，
> 于是**所有文件都命中**——我据此说"有平台风险"，其实全都不是。
>
> **两次的共同点：把「我的查询没找到」当成「它不存在」。**
> 与 [[local_simulation_missing_semantics]] 的「查不动 ≠ 空集」是同一条，
> 只是方向相反——那条是**没查到就说没有**，这条是**没查到就说坏**。

### 为什么这一天能找到四处

**因为改用「系统性对比」而不是「零散发现」。**

2026-09-28 前半段我一直在**逐个字段**地看（`original` 有没有读？`draft` 有没有读？），

> 「同一件事两处实现」这个形态，于是用一条 grep 找到第 4 处。

## 读路径与构建路径的「post 口径」曾经三处分歧（2026-09-28）

本仓库有**两条**从内容到 `Doc` 的路：构建期 `src/lib/content.ts` 的 `toDoc`
（拿 `astro:content`），与读源码 `readContentDirs` + `pageToDoc`（裸 Node，供 `scripts/*.mjs`）。
**它们必须给出同一个 `Doc`**，否则同一页在构建产物与 CLI 回答里形状不同，
而 `wiki:ask` 的 `docId` 正是订阅者做增量同步的键。

`content.ts` 里有 **4 处** `kind === 'wiki' ? … : …`（`related` / `review` /
`original` / `wikiKind`），而 `pageToDoc` 起初**一处都没对齐**。

**为什么一直没发作**：本站 posts 里 **0 篇**写这些字段（实测无 `^related:`、无 `^kind:`）。

> **「本站没有这种数据」与「这条路径正确」是两件事**——
> 前者让后者从未被测过，而两者在输出里长得一样。

修完三处，并加 `check:two-paths` 门禁：数构建侧有几处判定当基准，
**真跑** `pageToDoc` 两种 `docKind` 逐项断言（不 grep 两边源码有没有同样的字符串——
写法可以完全不同，**行为一致才是契约**）。

⚠️ 加 `post` 那一侧时踩过一次「键在、值是 `undefined`」：
`{ a: undefined }` 与省略键在 `doc.a` 上一样，但 `Object.keys()` 与
`JSON.stringify` 不同——而 `content-manifest` 正是把 `Doc` 序列化出去的。
所以 `post` 侧是**整个键都不出现**。

⚠️ 同日还发现：给 `knowledge-gates` 的摘要加门禁时，我加了第 14 道却忘了改
写死的 `/ 13`，它打印「通过 14 / 13」。**与「少一步不会有任何报错」同家族**，
已改成从步骤列表自己数（`total="$(printf '%s\n' "$steps" | grep -c .)"`）。

### 一条**被我夸大过、后来实测推翻**的说法（2026-09-28）

我在 `page-to-doc.ts` 的注释里写过：「`post` 侧的键整个不出现，而不是给
`undefined`——因为 `JSON.stringify` 会不同，manifest 会不一致」。

**实测：两边序列化后逐字节相同。** `JSON.stringify` 会丢掉值为 `undefined`
的属性，所以「键在、值 undefined」与「键不出现」**在产物上完全一样**。
差别只在**内存里那个对象**的 `Object.keys()` / `hasOwnProperty`。

已改成实测口径，并加了一条断言把这件事钉住
（`省略键与给 undefined 在 JSON 产物上完全相同——差别只在键集合`）。

> 教训与本文件里那条「本地绿 CI 红」同源：
> **我先写下一个听起来很严重的后果，再去核实它。**
> 而核实只需一行 `JSON.parse(JSON.stringify(x))`。
>
> 顺带说明「为什么要统一写法」这个决定**仍然成立**——
> 但成立的理由是「同一约束散在多处会互为掩护」，
> **不是**「产物会不一致」。理由变了，结论碰巧没变，但那是因为我先做对了收敛。

## `verify:migrate` 靠「别人已经建过目录」而绿（2026-09-28）

2. 靠这一点把 21 道拆成两个 job（纯计算 / 起子进程）→ 定位到子进程组；
   再把 8 道拆成 8 个 step → 定位到 `verify:migrate`；

|---|---|---|
