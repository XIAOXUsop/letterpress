# 门禁的负向验证记录

**每条门禁都记着：它被弄坏过吗？红了没有？**

## 为什么要有这份文件

「这个检查有效吗」这个问题，**光看它绿着无法回答**——
一个永远绿的检查和一个真在守的检查，在正常运行时长得一模一样。

本项目已经吃过好几次同族亏：

- `verify:search` 三项全绿，而它只查「全站 lang 一致」不查「lang 正确」；
- 刚加的「站内 JS 体积」门禁**永远量到 0**（`check-formats` 不跑 pagefind）；
- locator 检查只比章节号，`ch` 与 `ic` 同在 §5.1.1，于是 `ic` 没登记也放过。

**共同点：它们都绿过，而绿是它们没在工作的证据。**

## 怎么读这份表

- **验过 = 我真的注入过故障，并确认它变红。** 不是「理论上会红」。
- 没验过的行写「**未验**」——那不是缺陷，是**已知的空白**。
- 日期是注入的日期，不是脚本的日期。

> 那条「只做做不到的事」很容易在下次重构时又长回来，
> 所以**把「两条路逐字段相同」变成门禁**，而不是靠代码整洁。

## 门禁「没被证明过会红」有多少：量了一次（2026-09-28 收尾）

用一次性探针把 `verify:all` 的 40 步分类（跑完即删）：

| 类别 | 步数 |
|---|---|
| **本身就是负向验证** | 6 |
| **被别的变异脚本覆盖** | 12 |
| **没有负向验证** | 20 |
| 非单文件（`check` / `npm test`，性质不同） | 2 |

⚠️ **探针第一版把前两类报成「没有」**——判据是「该门禁的脚本文件名
出现在某个变异脚本里」，而 `verify:site-mutations` 那些**就是**变异脚本。
那是形态十一的反向：**「没查到」≠「不存在」**，而方向恰好与
`check:questions.mjs` 注释里记的那个坑相反。
**一个探针也会骗人，所以探针的结论在被采信之前必须自己核一遍。**

### 20 道里挑一道去验，抓到**一处真 bug**（2026-09-28 收尾）

挑 `check:onboarding-doc`（「文档里的实测数字与现在跑出来的一致」）。
它写得很扎实——语料非空断言、判据从文档表格里**解析**而不是抄常量。
三条变异全部被抓（断链数 3→7、lint 条数 10→13、正文里写不存在的命令）。

**但第三条本不该需要**：我去找锚点时才发现，那份文档里有两处
`npm run check:portability`，**而 `package.json` 里没有这个脚本**
（真名是 `verify:portability`——**这正是本文件前面记过的那个坑，
在同一份文档里又出现了一次**）。

> **读者会照着敲**，而它躲在白名单外。

**根因是白名单写错了形状。** 原来的取舍是：

> 只核 `docs/cli.md` 与 `README.md`——正文里举例写的 `npm run xxx`
> 可能在讲「假如有这样一个命令」，不判。

那是**按文件豁免一类通病**。「文档里的命令名会漂」是**通例**，
不是「只有那两份会漂」；而 `onboarding-a-new-site.md` 里那两处**不是举例**，
是**行内引用一个真实存在的门禁**，所以假设不成立。

**改成按位置排除**：围栏代码块（``` ）里的一律不核（那里确实可能在举例），
**其余每一处 `npm run <名字>` 都要有定义**。变异实测会红。

> **白名单是「我不打算核」的意思。**
> 写白名单之前先问：**这是「这份文件特殊」，还是「这类情况特殊」？**
> 答错的话，豁免会静默扩大——**而且不会有人发现，因为豁免的正是检查本身。**
>
> 同一条：那份文档的同一段话（解释「为什么是这四个模块」）**逐字出现了两次**，
> 一次在代码块内、一次在代码块外——`check:no-duplicate-lists` 量不到它，
> 因为它量的不是数组字面量。**每道门禁的盲区都写在它的注释里，
> 而「都写在注释里」不等于「有人会去看」。**

### 顺手核了另外三道文档类门禁：白名单只有那一处（2026-09-28 收尾）

改完就把同一类问题在别处找了一遍——**因为「一处是缺陷」与「一处是通例」
的处置完全不同**，而这个区别只能靠核，不能靠猜。

| 门禁 | 它有没有白名单 | 核的结果 |
|---|---|---|
| `check-doc-refs` | 有（产物路径 / URL 路径 / 源码路径三类分开） | **有理由**——「`/content-manifest.json` 是站点路径不是文件」，写得出理由 |
| `check-anchor-links` | 无 | — |
| `check-agents-doc` | 有（「只查三类可机械证伪的声明」） | **有理由且形状正确**——每条声明配一段专属验证代码，**新增一条要手写验证**，那正是刻意的 |

**结论：仓库里「按文件豁免通病」只有 `check:onboarding-doc` 那一处。**

> 所以这一轮真正修的是**一个缺陷**，不是一条通例——
> 而这个区别**不核就说不清**：如果它是通例，处置是加门禁；

⚠️ 核的过程中撞见**另一处同类漂移**，已修（2026-09-28 随后）：

`package.json` 里 `check:refs` 指向的脚本叫 **`check-doc-refs.mjs`**、

## 「决定所有门禁在不在」的那道门禁，自己没人守（2026-09-28 收尾）

`check:gate-list`（`verify:gates`）是 `verify:all` 的**第 2 步**，
而探针把它归在「20 道没有负向验证」里。**一道决定「所有门禁都在不在」的门禁，
自己没有任何东西证明它会红** —— 这比单个门禁失效更值得查。

它是 479 行、**20 条判据**，逐条注入：README 步数改成错的 → 红；
豁免理由引用的文件不存在 → 红；理由变成散文 → 红。

### 第 4 条判据是坏的，而且它坏在**自己记着的那个教训上**（2026-09-28 收尾）

前三条判据把「第 \d+ 步」算作**可验证的引用**。于是往理由里塞一句
「见 verify:all 的第 999 步」——**格式合法、指向一个不存在的步骤**——
门禁**照样绿**（实测）。

而讽刺的是：**`verify:only` 那条豁免当初真的就是栽在这里**。
它的理由写「被 verify:all 的第 3 步调用」，而第 3 步早就是 `npm test`。
门禁在自己的注释里**记着这个教训**，却只挡住了「没有引用」，
**没挡住「引用了一个已经漂掉的步骤号」**。

> **判据只认「格式像不像引用」，不认「引用还成不成立」**——
> 与 ①②（命令要真存在、文件要真存在）相比，它只做了一半。
> 而那**恰恰是它自己的注释里写着要防的那一半**。

修法要处理一个反向问题：`verify:only` 的理由里那句「**而**第 3 步现在是
`npm test`」是**被否定的历史陈述**，它的「第 3 步」不是「我指向第 3 步」。
所以判据靠**紧邻的词**分两种读法：否定式（`而第 N 步` / `原为第 N 步` / …）
不判，肯定式必须落在编排范围内。**两种都实测过。**

⚠️ **「靠一个词区分」是脆弱的，这是已知代价**，已写进门禁注释：
真正的替代是「理由改用结构化字段」，而那会把这个表从可读的注释变成配置。
**判据太宽会漏、太严会逼人绕开 —— 选一个错的代价更小的，然后写明代价。**

## 命令名与脚本名对不上：先量，再决定修不修（2026-09-28 收尾）

一次性探针扫了 63 个单文件命令（2026-09-29 实测；此前记 48），**9 个的命令名与脚本名对不上**——
比我先前凭印象记的 2 处多。逐个看，成因分三类：

| 类型 | 例 | 处置 |
|---|---|---|
| **有意** | `verify:only` → `bundle-and-verify.mjs` | 保留，它表达「只跑契约」这个意图 |
| **前缀差** | `verify:gates` → `check-gate-list.mjs` | 保留，登记 |
| **历史漂移** | `check:anchors` → `check-anchor-links.mjs` | 保留，登记 |
| **同一规律** | `verify:X-mutations` → `X.mutations.mjs`（4 条） | 保留，登记 |

**没有「顺手把文件名改成命令名」。** 那要同时动 `package.json`、CI、文档与
台账里的每一处引用，而收益仅仅是让一种查法好走——**成本低一个数量级的做法是
登记 + 让门禁守住**（`scripts/lib/command-scripts.mjs` + `check:command-scripts.mjs`）。

> ⚠️ **那张册子本身也是「同一份事实写两遍」**（`package.json` 有一份、册子有一份），
> 所以主判据不是「册子对不对」，而是 **「凡是分叉的都必须登记」**——
> 少了它，加一个新分叉命令时**什么都不会报**，而册子的全部价值恰恰是
> 「照着它一定找得到脚本」。

### 三条判据互相掩护，第三条一度看起来是死代码（2026-09-28 收尾）

写完先手工验：① 加一个未登记的分叉命令 → 红；② 册子登记的脚本被改名 → 红；
③ 登记已过时（命令名与脚本名对上了）→ **报的是 ②，不是 ③**。

**因为 ①/③ 都被「逐字一致」挡住了**——而那是**好设计**（第一层就该拦住）。
但它让第三条断言**不可达**，而**死断言会让人以为覆盖了它其实没覆盖的事**
（形态七的变体）。

处置不是删掉它，是**推演它怎么可达**：
要单独触发 ③，册子里必须有一条**本不该登记的**（对得上的名字被登记进去）——
而那是真实可能的（把一个后来才改成同名的命令顺手登记）。
照这个思路注入，**确实红了**。三条都写进了变异脚本。

## 「看起来只有一个出口，所以拆不掉」——这句话连错四轮（2026-09-28 收尾）

`check:single-literal` 里有一行 `if (!item.where) continue;`：**没有 `where` 的登记
被完全静默跳过**。那正是「按文件豁免通病」的形状（**豁免的正是检查本身**），
今天第三次撞上。加了守卫，然后被一条变异打回来——**打了四轮才真的防住**：

| 轮 | 我改成什么 | 变异拆掉什么 | 症状 |
|---|---|---|---|
| ① | 守卫：`skip` 不是字符串就报错 | — | 没理由的登记**完全静默** |
| ② | 守卫 + `else`（合法跳过） | 守卫 | `{ what: 'x' }` 被打印成 `ℹ …——undefined` 并放行 |
| ③ | 合成一个 `if/else` | `if` | 后面两行**无条件执行**，`else` 照样打印 |
| ④ | 「失败条件与控制流解耦」 | `if` | **也错了**：`problems.push` **就在那个 `if` 的 body 里**，拆 `if` = 拆掉记账本身 |
| ⑤ | **先算结论、再按结论打印** | 记账分支 | **仍红** ✅ |

> **四轮都栽在同一句话上：「结构上只有一个出口，所以拆不掉」。**
> 而**能拆掉它的不是结构，是「结论由分支是否执行决定」这件事**——
> 只要 `problems.push` 在某个 `if` 里面，
> **把那个 `if` 改成 `if (false)` 就等于删掉这条判据**。
>
> 真正的修法是**让「有问题」成为一份数据**（`unexplained` 数组），
> 打印与记账都只看这份数据。**于是拆掉任何 `if` 都改不了「结论是什么」。**
>
> ⚠️ 这**不防**「把整段分析删掉」——那任何门禁都防不住。
> 它防的是**「逐条判据被单独摘掉」**，而那正是这四轮的实际形态。

让「ENOENT dist」与「某条断言不符」能被分开看，并提示先重跑 `npm run build`。

## 「注释里说 X 负责」而 X 那边没有检查 = 没有人负责（2026-09-28 收尾）

## 把 `main` 的 YAML 解析接过来：先量「会不会变」，再量「哪种写法会变」（2026-09-29）

### 决定的前提：换解析器会不会改变行为（不能靠推理）

**第一步：现有内容上会不会变？**
一次性对照（跑完即删）：**11 篇真实内容 × 7 个标量 = 77 次逐字段比对，0 处不同。**

> ⚠️ **而「0 处不同」只说明「现在」没差别**——那正是今天记了一整天的形态
> （「当时全是对的」恰恰是最难发现的证据形态）。**所以还要第二步。**

**第二步：哪种写法会让两边分叉？** 实测三种**合法 YAML**：

| 写法 | `frontmatterField`（逐行） | YAML |
|---|---|---|
| `title: 第 5 章: 一个结论` | **读成** `"第 5 章: 一个结论"` | **报错**（不允许裸冒号） |
| `title: 标题 # 注释` | **抛错**（主动拒绝） | 读成 `"标题"` |
| `related: [甲, 乙]` | 给**原始字符串** `"[甲, 乙]"` | **两项数组** |

> **三处都是「YAML 更严或更准」，而「报错 / 读对」都比「读错 / 给原始串」好。**
> 而 `null` 尤其危险——它会被 `?? ''` 兜成空串，于是「这一页没标题」与
> 「这一页的标题缩进了」在下游**完全一样**。

### 换的过程中抓到三件事（2026-09-29）

`summary: **文件名…**` 以裸 `*` 开头，而**裸 `*` 在 YAML 里是别名语法**。

> **而那一篇若进真实构建，Astro 的 YAML 解析器也会拒绝它。**
> **所以修的是内容（加引号），不是回退实现**——
> 回退会让读路径**接受构建侧拒绝的内容**，那正是「同一份坏数据，一边失败一边接受」。

**② 我在注释里写了一句「保留 `frontmatterField` 作为兜底」——而我没实现。**
（**「注释里写了而代码没实现」今天第七次**。）而实测证明**那句承诺是错的**：
崩溃恰恰是正确行为，静默降级才是错的。注释已改写成「为什么 `throw` 是对的」。

**③ 一条变异自己造出了非法内容。**
`second-site-real.mutations` 的第⑧条写的是
`t.replace(/^slug: .*$/m, 'title: 导出说明')`——**那会造出两个 `title:` 键，

> **那不是「变异抓到了缺陷」，是变异自己造出了非法内容**——
> 而**症状与「缺陷」在输出上完全一样**（都是「红了」）。
> **这是「变异无效」与「判据有盲区」的第五次同形。**

### 而新行为必须有**能分开两种解析器**的判据（2026-09-29）

给「标量退回逐行解析」加了一条变异，**它绿了**——因为原有语料里
**每个字段两种解析器读法都一样**。

> **判据没有覆盖新行为，而「读起来全绿」正是它没覆盖的证据。**
> 与「被测集合是空的」同族：**两边一样时，比对必然通过。**

补了两条**只有 YAML 能读对**的语料：`title: 标题 # 注释`（逐行会抛错）、
`related: [甲, 乙]`（逐行给原始字符串，而 `relationList` 剥括号后**也能切成两项**

## 合并 `main` 时实测到一个**真 bug**：别的块会覆盖 `sources` 里的字段（2026-09-28 深夜）

### 而 `check:single-literal` 在那一刻红了，**而且它红得对**（2026-09-28）

## 根因不是并发，而是 **`npm.cmd` 压根起不来**（2026-09-28，第四次「检查骗自己」）

上一条我记的是「`ensureDist` 修不了并发」。**那个判断是错的**：
`npm run build` **不带 `clean`**（`build = astro build && pagefind`，
只有 `verify` 才是 `clean && build && …`）。

真正的根因：**我为了避开 `shell: true` 的 DEP0190，把 `npm` 换成了 `npm.cmd`** ——
而 `npm.cmd` 是**批处理文件**，Node 在 `shell: false` 下**起不来它**：

```
spawnSync('npm.cmd', ['run','build'])
  → status = null, error.code = EINVAL      ← 子进程压根没运行
```

而我的判据是 `r.status !== 0` —— **`null !== 0` 为真**，
于是**每一次都被报成「build 失败」**，而真相是「它没跑」。

| | |
|---|---|
| 症状 | 34 条变异里 **2 条一直假红**（`verify:negotiation` 那两条） |
| 我先猜的 | 「并发」（`docs/cli.md` 里写明那几道门禁必须串行） |
| 实际 | **Windows 上调 `npm` 的方式错了** |
| 修法 | `cmd.exe /c npm`（实测 `status=0`）——**不用 `shell: true`**，DEP0190 不回来 |
| 同时 | **`r.error` 存在时不能说「build 失败」**——那是「压根没起来」，与「跑完且失败」是两件事 |

> **这一条我今天栽了第四次**（前三次：grep U+FFFD 把门禁自己的字面量当残缺、
> grep 空括号把 `process.cwd()` 当残缺、探针把变异门禁报成「没覆盖」）。
> **四次里有三次的错都在我的尺子上，而这一次的代价是 34 条变异里 2 条一直假红。**
>
> ⚠️ 更要紧的是：`red()` 里还有**同一个坑的第二处**（`verify` 那条走 `npm run verify`）——
> 它没发作**只因为没有变异以它为 target**，**那是埋着的雷**。一并改了。
>
> **判据：任何 `spawnSync` 的结果，先看 `r.error` 再看 `r.status`。**
> `status: null` **不是**「退出码 0」也不是「非 0」，它是**「没拿到」**——
> **而「没拿到」被当成「非 0」时，一条环境问题会伪装成 34 条门禁失败。**

> 否则「核了 5 条」会被读成「11 条都核了」。那正是今天第三次记的形态
> （「扫到 0 处」被读成「通过」）。

### `orphan-page` 那条第一次红了，而**规则完全正确**（2026-09-28）

我第一版断言「整份语料不该报 `orphan-page`」——**错得很有代表性**：
语料只有 2 篇，而**入口那篇自己没有任何入链**，所以它**必然是孤儿**、
必然被报（`orphans` 实测就是 `["入口"]`）。

正解是断言**「被链那篇不在 `orphans` 里」且「入口那篇在」** ——
两条都断言，才能证明「有没有入链」真的决定了报不报。

> **这是 2026-09-28 第四次「我以为对不上，其实量错了东西」**：
> 前三次是「注释量 HTML 侧而 docs 量 MD 侧」、「静态分析只捞到 1 条」、
> 「探针正则漏了『检查了 N 个』」。**四次里有三次的错都在我的尺子上。**

### 第三列第一版只核行为，把文档反过来说它照样绿（2026-09-28）

`cjk-slug` 那条我第一版只核「默认下报不报」。于是把文档里的「默认关闭」

**行为对、文档错，判据无感**。

> 与形态十一同源：**核的是「实现是什么」，声称要核的是「文档说了什么」。**
> 而这一列的每个说法都是可判真假的——**只要把它从文档里读出来再比**。

改成从 `AGENTS.md` 那一行**解析出「默认开/关」**再与实测比，变异立刻被抓住。

⚠️ 顺带发现我**自己加的一个条件恒假**：
`actuallyOff`（「默认**不**报」）与 `actuallyOn`（「**开选项后**报」）
**本来就是两个都 true**（「默认不报」与「开选项会报」并不矛盾），

核它要两件独立的事：① 文档说的默认行为与实测一致 ② **那个选项真能打开它**。

### 顺带：`ensureDist` 修不了「并发」，而那不是它的锅（2026-09-28）

把「`dist` 在不在」改成「清单里点名的每个 `.md` 都在 `dist` 里」之后，
那两条 `verify:negotiation` 的红**仍然出现**，而它打出的诊断是
**`⚠ build 失败，下面依赖产物的门禁结果不可信（那不是变异造成的）`** ——
**那条诊断按预期救了场**（它把「环境」与「我的错」分开了）。

单独跑 `npm run build` **成功**，所以是 `mutate()` 内部那次失败：
`ensureDist()` 判定不一致 → build，而 **build 自己会 `clean`** ——
**若此时有另一个进程在读 `dist`，就会读到中间态**。

**这不是 `ensureDist` 能修的**：`docs/cli.md` 里写明那几道门禁
**必须串行**（`verify:base` 清空 `dist`、`verify:formats` 往里塞探针），
**而并发正是它要防的事**。记在此处，**不在这一轮硬修**——
**修它要先解决编排的串行保证，那比这一轮大**。

## 静态分析量不出「级别」——只能真跑，而真跑要造三件事（2026-09-28 收尾）

补了「规则集相等」之后，表上**第二列（级别）一条都没核** ——
而「`broken-wikilink` 是 error（会让构建失败）」正是 **agent 最会照着用的那一列**。

**先试静态分析，不可靠**：`level:` 散在各规则函数内部，
「从 `rule:` 往上找 12 行」只捞到 **1/11** 条（与 `check:field-coverage`
那次「字面匹配三次自己失败」同族）。**级别是运行期属性，只能跑出来。**

真跑之后发现造语料要满足三件事，**每一条都是撞上去才知道的**：

| # | 坑 | 症状 |
|---|---|---|
| ① | **必须跑两轮**（`docKind: 'post'` + wiki） | `post` 那轮 `orphan-page`/`redundant-relation` 不报，wiki 那轮 `reserved-post-slug` 不报。**只跑一轮 7/11**，我一度以为是「语料不对」 |
| ② | **同名标题要造两对** | 被引用的报 `ambiguous-wikilink`、没人引用的报 `ambiguous-title`。**只有一对时后者被盖掉** |
| ③ | **两个「同名但不同」别搞混** | `duplicate-slug` 是 **slug 同、标题不同**；`ambiguous-*` 是**标题同、slug 不同**。我第一次造反了，只触发到后者 |

助手会再写一个 `summary:`，**后者覆盖前者**，于是那条永远不触发。

> 而真相是「我量错了东西」。** 这是今天记了一整天的形态第三次现身。
> **判据：结果与预期不符时，先查是不是量错了东西，再改实现。**

新门禁 `check:rule-levels`，语料触发 11/11，**逐条与文档声称一致**；
并加了一条「**语料没触发到的规则必须报**」——「没触发」与「都对」在结果上无法区分。

### 顺带把 `ensureDist` 的判据修对了（2026-09-28）

`mutate()` 跑「恢复后仍红」那一步时，`verify-negotiation` 报

那挡住了「没有产物」，**挡不住「产物在、但是上一次门禁留下的旧的那份」**。

> **「产物在」与「产物对得上现在的源码」是两件事**，
> 而第一版把前者当成了后者的**充分条件**。

改成：清单里点名的每个 `.md` 是否真的在 `dist` 里。

⚠️ **但要诚实说清一件事**：改完之后我立刻重跑，34/34 全绿——
**而那两条红在我手动 `npm run build` 过一次之后就不再出现了**。

**34 条里两次 build 就是好几分钟**，而那两条红正出现在 build 还没跑完时。
**这个不确定性没有消除，只是缩小了。**

## 「文档里说的还对吗」与「文档该说的都说了吗」是两个方向（2026-09-28 收尾）

顺着「第三件事」（文档与门禁之间没有「哪几条被核了」的对照表）去读 `AGENTS.md`。
13 个小节，`check:agents-doc` 核 4 组。**第五个规则小节没被它核**——
但那不是漏核，是**那道声明的判据在别处**（`check:staged` 守着
「验证通过之后、提交之前」那节）。

**真正的缺口在另一处**：`AGENTS.md` 有一张「**每次构建会跑体检**」的表，

|---|---|---|

| `ambiguous-title` | warn | 同上 |

> ——`AGENTS.md` 开头就写着「那是**给 agent 读的约定**」。

> 与形态四同源但方向相反：那一条是「集合空了还说通过」，
> 这一条是「**集合没满也说通过**」。

推导结果里没有它们就报红——**两份名单不一致 = 至少一份是错的**。

**两次变异验证**：
① 非豁免的 `wiki-ask` 用 `exit(1)` → 红；
② **豁免的 `measure` 用未登记的码 42 → 仍红**——证明**豁免没有变成「什么都能过」**。

⚠️ 顺带修了一处「结论行与实际判定不符」：豁免项的输出原本打 `✗`
（因为它含码 1），而**退出码是 0** —— 读输出的人会以为有东西坏了。

## 手写的名单必然漏——改成从文件系统推导（2026-09-28）

`check-portability` 的 `CORE` 原先是**手写的 8 个**，而实测 `src/lib/wiki/` 下
**裸 Node 能加载的有 13 个**——漏掉的是 `read-page` / `frontmatter` / `sources` /
`verify` / `wikilink`。

> 漏掉的后果很具体：**这五个里任何一个被加上 `.js` 后缀 import，门禁都不会报**——
> 而那正是本门禁第一条要治的病。**手写名单必然漏，漏掉的东西等于没被检查。**

改造过程中撞了**三次判据失误**，每一次的错都不同：

| # | 我改的 | 报的 | 为什么错 |
|---|---|---|---|
| ① | 导出名按文件名猜（`read-page` → `read-page`） | 「只有一个调用方」 | 它真实导出 `readContentPage`/`readContentDirs`，**真实有 11 个调用方** |
| ② | 排除 `check-*` / `verify-*`（理由：它们是检查器） | 「只有一个调用方」 | `check-questions` 拿金标量检索，**那是真实的第二个消费者**。而**误报会把人推向错误的修复**（去拆掉正确的分层） |
| ③ | 按「能否被裸 Node 加载」排除构建期模块 | 「只有一个调用方：`astro.config.mjs`」 | **加载能力是运行环境的属性，「是不是构建期链的一环」才是角色属性**。且改判据前必须**把配置文件纳入扫描范围**，否则「只被配置用」与「没人用」分不开 |

> 三次的共同点：**我改了判据，却没先问「新判据在正常状态下长什么样」**。
> 三次都是「门禁红了 → 我以为实现有问题 → 其实是判据有问题」。

## 「检查脚本不算调用方」——那个判断对 ≥1 成立、对 ≥2 不成立（2026-09-28）

`check:portability` 的第三条从「≥1 个生产调用方」收紧到「≥2」之后，**立刻报出 5 个「只有一个」**——
而那是**判据自己的缺陷**：它排除了 `scripts/check-*` 与 `verify-*`，理由写的是
「它们是检查器，不是产品的调用方」。

实测 `check-questions.mjs` import 了 `splitPassages`——**它拿那道金标量检索**，
改坏了 `splitPassages` 它就会红。**那是真实的第二个消费者。**

> 把它排除，等于让门禁在「只有一个消费者」时误报，
> 而**处置会误导人去拆掉分层**（`retrieve` → `context-pack` → `wiki-ask` 是一条链，
> 不是重复实现）。
>
> **「它是什么」与「它算不算」是两件事。** 一道门禁在用某个函数量金标，
> 那就是消费者；只有**故意把它弄坏**的那些（`*.mutations.mjs`）才不算。
>
> 而这个错误的危害不对称：**误报会把人推向错误的修复**
>（拆掉正确的分层），漏报只是少一道提示。

### 「绿色」这个输出有**两种**含义，而它们长得一模一样（2026-09-28 收尾）

做 `check:no-duplicate-lists` 时，连栽**两次**，而且两次都是同一个形状：

| # | 我看到的 | 我差点读成 | 真相 |
|---|---|---|---|
| 1 | 注入「跨行的重复清单」后门禁仍绿 | 「判据漏了跨行」 | **注入压根没写进去**——锚点 `export interface ReadPage` 在 `read-page.ts` 里不存在，`String.replace` 找不到就原样返回 |
| 2 | 往 `read-page.ts` 注入后门禁仍绿 | 同上 | 注入只写了**一份**清单——**一个重复本来就该是绿** |

> **「绿」既可能是「它没看见」，也可能是「压根没被喂进去」。**
> 而这两种的输出**完全一样**。
>
> 这是「它报了 ≠ 它判了」那条的**反面**：那条讲「报了不代表判了」，
> 这条讲**「没报也分不清是没看见、还是没被喂进去」**。
> 所以**每次注入都必须自证注入成功**——
> `new-gates.mutations.mjs` 的 `mutate()` 现在写回之后立刻
> **比对文件是否真的变了**，没变就报「注入无效，本条结论不可用」。
>
> 顺带一条更老的同族教训：**查锚点存不存在，比跑一次变异便宜得多**。
> 我是先跑变异（绿）才去 grep 锚点的，顺序反了。

### 判据自己也得先被验一遍（2026-09-28 收尾）

`check:no-duplicate-lists` 写完先跑自测（5 条**临时副本**，
写进 `.verify/no-dup-lists/`，**不碰真源码**），**当场抓到一条真盲区**：

> 归一化用 `\s+`（吃掉**全部**空白），而元素切分按 `,`（**保留**元素内首尾空白）。
> 于是 `['x', 'y']` 与 `['x','y']` 归一化后**不等**——本该判为「逐字相同」的
> 两种排版被判成两个不同的清单。

修法是**先切分去空白、再拼**：`items.map(s => s.replace(/\s+/g,'')).join(',')`。

> 这条盲区**是靠自测抓到的，不是靠变异**——
> 变异验证的粒度是「缺陷注入后门禁会不会红」，
> 而**根本没注入成功的变异**（上表第 1 条）**恰好被这条覆盖不到**。
> 两种验证手段量的是不同的东西，缺一不可。

### 覆盖率会被悄悄收窄，而输出一个字都不变（2026-09-28 收尾）

`check-no-duplicate-lists` 的 `ROOT_DIRS = ['scripts','src']`
是个**决定覆盖面**的字面量——把它改成 `['src']`，
「0 处重复」这个结论**一个字都不会变**，因为 `src/` 里确实没有重复。

所以补了一条**实测下限**：`scripts/` ≥ 54 个文件、`src/` ≥ 70 个
（这两个数是**实跑得到**的——第一版我凭印象写 `100 / 5`，
门禁立刻报 scripts 只有 54 个，**尺子自己先量错了**）。

> **下限定的是下限，往上不红**——仓库会长，钉住上限就会天天误报。
> 这是形态五「被测集合是空的」的变体：
> **不是集合空了，是集合被人改小了，而报告没跟着改。**

### 「同一份清单写两遍」这一天栽了四次，第四次成了门禁

| # | 清单 | 漏在哪 | 处置 |
|---|---|---|---|
| 1 | `check-portability` 的 `CORE` | 手写 8 个，**漏了 5 个** | 改成从文件系统推导 |
| 2 | `check-exit-codes` 的 `USER_CLIS` | 手写 4 个，**漏了 3 个** | 改成从文件系统推导 |
| 3 | `check-gate-list` 的 `NOT_IN_ALL` ↔ 变异脚本的 `file` 值 | 改了 A 忘了改 B | 当场手工同步 |
| 4 | `new-gates.mutations.mjs` 的 `GATES` ↔ 干净态检查的数组 | 加了第 5 道忘了同步 | 当场手工同步 + **这次加了机械检查** |

前两次的结论是「手写名单必然漏」，于是改成推导；后两次是**「两处字面量要手工同步」**——
那是推导解决不了的，只能机械拦住。所以有了 `check:no-duplicate-lists`：
**同一文件里内容逐字相同、且 ≥2 元素的 `const X = [...]` 出现两次就红。**

⚠️ 它的**边界必须写清楚**，否则下一个用它的人会高估它：

- ⚠️ **它量「字面量重复」，量不到「逻辑重复」**——后者要读懂每个函数；
- ⚠️ **它排除 `*.test.ts` / `*.mutations.mjs`**——那些是造固件的，
  `const pages = [makePage(), makePage()]` 两份**是巧合不是清单**
  （不排除时 26 处 → 排除后 0 处，26 : 3 的比例就是「判据太宽就变成噪声」）；
- ⚠️ **只报「逐字相同」的**——同名不同内容是两个碰巧同名的清单，不一定是错。

### 「量到了盲区大小」比「再加一道门禁」更该先做（2026-09-28 收尾）

`check:no-duplicate-lists` 写完、验完、接进编排之后，我**第一件事是量它还漏什么**，
而不是继续加规则。一次探针（跑完即删的临时脚本）的结果：

> 126 个文件里 **56 份不同的清单，其中跨文件重复的只有 1 份**——
> 而那 1 份还是这道门禁**自己刚写进去的** `['scripts','src']`。

两处收窄因此是**有数据支撑的**：

1. **跨文件那份**收敛成 `scripts/lib/source-dirs.mjs` 的 `SOURCE_DIRS`
   （`check-portability` 的 `PROD_CALLERS` 与 `check-no-duplicate-lists` 的
   `ROOT_DIRS` 本来就是同一个事实）；
2. **不再加跨文件判据**——1/56 的比例，加一道门禁去守它不值；
   而门禁的注释里写明了这个边界，免得下一个用它的人高估它。

⚠️ **同时纠正了一个我自己的误判**：我原以为「今天四次里的前两次
（`CORE` 漏 5 个、`USER_CLIS` 漏 3 个）本门禁也抓不到」。
**那是错的**——手写 8 个、实际 13 个，手写那份是**子集而不是副本**，
而**子集根本不是「重复」**。那两次的形态是「名单没从数据源推导」，
本门禁对它们**从来就没有任何覆盖**，现在写进注释了。
**高估一把尺子比低估它更危险**：以为漏了会去补（其实没什么可补），
以为够了就再也不会有人看它。

### 一道门禁会**把自己的锚点改没**——而那正是它该被抓住的时刻（2026-09-28 收尾）

收敛 `ROOT_DIRS` 之后，`new-gates.mutations.mjs` 里那条变异的锚点
（`const ROOT_DIRS = ['scripts','src'];`）就不存在了，于是全量跑**红了**：

```
✗ 锚点出现 0 次，变异未生效
```

这条红**是那个半小时前刚加的自检救下来的**。没有它，同一个情形会被读成
「`check:no-duplicate-lists` 对收窄覆盖没反应，判据有盲区」，
然后**为了迁就一个已经失效的锚点，去把刚收敛掉的东西重新拆开**。

> **负向验证脚本自己也是需要维护的代码**，而它腐化的方式很隐蔽：
> **重构会让它的锚点指向不存在的东西，而它的失败信息读起来像「被判据有盲区」。**
>
> 所以「锚点出现 N 次」必须是一条**独立的、自证的**失败分支——
> 它说的是「**本条变异不成立**」，而**不是**「被测门禁有问题」。
> 这两种混在一起，就会有人去修错的对象。

## 「同一件事两处实现」——2026-09-28 一天内的第四处

### 一次**误报**，以及它与真缺口的区别

同一个下午我用同一个方法（「系统性对比」）做了两件事：

| | 声称的缺口 | 实际 |
|---|---|---|
| ✅ | `docs/cli.md` 写着 `npm run check:portability`，而真实名字是 `verify:portability` | **真缺口**——照着敲得到 `Missing script` |
| ❌ | `README.md` 指向 `docs/cli.md#搜索的加载器…` 的锚点「不存在」 | **误报**——那个标题真实存在（`##` 级，不是 `###`，我 grep 时只查了 `^###`） |

两者用的是同一套推理，**结果一真一假**。分它们的不是方法，是**有没有真的去核**：

- 真缺口那条，我跑了 `package.json` 确认 `check:portability` 不存在；
- 误报那条，我**只跑了 `grep '^###.*搜索的加载器'`**（0 命中）就下了结论，
  **没去看它是不是别的标题层级**。

> **「grep 没命中」与「它不存在」之间隔着一个「grep 的模式对不对」。**
> 而我今天已经栽在这上面一次：查平台依赖时用
> `grep -lE "\\\\\\\\|/tmp|chmod"`，那个 `\\\\` 匹配的是**任何**反斜杠或 `/`，
> 于是**所有文件都命中**——我据此说"有平台风险"，其实全都不是。
>
> **两次的共同点：把「我的查询没找到」当成「它不存在」。**
> 与 [[local_simulation_missing_semantics]] 的「查不动 ≠ 空集」是同一条，
> 只是方向相反——那条是**没查到就说没有**，这条是**没查到就说坏**。

### 为什么这一天能找到四处

**因为改用「系统性对比」而不是「零散发现」。**

2026-09-28 前半段我一直在**逐个字段**地看（`original` 有没有读？`draft` 有没有读？），
找到两处。**然后改成「把两边逐项列出来对比」**（构建侧读哪些字段 vs 读路径读哪些），
一次找到**七处**；**再改成「按签名找同名导出」**（哪些函数名出现在多个文件），
一次找到**四处重复实现**。

> **一个一个看，只看到你想到要看的；列出来对比，能看到你没想到的。**
> 而后者的成本并不更高——两张表的差异，比十次「记得检查吗」更可靠。
>
> 而且**第三、四处是靠第二处的清单找到的**：第 3 处
> （`readContentDirs` 与 `readContentPage` 各算一遍）让我意识到
> 「同一件事两处实现」这个形态，于是用一条 grep 找到第 4 处。
>
> **一处的发现应当变成一次搜索，而不只是变成一次修复。**

| # | 重复的东西 | 漂开的后果 |
|---|---|---|
| 1 | frontmatter 解析（`wiki-impact.mjs` / `check-impact.mjs` 各一份逐行扫描） | 两个命令对同一页给出不同的引用集，**两边都绿** |

**共同形态：漂开时不报错。** 每处都要靠人偶然发现，

⚠️ **它量的是「字面量又出现了」不是「逻辑又实现了」**——后者要读懂每个函数，
量不到。但字面量是绝大多数漂开的载体，而**漏报的代价（悄悄多一处真值）
高于误报的代价（多写一行注释）**。

## 第 4 条的一个**具体未完成项**：构建侧的关系字段名仍是写死的（2026-09-28）

## 读路径的 `draft` 曾经完全不读（2026-09-28，第 6 处分歧）

`readContentPage` **不读 `draft`** → `pageToDoc` 恒给 `false` →
`buildGraph` 的 `filter((d) => !d.draft)` **形同虚设** →
**草稿会进 CLI 的检索与影响分析，而构建产物里没有它。**

与前五处「post 口径」不同：**这一处只要有一篇草稿就会发作**。
本站 0 篇（实测），所以没暴露；而 `verify:formats` 的草稿隔离探针
**只验构建产物**（页面 / 孪生 / OG / manifest 里没有它），**不验读路径**——
那正是它漏掉这一处的原因。

顺带发现**第七处**：读路径的 `review.status` 是 `string`（原样透传），
而 `content.config.ts` 的 zod 是 `z.enum(['pending','reviewed','stale'])`。
实测 `status: garbage` → **构建失败而 CLI 静静接受**。
已让 `parseReview` 校验（非法值当「没写 review」），并把 `PageReview.status`
收窄成三个字面量——**收窄之所以安全，正是因为加了校验**。

> 这两处是同一个动作里发现的：**类型不一致逼我去看运行时行为，
> 而运行时行为又逼我加校验。** 若我只改类型不测运行时，

## 读路径与构建路径的「post 口径」曾经三处分歧（2026-09-28）

本仓库有**两条**从内容到 `Doc` 的路：构建期 `src/lib/content.ts` 的 `toDoc`
（拿 `astro:content`），与读源码 `readContentDirs` + `pageToDoc`（裸 Node，供 `scripts/*.mjs`）。
**它们必须给出同一个 `Doc`**，否则同一页在构建产物与 CLI 回答里形状不同，
而 `wiki:ask` 的 `docId` 正是订阅者做增量同步的键。

`content.ts` 里有 **4 处** `kind === 'wiki' ? … : …`（`related` / `review` /
`original` / `wikiKind`），而 `pageToDoc` 起初**一处都没对齐**。

**为什么一直没发作**：本站 posts 里 **0 篇**写这些字段（实测无 `^related:`、无 `^kind:`）。

> **「本站没有这种数据」与「这条路径正确」是两件事**——
> 前者让后者从未被测过，而两者在输出里长得一样。

修完三处，并加 `check:two-paths` 门禁：数构建侧有几处判定当基准，
**真跑** `pageToDoc` 两种 `docKind` 逐项断言（不 grep 两边源码有没有同样的字符串——
写法可以完全不同，**行为一致才是契约**）。

⚠️ 加 `post` 那一侧时踩过一次「键在、值是 `undefined`」：
`{ a: undefined }` 与省略键在 `doc.a` 上一样，但 `Object.keys()` 与
`JSON.stringify` 不同——而 `content-manifest` 正是把 `Doc` 序列化出去的。
所以 `post` 侧是**整个键都不出现**。

⚠️ 同日还发现：给 `knowledge-gates` 的摘要加门禁时，我加了第 14 道却忘了改
写死的 `/ 13`，它打印「通过 14 / 13」。**与「少一步不会有任何报错」同家族**，
已改成从步骤列表自己数（`total="$(printf '%s\n' "$steps" | grep -c .)"`）。

### 一条**被我夸大过、后来实测推翻**的说法（2026-09-28）

我在 `page-to-doc.ts` 的注释里写过：「`post` 侧的键整个不出现，而不是给
`undefined`——因为 `JSON.stringify` 会不同，manifest 会不一致」。

**实测：两边序列化后逐字节相同。** `JSON.stringify` 会丢掉值为 `undefined`
的属性，所以「键在、值 undefined」与「键不出现」**在产物上完全一样**。
差别只在**内存里那个对象**的 `Object.keys()` / `hasOwnProperty`。

已改成实测口径，并加了一条断言把这件事钉住
（`省略键与给 undefined 在 JSON 产物上完全相同——差别只在键集合`）。

> 教训与本文件里那条「本地绿 CI 红」同源：
> **我先写下一个听起来很严重的后果，再去核实它。**
> 而核实只需一行 `JSON.parse(JSON.stringify(x))`。
>
> 顺带说明「为什么要统一写法」这个决定**仍然成立**——
> 但成立的理由是「同一约束散在多处会互为掩护」，
> **不是**「产物会不一致」。理由变了，结论碰巧没变，但那是因为我先做对了收敛。

## `verify:migrate` 靠「别人已经建过目录」而绿（2026-09-28）

2. 靠这一点把 21 道拆成两个 job（纯计算 / 起子进程）→ 定位到子进程组；

`check-gate-list.mjs` 的 4b 声称核「有负向验证的门禁，其负向验证覆盖了每一项判据」。

| ① 有变异脚本 | 读 `scripts/` 下每个变异脚本（文件名含 `mutations`）的 **`target:` 字段** | 17 道 |
| ② 台账里有一行 | 读本文件**表格第一列**的门禁名 | 15 道 |

## 发布状态对账（`check:release`）与这一天第三次 `git checkout`（2026-09-29）

### 先量到的事实：220 个提交从未反映在任何 tag 上

```
$ git tag
v0.1.0  2026-09-18  9361b2b
$ git log --oneline -1 v0.1.0
9361b2b fix(ci): 内容格式探针必须排在产物检查之后
$ git rev-list --count v0.1.0..HEAD
220
```

而 `package.json` 仍写着 `0.1.0`。**所以读的人会以为 `0.1.0` 就是当前状态。**

> `prepublish-guard` 的最后一句提醒「确认版本号、`CHANGELOG`」是**散文**——
> 而本项目栽过好几次「注释/散文里写了而代码没做」，**所以那句话要变成可判定的。**

### ⚠️ 而「HEAD 比 tag 新」**只报事实、不报缺陷**

那是「发过、之后又改了」的**正常状态**。本项目栽过「判据太宽就变成噪声」——
所以判据把它**报在输出里**（读者会看到「版本号 ≠ 当前代码的状态」），
**却不 `problems.push`**。

### `CHANGELOG` 显式关掉，而**理由是量出来的**

`v0.1.0..HEAD` 有 **220 个提交**，其中 **136 个没有类型前缀**——
而看内容，**绝大多数是这几天的内部门禁工作**（`加判据 4c…`、`README 的「30 秒开始」…`）。

**它们不是「使用者能感知的变更」。** 从 `git log` 自动生成也不行——
那 136 条要**逐条归类**，**那是判断题不是机械转换**。

> **判据逼人做它不该做的事时，人会绕开**（而不是照做）。
> 而「写一份假装完整的 CHANGELOG」比「没有 CHANGELOG」**更坏**：
> **它会让读者以为 release note 是权威的**。

所以关掉，并把理由写在源码里——**「关掉」与「忘了做」在输出上完全一样**（形态四），
**所以关掉这件事本身必须能被查到**。

### 4c 的台账解析第一版**太窄**：12 行星着「（新）」

旧正则要求「反引号后紧跟竖线」，而台账里有 **12 行**是 `` `check:two-paths`（新） ``
——**那 12 行对 4c 等于不存在**。

> 「（新）」是给人看的备注，而**机器不该因为它看不见那一行**——
> 那与「文件里没写」在输出上完全一样（**形态四的变体**）。

2026-09-29 实测：加 `check:release` 时 4c 报「三样都没有」，
而台账第 93 行**明明有那一行**——**差别只是「（新）」两个字**。

### ⚠️ 而 4g 收窄正则的代价今天就体现了：它**漏**了

4g 的「编排步数」只认「共/全部/现有/目前是 N 步」与「`verify:all` 有 N 步」两种写法，
而台账里有一句**讲 4g 自己出错过程**的历史记录：

> 台账当时写的是「编排有 44 步」（而正则要求「`verify:all`」与「有」之间没有别的东西）；
> **注意这里刻意换了写法**——那句话记的是**当时发生过的事**，
> 而若写成「`verify:all` 有 N 步」的形状，4g 会把它当成**现状声明**来核。

> **判据太窄会漏**——**这是我在 4g 那时明写过的代价，今天真的发生了。**
> 而「漏」比「噪声」便宜：**噪声会让人忽略真信号**。

### ⚠️⚠️ **这一天第三次用 `git checkout -- <file>` 收尾手动实验**

它撤销的是**那个文件的全部未提交改动**——这一轮台账上的所有改动（12 行校准、
两行新记录）**一次全没**。而我已经为这件事写过记述了**两次**，还是又犯。

> **`git checkout -- <file>` 不是「撤销我刚才那次注入」，是「把这个文件回到 HEAD」。**
> 而我要撤销的**只是那一次注入**。
>
> **处置**：手动实验之后**不要 checkout**——
> 要么用 `mutate()` 自己的还原（它只还原它注入的那一处），
> **要么先提交再注入**。
> 而**临时脚本要写成可重复运行的**，这样重建比撤销便宜。

## 发布前护栏：`prepublishOnly`，以及**不能**挂 `prepack`（2026-09-29）

实测：项目**七种 lifecycle 脚本一个都没有**，而 `private` 也没声明
（**默认 `false`，即「允许发布」**）——于是任何人在任何一个绿的分支上
敲 `npm publish` 都能发出去，而 **npm 不会替你跑 `verify:all`**。

### 挂在哪个 hook 上：查来的，不是记忆

读的是 **npm 11 自带的官方文档**
（`node_modules/npm/docs/content/using-npm/scripts.md` 第 151–157 行，
WebFetch 被拦时在本地找到的——**npm 自己就带着文档**）：

```
#### `npm publish`
* `prepublishOnly`   ← **只在 npm publish**
* `prepack`         ← npm pack / npm publish / git 依赖
```

> **`prepack` 那条明写它也在 `npm pack` 时跑**——
> 而 `check:package-files` 的判据②**每次都跑 `npm pack`**。
> 挂上去就变成套娃：打包 → `prepack` → 护栏 → `verify:all`（45 步）→ 打包 → ……
>
> **hook 名相似，语义完全不同**——而那个相似正是容易选错的理由。

所以判据④把这件事变成**每次构建都会被检查**的：`prepack` / `prepare` /
`prepublish` **一律不许被占用**，而 `prepublishOnly` 必须指向护栏。

### 而护栏自己第一次跑就被 `check:exit-codes` 判红了

我写了两处 `process.exit(1)` 与一处 `process.exit(r.status ?? 1)`，
而门禁报：**`1` 是「未归类的失败」，不该被主动使用**；
第二个表达式**它连认都不认**。

**而「门禁没过」在原有六个码里没有对应的**——它归不到任何一个：

| 看着像 | 为什么不合适 |
|---|---|
| `EXIT_INVARIANT`（6） | 那是「**本工具的 bug**」；门禁红是**正常结果** |
| `EXIT_ENVIRONMENT`（3） | 那是「读不到目录 / 网络不通」；门禁**跑完了** |
| `EXIT_USAGE`（2） | 那是「你该改参数」；门禁红要改的是**代码** |

于是加 **码 7 `EXIT_GATE_FAILED`**。

> **「检查判定不通过」与「检查跑不起来」是两件事**——
> 而它们**在那个脚本里原本共用退出码 1**，
> 消费方无法区分「该改代码」与「该改环境」。
> **那正是 `exit-codes.mjs` 存在的理由在重演一次。**

护栏的两个分支都**实测过**（临时把 `verify:all` 换成必红 / 必绿的命令）：
红 → 退出码 7、绿 → 退出码 0。**不实测就只是我写的两个分支。**

> **守卫型判据（剥注释、钉下限、查空集），正确时必然是绿的。**
> 而「我注入的东西被正确地忽略了」与「我注入的东西压根没进它的视野」
> **在输出上完全一样**。
>
> **变异要注入的是缺陷。** 守卫失效的那个状态才是可观测的：
> 这里就是「注释里的字符串被算进基准 → 基准 ≠ 名单 → 报红」。

⚠️ **而「拆守卫 + 塞注释」本来需要改两个文件，`mutate()` 做不到**
（`alsoEdit` 作用在**同一个文件**的注入结果上，实测报「第二处锚点 0 次」）。

**能只用一处达成同一失效状态，就不要用两处**：
`content.ts` 第 82 行**本来就留着**那句解释（误报的现场记录，一直没删），
所以拆掉守卫那一处就够了 —— 基准 4 → 6。

⚠️⚠️ **锚点该从目标文件里「切」出来，不该手写。**
为同一个剥离语句手拼了五次（反斜杠层数两次、漏一个星号、把双反斜杠当成一个、末尾分号），
而 `mutate()` 每次只说「出现 0 次」。**一次性脚本读出那几行**才是唯一正确的做法。

## 「绿」的**第三种含义**：变异本身无效（2026-09-28，给 `check:gate-list` 加判据时）

给 `check-gate-list.mjs` 加判据 ②½/②⅔（「理由里若断言『第 N 步是 X』就核那一步」
「每条豁免要么引用一步、要么登记」）时，**同一条变异失败了三次**，
而三次的报法**逐字相同**：`check-gate-list.mjs 仍绿`。

| # | 我注入的 | 真相 | 靠什么发现的 |
|---|---|---|---|
| 1 | 改编排第 3 步（`package.json`） | **判据一次都没执行**——理由里没有「第 N 步是 X」那种写法 | 手工跑一次编排，看 `steps[2]` |
| 2 | 删掉理由里的**否定式**步号引用 | 那种引用**本就不该**触发 ②½；而 ②⅔ 问的是「登记了吗」 | 读 ④ 那段判据自己写的排除规则 |
| 3 | 改 `NO_STEP_REF` 里那条的**理由文本** | 那是 **`Map`**——②⅔ 问的是 **key 在不在**，改 value 它不看 | 门禁印的 `豁免表 9 条，其中 8 条登记` **一字未变** |

> **形态十一说「绿 = 没看见 或 没被喂进去」。这里是第三种：变异无效。**
> 前两种靠「注入后自证文件真的变了」能分开，**第三种不能**——
> 注入成功了、门禁也跑了，**只是改的不是它在问的那一处**。
>
> **唯一分开它的办法是读门禁自己打印的那几行。** 第 3 例里它已经把答案印出来了
> （计数没变），而我在改一个它不看的字段。

⚠️ **删条目要连换行一起删**（`find` 带 `'\n'`、`replace` 是空串）——
只把条目替换成空会**留下一个空行**，而空行在 JS 里合法，条目等于没删。

⚠️⚠️ **同日另一个更贵的教训：`git checkout -- <file>` 撤销的是那个文件的全部未提交改动。**
我用它收尾一次手动注入实验，**顺手把那一轮新加的整段判据一起撤销了**——
而门禁**照样绿**（它回到了旧版本，那段判据压根不在）。
**要撤销一次注入，用 `mutate()` 自己的还原**（它只还原它注入的那一处）；
若那轮还有别的改动，**先提交再注入**。

## 「模板」还是「包」——两套准备，只有一处承诺（2026-09-29）
### 判据⑤：④ 只核「有没有写明」，**⑤ 核「写的是不是同一件事」**（2026-09-29）

④ 的 `claimsTemplate` 是**全文搜「这是模板」**——而 **别处若写一句与它矛盾的话，
④ 照样绿**，因为它只认自己搜的那一句。

> **全文搜一个词找到「有一处这么说」，不等于「没有别处说反的」。**
> 而 README 是**给人读的**，人会补一句说明——
> **补的那一句正是最容易与原句矛盾的地方**。

判据只抓**明确的对立/转向句式**（`不是模板` / `只是主题` / `当成依赖` /
`可以 npm i letterpress`）——

> **而这必然漏**：有人写「它更像库而不是模板」而正则抓不到。
> **漏比误报便宜**——误报会逼人改掉本来正确的句子，
> 而「判据太宽就变成噪声」是本项目反复交的学费。

⚠️ **而「一种说法」不能靠字符串相等判**——同义不同字
（「主题」与「模板」、`template` 与 `starter`）是常态，
判「同义」是语义问题，**机器做不了**。所以只抓**对立**，不抓「不同」。
